## 2. Slices, in order

Every slice with a migration is merged by the owner (ledger rule: the owner merges any PR with a migration or installer change unless they say "u merge" for that PR).

What is true about releasability. The application code in each slice works with or without its SQL (a feature check, or the existing 503 pattern for a missing function). But the ladder files exist in the repository as soon as a slice merges, and three installers (workspace lifecycle, account lifecycle, request withdrawal) refuse to run until every ladder file is applied. So the owner runs `real_use_action=install` immediately after each slice merge, before any lifecycle action. Install-once-at-the-end is not an option.

## 3. Named database objects, by purpose

No SQL bodies here. Names follow the module pattern. All new tables are in `customer_private`, have row security on, and have no grant to the runtime or auth logins. All new helpers are revoked from PUBLIC, the runtime and auth logins. Entry points that staff or customers call are the only ones granted to the runtime login. Tables that hold staff writes carry their own idempotency columns: staff actor, command id, request JSON, with a unique key on staff actor and command id. The `operation` CHECK of `organisation_link_request` is not touched.

## 6. Owner steps, in order

1. Review and merge the docs PR (slice 0).
2. For each build slice 1 to 4, in order: review and merge the PR (the owner merges because each holds a migration; builds never migrate). Then immediately run the protected install: the install workflow with `apply = yes` and `real_use_action = install`, everything else unchanged. Do this before any lifecycle action, because the workspace lifecycle, account lifecycle and request withdrawal installers refuse until every ladder file is applied. The install only migrates; it neither enables nor pauses (`scripts/install-customer-modules.ts:378-389`). No new workflow input is used. There is no "install once after slice 4" option.
3. Observe, after each install, with what the run already reports: the report line `customer_real_use_migrations: N applied` goes from 12 to 13, 14, 15 and 16 as the four slices install; the lifecycle installers still run (they are not refused); the customer link route still answers "unavailable" with the flag OFF. It is not part of Phase 1 and needs, at least: real sources named and vetted by the owner, rights defaults reviewed, staff trained to use warnings, suppression and redaction, the production values of the real-use switches observed (KI-41), the handling of open claims during any flag pause decided (open choice 12), and real-session acceptance of the whole flow.

Nothing in these steps is performed by this design.
