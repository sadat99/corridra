## 1. What this screen is for

One job: let one person see which routes are ready to go live, fill what is missing, keep facts fresh, and publish a pack change, without ever facing everything at once.

The owner's words that shape it (ADR-093, 26 November 2026, first hand): "ensuring nothing becomes overwhelming for anyone while not compromising with anythign needed", "always the easiest, smoothest option over complex option when that is essential and doesnt add value over 20%", "no need to have second person. one person is enough".

Design answers to those words:

- Core fields first. The default view of a route is "To Do": only the Pending Core fields and the stale Core facts. The 17 sections are one tap away, not the first thing.
- One save, one reason. Edits are collected and saved together with one reason and one authenticator check.
- Facts and pack are kept apart in words and in cost. Saving facts never touches readiness. Changing a pack setting or the status always says it resets readiness, before the person confirms.
- One person can do everything the roles allow, with each step still recorded under their name.

## 8. The route view

### 8.1 Header

`h2` the route name with flags. Below it, in order:

3. If any stale: clock mark, "2 facts are stale. Check them before relying on them." (one: "1 fact is stale. Check it before relying on it."). Staleness never blocks; this is a nudge.
4. The readiness line (section 10), from `overview().routes[].readiness`, typed `{ completeMissionTypes: string[] } | null` on the page (the service also gives the current `packId`, which the page action drops because nothing draws it); the value is null when the route has no pack or the reader is not owner or admin, and then the line is not drawn. 5. The last pack change, read from `packHistory` (which needs `audit.read`, so owner and admin; not from the overview): "Pack version 3, proposed and published by you, effective 26 Nov 2026" (the date is the pack's effective date, and the line says so). A pack that did not go through review has no proposer, and the line says so: "Pack version 3, effective 26 Nov 2026. This change did not go through review, so no proposer is recorded." When the read fails the quiet line "The last pack change is not available." is drawn instead.

It is the one way between the two views and the way back from a section: opening a section sets `section`, and choosing either segment clears it. No Back-to link.

### 8.6 Section marked Not applicable

Owner action "Mark Section Not Applicable" opens a dialog with one field, the reason (3 to 500 characters), a line "Every field in this section that is not Filled becomes Not applicable. Filled facts keep their value. Pack settings that are Core stay required." and "Mark Not Applicable". When a Locked Core row in the section is not Filled the section stays Pending after the mark and says: "This section is marked Not applicable, but Working languages and 1 more pack setting are Core and still Pending." Unmarking is a quiet "Unmark Section" action on a marked section; it stages the same way and is saved with the facts as a new version, so the section returns to its own state. Staging and merging of marks is built in PR 2a (pure library); the dialog is drawn in PR 2c.

Rules added by PR 2a (built in the pure fact form library; the screen is PR 2b):

- A custom field's row has a third answer beside Filled and Not applicable: "Remove Field". It removes the custom fact from the document, is staged like any edit and saved with the facts. A standard row has no such answer: its absence is Pending.
- "Pending" is not offered on a row covered by a section marked Not applicable. The row's help says: "This section is marked Not applicable. Unmark the section to make this field Pending."
- Choosing Pending on a content row removes its fact on save; the summary lists it as "Removed".
- "Add Custom Field" is two steps. Step 1 of 2: Define (label, section, type, and the allowed values for a choice or a list; the key is made from the label as `custom.` and lowercase letters, digits and `_`). Step 2 of 2: Value (the control of the type and the source, as above). A custom field is Filled or Not applicable; Pending is the absence of the fact.
- Numbers. The only standard number field in v1, "Days to get a visa" (`travel.visa_lead_time_days`), takes whole days from 0 to 9999, so its control has a minimum of 0. The standard allows a minus sign for a custom number field (a canonical decimal, up to 15 digits and 5 decimals), so the control of a custom number field must not carry a minimum of 0 (PR 2b: `NumberField` takes an optional `min`, 0 when it is left out, and none when it is given `null`; the custom control passes `null` and the standard whole-day field keeps 0). Money is an exact amount in minor units above zero, in its own currency, with extra decimals refused.
- Words built in PR 2b (the same words as the library, `route-pack-editor-fact-form.ts`): number "Use a number such as 12 or 12.5, with at most 5 decimals." and, for a whole number, "Use a whole number."; money "Use at most 2 decimals for USD." and "Use a whole amount for JPY."; date "Pick a date."; text "Write at least 20 characters." (the field's own minimum); a list entry "Check entry 2. {the format of the field}." and "Do not use the | sign in an entry. The route file uses it to separate values."; link "Give a web address that starts with https://." The character counter and the money decimals are refused as the person types; every other refusal shows when "Next" or "Keep Change" is pressed, and focus moves to the first invalid control.
- PR 2b: a standard field offers Filled, Not applicable and Pending; a custom field offers Filled, Not applicable and Remove Field, with "This field is no longer listed on this route after you save. Earlier versions keep it." Choosing Pending on a Filled fact says "Pending clears the saved value from the next version. Earlier versions keep it." "Keep Change" with nothing different closes the row and says "No change to keep." Pending on a Core field of a live route shows, in the editor, the caution "These Core fields are now Pending on a live route: {labels}. This does not mean the route is cleared." and never disables anything.
- PR 2b: Edit shows only for the owner, on a row that is not a Locked pack setting and whose answers are not empty; once, in the state line of the row. A row that is open for editing keeps its label and Core chip and hides its value; one row is open at a time and its draft is held by the editor, so it survives a change of view or section until "Keep Change" or "Cancel". An open draft is never dropped without asking: "Review and Save" and another "Edit" first return focus to the open row.

### 9.2 Conflict

If another save landed first (the service answers 409 `ROUTE_PACK_CONTENT_CHANGED`, question 12, answered): the page re-reads the overview, then the dialog shows "Someone saved route facts for this route first." and, for each fact both of you changed, two `ChoiceRow` answers, "Keep mine: {value}" and "Use theirs: {value}". Facts only one side changed merge without asking. The page then sends the whole merged document at the next version (the service takes the whole document, never partial changes). Primary "Save With These Choices". Nothing is lost silently.

PR 2b builds the dialog. While the page reads again it says "Checking what changed…" and cannot be closed. It never sends on its own after a conflict. Three cases, in the words below ({labels} are the first 3 labels in the order of the rows, each cut at 40 characters with "…"; one is "A", two "A and B", three "A, B and C", four or more "A, B, C and 2 more"; a section mark is "Section 5 mark"; a custom field is named by its label; a count of 1 is singular and a line with nothing in it is not drawn):

- Nothing clashes. A status paragraph, focused when the check ends (not "Save Facts", so a reflex Enter cannot save blind): "Someone saved route facts for this route first. Their changes do not clash with yours. The latest version is 7." then "Your change to {label} is kept. The other save did not change that fact." (two or more: "Your changes to {labels} are kept. The other save did not change those facts."), then "The other save already includes your change to {label}, so nothing is left to save for it." (two or more: "... your changes to {labels}, so nothing is left to save for them."), then "Check the summary, then save again." The summary shows the edits that are left and the next save is a new request with a new command id.
- Everything was already saved. "Someone saved route facts for this route first. It already includes all of your changes. The latest version is 7. There is nothing left to save." The one action is "Close" (focus goes to the unsaved bar, or to the status line when nothing is staged any more). There is no "Save Facts".
- Something clashes. The heading "Someone saved route facts for this route first." takes focus; the two lines above about what was kept and what was already saved stand in place of "Facts only one of you changed are kept as they are." (that sentence stays when both are empty); "You both changed the facts below. Choose one answer for each."; up to 3 clashing facts a step, "Step 1 of 2: Choices · Next: Choices", two `ChoiceRow` answers each, "Keep mine: {value}" and "Use theirs: {value}", neither chosen at first; a value is cut at 120 characters, a list is joined with commas, money reads "USD 45.00", a removal reads "Pending (cleared)" and a mark or a note reads "Not applicable: {note}". The last step's primary is "Save With These Choices", disabled with the visible words "Choose for Each Fact" until every clash has an answer. If another save lands first again the heading is "Someone saved route facts again first." with the same lines.

PR 2a: the merge is three way. Each staged edit keeps the base (the fact as it was when the edit was first staged), and the document just read is theirs. For a fact: theirs equal to the base means mine applies; mine equal to theirs means the edit is dropped; anything else is a conflict, including one side removing a fact the other changed and both sides adding the same custom key with different content. Section marks are merged the same way. An edit keeps the base it was first staged with, so a conflict stays open however often the stage is merged again or restored from the mirrored copy, and ends only when the person chooses "Keep mine" or "Use theirs" for that fact; while any choice is missing, "Save With These Choices" is not offered and the stage keeps its old version. The dialog always asks when a stage made on an older version meets a newer one, also when a stage was restored from the mirrored copy, even if nothing conflicts (it then lists the edits that merged without asking and the edits that were already saved). The merged save is a new request with a new command id, because the first id belongs to the document that was refused.

## 14. Accessibility

- One `h1`, the existing Settings page title. `h2` "Routes", `h2` the open route's name, `h3` sections, field labels are plain text in a list item, not headings.
- The Routes list is a `ul`. Each name is a link with the accessible name "Bangladesh to China, pack Testing, Core 14 of 20 done"; the open one has `aria-current="true"`.
- The view choice is a radio group labelled "View" (arrow keys), as `SegmentedFilter` already is. Each section link in the grid is named "5, Trade fairs and events, Pending, 2 Core pending".
- Edit buttons are named by the row: "Edit Working week", "Change Working languages". The expanded editor is a `group` named by the same words. State is announced as words by `FactMark` text, never by a shape alone.
- Staging announces: `role="status"` "Change kept. 3 changes not saved." Saving, publishing, importing and exporting each announce start (busy) and result; failures use `role="alert"`.
- Focus: opening a field moves focus to its first control, Cancel or Keep Change returns it to the Edit button; a dialog traps focus and returns it to the control that opened it (`Dialog`); after a save the focus goes to the status line; after an import error list appears focus goes to its heading; the first invalid field takes focus on a refusal.
- Keyboard: every action is a real button or link, no pointer-only path; Escape closes a dialog (not while locked); closing with staged edits asks first and the safe choice, "Keep Editing", has focus.
- Touch targets 44 px up to 768 px, including list rows, section rows, Edit and the choice rows. Contrast WCAG 2.2 AA from the tokens only; state and stale are shape plus word. Reduced motion respected; the only motion is the existing dialog open and the in-place row expand, each under 300 ms, nothing plays on its own.
- Text reflows at 200 percent; no information is only in a tooltip. Values use `dir="auto"` and wrap. Disabled choices state their reason in visible text.
- Test selectors follow the accessible names above (roles and names, not class names). Existing `id` and `name` values are untouched.
