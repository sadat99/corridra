# UX update plan: verification record and addendum, 24 October 2026

Status: dated record, proposed. The facts here expire; [the UX charter](ux-charter.md) does not. Where this record and the charter differ, the charter wins.

Subject: the owner's "final strict plan for parallel Claude Code sessions" of 24 October 2026, supplied in a session. The plan is not stored in the repository, so this record is written to be read without it. Where it mentions the plan's own questions (Q1 to Q3) or waves, it uses the plan's names.

Method: the full V3 contract, product vision v2.1, UI direction, art review sheet, known issues, the ADR statuses and the mission mail proposal were read. Each factual claim in the plan was then checked against files at main `b48ec05` and the open pull request list. Not done: the app was not run, the unit, integration and browser suites were not run (only the document tests, on the files added here), and no production setting was read.

## 1. Result in brief

- The plan's baseline holds. Main is still `b48ec05` and `node scripts/v3-context.mjs verify` passes.
- 22 statements are confirmed (section 2).
- 10 statements differ from the system today (section 3). The largest is an open pull request, PR171, that builds the language switcher with a different design from Lane 2.
- 17 places have no guidance in the plan: where it meets a locked rule or an existing part, or a part of the system it does not place (sections 4 and 7). Each has a default placement, marked as judgement, so work can proceed without waiting.
- 7 process gaps would stop or slow parallel lanes (section 5).
- 8 decisions need the owner (section 8). Four of them block Wave 1.

## 4. Alignment flags: no guidance in the plan

Each flag has what was found, a default placement chosen by judgement under the charter, and whether the owner must call it. Defaults are proposals about labels and position. None touches data or permissions.

**A1. The customer navigation is named by the contract and locked by UI direction.** UI direction locks "Home, My Work, Companies, Results, More" and says the file is changed first, with the reason. The contract (section 4) and requirements V3-04-043 to V3-04-045 name the same set, and the register text is hash-checked, so it cannot be edited. Default: Lane 4's first commit amends the navigation table, the customer kit table and the glossary in UI direction with the owner's recorded approval. The pull request cites V3-04-043 to V3-04-045 and V3-07-019. The register is left alone and the amendment is recorded in the work log. A search for the navigation finds `tests/operator/v3-billing-ui.spec.ts`, `tests/operator/v3-service-requests-ui.spec.ts` and the capsule rule in `tests/design-system.test.mjs` (`.guide-tabs a`); Lane 4 confirms the full list before editing any of them. Owner call: confirm the new labels. Note that "Library" must keep "Results" visible as a heading, because "what results did we achieve" is one of the contract's five questions.

**A2. "Your Move", "Move card" and "Them" meet the plain-language rule.** UI direction rule 4 bans figures of speech and names "next move" as an example. The glossary says to use the real role (buyer, supplier) in interface text. The shipped email already avoids the word ("One thing needs you"). Default: keep the owner's names for the structure and in code, put every user-visible string in the catalogue so a label is one edit, and prepare a plain fallback set for the cover-the-words test: "Waiting for you" for Your Move, "Supplier" or "Buyer" for Them, "Corridra team" for Corridra, "Where this request stands" for the Road. In every language the names are translated by meaning, not literally. Owner call: yes, after the test.

**A3. Three pages already show one piece of work, with three ids.** `/account/requests/[requestId]` (request and progress), `/account/missions/[resourceId]` (the accepted Mission Room under Results, with the comparison matrix and decisions) and the plan's new `/account/rooms/[requestId]`. The plan does not mention the existing Mission Room. No join between a request and a saved mission is proved. Default: the new Room is a composition above both. It is keyed by the request, shows the Road and message strip, and mounts the existing comparison matrix and `SavedCommercialReport` as the Compare and Evidence lenses only where a readable link between the two exists. Where none exists it links out and invents no join. Both old URLs keep working. Lane 1's inventory states the link or its absence. Owner call: no.

**A4. Three owned parts are not mentioned.** `JourneyBar` (UI direction: "work items show the journey bar", used today only in the request flow), `NextStepCard` (locked: one per screen, first on Home and on a piece of work; used today only on the account home) and `FactLabel` (the five trust names with icon and plain line). Default: the Road is the work-item journey bar. It reuses the same list, `aria-current` and done markers and does not edit `journey-bar.tsx`. The first move on the front door is the next-step card. The trust seal is `FactLabel`, not a second set of five silhouettes and glosses. Owner call: no.

**A5. The Road mapping runs backward and cannot light every step.** The legal path is MEETINGS, FOLLOW_UP, COMMERCIAL_PIPELINE, CLOSED, and COMMERCIAL_PIPELINE can also be reached from ACTIVE or TARGETING (`packages/missions/src/index.ts`, `missionCommand`). The plan maps FOLLOW_UP to step 6 and COMMERCIAL_PIPELINE to step 5, so the marker would step back. No status means Compare or Decide. ON_HOLD stores `held_from`, which the customer cannot read, so the marker position is unknown. Default for ADR-0067: DRAFT and QUALIFICATION to Define; ACTIVE, TARGETING and OUTREACH to Find; MEETINGS to Visit; FOLLOW_UP, COMMERCIAL_PIPELINE and CLOSED to Follow through, each with a plain sub-line taken from the status; ON_HOLD with no marker and a side note; CANCELLED as a side note. Compare and Decide light only when a readable record for the same piece of work exists (a delivered report, a recorded customer decision), and otherwise read "not tracked yet". A property test over the transition graph proves the step never decreases. Owner call: confirm at ADR-0067.

**A6. The holder badge cannot be derived as planned.** The plan derives it from status and who wrote the latest reply. Replies are team-only, so "You" and "Them" can never come from them. Default: in Phase 1 the Road carries no holder badge. A holder appears where it is true by construction: on front door cards for items the person holds, and on service request rows where the status says who waits. "Them" is shown as Supplier or Buyer and arrives with Move records and the Reply Page. Test participants are told this before the cover-the-words test. Owner call: no.

**A7. Workspace and role scope is not mentioned.** A person can belong to several customer workspaces with different roles (workspace chooser, member roles, leaving). The front door and areas are per workspace. Default: every front door card and count is scoped to the active workspace and the person's role. Other workspaces show only a count of items waiting, never their content. Sample or real mode is read per tenant. Owner call: no.

**A8. The planned front door has no start action.** The account home today leads with a next-step card to start or continue a request. The plan's empty state shows only the latest mission. The money path starts with a request. Default: the front door always carries one quiet "Start a request" action, and it is the primary action when nothing waits. Move sources are confirmed against the inventory; the first candidates are an unfinished draft, an unanswered workspace invitation, a company link waiting on the customer, a delivered report with no recorded decision, a new team reply, and a service request in status `quoted`. Owner call: no.

**A9. The Road motion is longer than the rule.** UI direction allows 120 to 220 ms for state changes only, and the token is `--dur`, 160 ms. The plan says 200 to 250 ms and a card that travels. Default: the marker advances inside 220 ms using the tokens, honours reduced motion, and no card travels. Owner call: no.

**A10. Seals and an emblem need drawing, and inline SVG is banned.** `tests/design-system.test.mjs` fails on any `<svg>` outside a fixed list. Default: build the emblem and Road line from CSS and `CorridraIcon` glyphs. If a true diagram is unavoidable, the owner approves adding exactly those files to the diagram exceptions, as the route diagram already has. Owner call: only if needed.

**A11. Trip features sit beside a hard product boundary.** The vision and contract say Corridra is not a travel, hotel or visa service. The plan has a Trip lens, a Trip Book, a boarding list and a countdown. Default: these show the commercial itinerary only (meetings, visits, programme days, readiness of participants). They never book, sell or advise on flights, hotels or visas. The charter states this as a boundary. Owner call: no.

**A12. Pulse touches requirements that are GATED, and the contract asks for more evidence per pull request.** V3-06-009 (authorized real communications and notifications) and V3-09-045 (provider and outreach restrictions) are GATED in the register. The plan's lane evidence does not list requirement IDs or original and destination paths. Default: Lane 7's pull request cites those IDs, leaves them GATED or PARTIAL, and never calls Pulse commercially live. Every lane pull request lists changed requirement IDs and the original and destination paths, as the charter's section 6 says. Owner call: no.

**A13. PR171 and Lane 2 are two designs for the same thing.** PR171 (owner decision "option A", recorded in its work-log entry): static pages stay English, the visitor's choice lives in the browser (`localStorage`, `corridra.language`), five languages (English, Bangla, Chinese, Spanish, Arabic with right-to-left), release by `CORRIDRA_LANGUAGES_REVIEWED`, drafts shown by `CORRIDRA_LANGUAGES_PREVIEW`, header, footer and skip link translated, 23 catalogue tests and 10 browser tests. The plan: cookie, browser language and country, `messages/released.json`, `CORRIDRA_UX_I18N`, seven languages with French and German. Default: PR171 is the base. Lane 2 becomes phase 2, after PR171 merges: ADR-0062 records what PR171 does; `CORRIDRA_UX_I18N` and `released.json` are dropped (with neither language setting present the product is unchanged, so PR171 already is the off state); new strings for new components go into the same message module; a test ties the UI language list to what `displayDate` and `displayMoney` accept; each released language has a reviewer name and date on record; the 75 stylesheet lines move out of `globals.css` into a component stylesheet as a pure move; French and German stay later additions. Two consequences to state plainly. Browser-only storage means the server does not know the visitor's language, so mission mail stays English until ADR-0063 stores a language in notification preferences. The privacy page does not yet mention the stored choice, which needs the owner's review (PR171 says so too). Owner call: yes, see decision 1.

**A14. Link-based recipient pages, the helper area and the founder view have no home.** `/buyer` (private introduction), `/client` (private mission progress), `/programme` (programme outcomes) and `/mute/[requestId]` are reached by a link, not by the customer navigation. The plan's route classes are customer, public, staff, contributor and API. `/contributor`, `/network` and the founder page `/operator/owner` are separate audiences with locked navigation sets in UI direction. Default: add a "recipient by link" class. These pages stay outside the customer navigation, and the All tools test excludes them with a written reason. `/buyer` is the base the Reply Page grows from. Contributor and founder front doors follow the charter shape in a later wave. Owner call: when to schedule them.

**A15. The plan's test gate differs from the locked one.** The plan uses a cover-the-words test with 8 of 10 users including Bangla readers. UI direction also requires a five-person task test and blind users with TalkBack, VoiceOver and NVDA before guided screens ship, and withholds the claims "easy for any literacy" and "usable without sight" until then. Default: keep the plan's test as Gate 2 and add UI direction's two as conditions for those claims, not for merging. All new capabilities stay behind switches in the meantime. Owner call: no.

**A16. Locked parts not yet covered.** The four states are loading, nothing here yet, something went wrong and no internet. The plan lists only empty, loading, error and denied. The accessibility menu in More (language, text size, read aloud, stronger colours, less movement) is locked and unbuilt. Default: add "no internet (keep going, send later)" to every new screen's states; the language control from PR171 stays in the header, and the accessibility menu is unchanged and not part of this revamp. Owner call: no.

**A17. My Work holds delegations.** V3-04-045 says records within My Work may be missions, sourcing engagements, meetings and delegations. The plan renames My Work "Missions". Default: the Missions area has two sections, requests and missions, and programmes. Lane 10's programme room is reached from there. Owner call: no.

Neither file is in the plan's shared files table. Both are append-only, as KI-07 says. This pull request adds its own two entries.

Rule: after adding the label, list open pull requests with it again; the lowest pull request number holds the lock and the others remove their label and wait.
- **P4. Local test runs in the cloud container have two traps the plan omits.** Operator test 8 (`workspace.spec.ts:2403`) fails on clean main there (KI-19), so compare with clean main before blaming a change. The Chromium path differs between notes (`chromium-1194` in KI-12, `/opt/pw-browsers/chromium` in KI-19); use the one that exists. The operator suite needs the native PostgreSQL steps in KI-15.
- **P5. Budget classes are missing for new screens.** Default classes: All tools, operator Move panel and reply review queue are "record, queue or report" (4 and 2.5), with All tools groups folded and counted; programme room is a record (4 and 2.5); the status-link page is a record; fair pages are reading pages (6 and 3); the Reply Page is a flow step (1.5 and 1). Your Move is a landing page (5 and 3) and the Room a record, as the plan says.
- **P6. Branch arithmetic.** At most eight names including main. Six are in use with this session's branch. Retiring `ccr-998044a6-w7yufu` (merged) frees one. PR171's branch frees one when it merges. `fix/view-as-preview-polish` and `docs/network-release-status` hold unmerged commits and need an owner decision. Two lanes can start now (Lanes 1 and 3 share no files). Deleting `ccr-998044a6-w7yufu` makes room for a third, and PR171's branch for a fourth once it merges. This pull request's branch also holds a name until it merges. Keep one name spare.
- **P7. Branch reuse after squash.** KI-17: restart a branch from main after any squash merge. The plan says delete after merge, which is the safe form.
