# ADR043: Customer command authority for canonical programme context

Status: implemented locally; focused acceptance in progress. Optional synthetic authority only; no cloud installation, feature activation or accepted full organiser journey is claimed.

## Existing authority and preservation mapping

The canonical programme already exists in app.delivery_programme. Its versioned organiser, market, purpose, start/end, time zone and responsible-actor context already exists in app.delivery_programme_context (migration0025). DeliveryExperienceService.context and delegationContextInput are the current staff ports. Existing app.guard_delivery_experience enforces staff actor, tenant access, owner/admin/operator role, exact field sets, market/time-zone references, version order and a responsible authorised staff member. The row/event trigger also requires real staff or the narrowly accepted ADR037 programme-creation command. A customer provider proof is deliberately not staff authority.

Reuse the canonical context table and its version history. Do not create a second programme backend, invent a staff session, grant broad service membership, weaken an original permission, edit migration history or rewrite a context row. Context changes require a new independently reviewed optional customer port, rather than a navigation repair.

The same migration's app.delivery_agenda has a different contract: at least one existing imported participant mission is required, and CONFIRMED requires actual scheduled/held meetings for the relevant participants. Independent customer registrations and their original private missions can belong to different authorities. An objective summary grants no mission transfer or meeting authority. Keep the original agenda/import/meeting/report path unchanged. General programme activities and independent commercial coordination require their own explicit mapping; do not make empty mission references or invented confirmed meetings satisfy the existing agenda guard.

## Proposed bounded addition and blast radius

Add an opt-in customer context command after accepted programme authority. Only the current verified/admitted owner or admin of the exact synthetic customer programme may append a context version. Inputs reuse the existing market, time-zone, date and text schemas; the command ID and expected current version are explicit. Market is a country or trade bloc, independently of meeting location or service coverage. A selectable market must not claim local delivery is active.

A separate private one-use execution grant should bind the fresh proof, backend PID, transaction ID, exact canonical context-table OID, full normalised row digest, programme workspace, real customer initiator, active service executor, random unreturned nonce and short wall-clock expiry. Runtime/auth cannot mint/read grants. Recheck admission, role and proof after workspace/programme/event lock waits and before returning. Reuse canonical programme/version/event locking; document lock order against the staff path before implementation.

A forward additive migration may narrowly extend only app.guard_delivery_experience and the currently accepted app.record_change with an exact customer-context branch. Require the known dependency function hashes/security attributes; unknown drift blocks installation. Preserve the original staff predicate, source-rights, fresh-MFA disclosure clauses, old JSON validation and every unrelated table branch byte-for-byte. No RLS, membership, original record or approved migration file changes. ADR037's programme-creation grant must retain its original table scope; never reuse its nonce to authorise a context row.

The configured service may execute the canonical insert, with actual customer attribution retained separately. It must not become a pretend human owner. The proposed new customer row has an explicit ownerKind=CUSTOMER discriminator and ownerId bound to the actual admitted customer principal. Existing rows without the discriminator retain their original staff-owner meaning;the staff port and its exact original JSON contract stay unchanged. A new customer port must validate the discriminator and cannot write staff ownership. This is an explicit versioned responsibility extension,not an identity merge or changed meaning of old records.

Actual source inspection shows the original institution report projects context with details minus ownerId and reason. Preserve that withholding and original snapshot cutoff;do not add other private identity fields or rely on an exclusion list for new participant DTOs. New customer/participant reads must use a positive allowlist containing only programme context plus the nonprivate owner-kind label. Owner/customer principal/executor IDs remain internal. Existing staff raw-context rendering and original staff context edits require explicit compatibility tests for customer-discriminated versions. No private participant/source,publication,recipient or financial rights are granted.

Read access for programme owners/admins and active registered participants must be separate explicit ports. Return only the current programme context allowlist, with bounded history and short scope expiry. Participant revocation removes programme context visibility without changing independent private mission rights. Do not expose internal executor, principal, request or tenant references through a participant DTO. Existing imported participants and private publication links keep their original scopes and snapshots.

## Acceptance and rollout

Tests must snapshot populated original rows, function definitions/attributes/ACLs, RLS and migration receipts. Assert only the documented new guard/event branches differ; exercise old staff/MFA/import/agenda/report behavior unchanged. Test owner/admin success, member/other workspace/participant write denial, forged settings and proof, temporary lookalike relations, unrelated-table denial, exact retry and supersession, concurrent versions, expiry/revocation after all waits, and event/audit/outbox atomicity with actual customer/service attribution.

UI belongs under the existing programme card and participant programme view. Use a clear target-market label and preserve country/bloc, meeting location and service availability distinctions. Show original dates/time zone and a visible reason/history for changes. Do not add capacity, eligibility, price, payment, agenda confirmation or outreach controls without their actual reviewed backend. Verify empty/loading/error/conflict/retry/expired/revoked/interrupted states, keyboard, mobile/tablet/desktop and accessibility.

New exposure must default off, require existing synthetic/nonproduction prerequisites and remain production hard off. No cloud installation, real admission, provider/outreach/payment/inference activation or D01–D06/D08 change. Actual managed-provider end-to-end acceptance remains independently NOT VERIFIED. Rollback disables the new port and retains canonical context versions, consent and event history. Full independent Delegation OS and economics are separate acceptance scopes.
