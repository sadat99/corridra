## Decision summary

1. One base. Every source (staff research, partner organisation, individual partner, data platform) feeds the same candidate record, which points at the same structured profile version. A candidate that staff confirm from a public source becomes a target in the existing organisation, source, relationship, target, assessment and introduction records; the partner's or platform's own data stays in the candidate row. No organisation-like table, no second research engine, no second ledger, no second permission system.
2. Nomination is not identity. A supply source nominates a company. The supply flow lets staff target a company only after it exists in `app.organisation` from a public source, ingested through the existing path with one of the five ADR-079 public types. This is a staff rule backed by one SQL refusal in the supply module (a MATCH to an organisation whose current rights type is `licensed_dataset` or `other` is refused); the ADR-079 wrapper and the 8-argument ingest stay unchanged and never refuse. Agreement-backed data (partner, platform) stays in tenant-scoped candidate rows. The residual risk is named in section 4. No ADR-079 amendment is needed.
3. Two rights registers, no third. ADR-079's `organisation_source_rights` describes where an organisation's identity came from. `app.data_rights_policy` describes the licence and agreement of a supply source's `source_record`. The supply registry holds operations only (kind, status, connector configuration) and points at both.
4. ADR-079 slice B is built first and unchanged (S1). No supply field is added to it.
5. The seller sees one counterparty, Corridra. The supplier is never named to the seller or the buyer. Mode A (Corridra facilitates) is today's ADR-018 path. Mode B (the seller meets the buyer) is paid by a disclosed introduction fee line on the existing quote and ships locked.
6. Everything ships off. The module has its own control and app switch. Partner kinds, the platform kind, connectors, Mode B release and any personal-data path each have a separate closed control that no installer choice can open.
7. Each slice is role-agnostic (buyer, supplier, distributor, partner), so Source and Organise reuse it without change.

## 2. Principles that every slice obeys

- Staff tenant. Every supply row is in the tenant that holds the mission (the intake tenant for real requests). A seller workspace never holds supply rows; it reads only what is published to it.
- Provenance. Every new tenant table carries `tenant_id`. Real and synthetic never meet: the synthetic policy and the ADR-056 real-use pair (`real_use_add`, `real_use_read`, using `app.real_use_allowed(tenant_id)` and `app.tenant_processing_purpose(tenant_id)`, as at `0002_real_request_authority.sql:420-422`) are both present on every table.
- Append-only. Every new table except `app.supply_sync_run` has `app.reject_rewrite()` on update and delete. Changes are new versions or new decision rows. `app.supply_sync_run` is the one guarded mutable operational table (section 3.4); its history is the append-only `app.supply_sync_event`.
- Opt-in per mission. A supply mission is a mission with a `supply_engagement` (section 3.7); that one definition is used everywhere below. A profile version alone changes no behaviour. Every other mission behaves exactly as today, with the module installed and enabled.
- Commands. Every write goes through one SECURITY DEFINER command function with a command id, a request hash and a stored result in `app.supply_command` (tenant, id, actor, action, request hash, result ids). An exact retry returns the original; the same id with changed content is refused with "Command ID reused with different values" (the research wording).
- Events. Every new table that records a decision has the AFTER INSERT `app.record_change()` trigger, so its event, audit and outbox rows are written in the same transaction with ids, version, status and role only. No text, amount, name, email or reason enters an event.
- Source-reported. Nothing in this module writes `verified`. Partner and platform data read "source-reported" everywhere. Verification remains the existing independent ADR-017 publication.

## 3. Data model

All tables are in schema `app`, tenant-scoped, RLS enabled, no DELETE grant and no UPDATE grant; every table except `app.supply_sync_run` is append-only. Read policies use `research.read` roles (owner, admin, operator, reviewer, viewer); writes use command functions that check `research.manage` roles (owner, admin, operator) unless stated. "Fresh MFA" below means the existing `app.fresh_mfa()` (`migrations/0001_identity_tenancy.sql:95`), as the staff service-quote functions use it (`customer-service-request-migrations/0001_*.sql:689`).

### 3.1 Structured profile (role-agnostic)

`app.counterparty_profile_version`: `id`, `tenant_id`, `mission_id`, `role` (BUYER, SUPPLIER, DISTRIBUTOR, PARTNER, the `recipient_disclosure` set at `0025:23`), `version` (unique per tenant, mission, role), `target_profile_version` (the free-text version it was written beside, nullable), `fields` jsonb, `fields_digest` (sha256 of the canonical JSON), `reason`, `created_by`, `created_at`. CHECK on `jsonb_typeof` and size (at most 8000 bytes). The JSON shape is one strict schema in `packages/domain/src/counterparty-profiles.ts`:

The route (origin and target market) is not a field: it comes from the mission's route assignment, so a profile cannot disagree with its route. Saving creates version n+1 with an expected-version check; a stale version is refused with "This profile changed. Reload it and try again." Every candidate, brief card and research record names the profile version id it was made for; a connector request names the brief card version it was built from (section 6.1). Earlier tasks keep their version. Seller confirmation of a profile through the ADR-072 pinned confirmation path is possible later and is not part of S2 (owner decision 17).

### 3.2 Source registry

`app.supply_source`: `id`, `tenant_id`, `kind` (`staff_research`, `partner_organisation`, `partner_person`, `data_platform`), `created_by`, `created_at`. The kind never changes.

`app.supply_source_version`: `source_id`, `version`, `status` (`no_agreement`, `active`, `paused`, `expired`, `retired`), `label` (internal, 3 to 120 characters), `source_record_id` (the `app.source_record` that evidences the source or its agreement; FK by tenant), `default_retention_months` (1 to 24), `agreement_ends_at` (nullable), `organisation_id` (nullable; set for `partner_organisation`, must be an existing organisation the tenant can see), `connector` jsonb (nullable; only `data_platform`; section 6), `reason`, actor and command columns. Unique per source and version. Rules enforced in SQL:

- `staff_research` needs no agreement and is the only kind whose `status` may be `active` while the `partner_kinds` and `platform_kind` controls are closed.
- `partner_organisation`, `partner_person` and `data_platform` may be `active` only when their control is open and the current `app.data_rights_policy` version of `source_record_id` exists, is effective and has `retention_until` in the future. For `partner_person` that source record is the partner's agreement record, separate from the network profile's eligibility source. Until then they can exist only as `no_agreement` candidates. No such row is seeded; no platform or partner is named by this record.
- Connector settings (`connector`) can be written only by an owner or admin with fresh MFA.
- Retention of a candidate is the earliest of the source record's `retention_until`, the agreement end and `default_retention_months` from the observation (owner decision 15).

`app.supply_source_member`: `source_id`, `principal_id` (a contributor with a `network_profile` in the same tenant), `version`, `active`, reason, actor. A partner organisation acts only through these named persons.

### 3.3 Candidates

`app.supply_candidate`: `id`, `tenant_id`, `mission_id`, `profile_version_id`, `source_version_id` (the exact source version used), `method` (`manual`, `file_import`, `partner_submission`, `connector`), `import_batch_id`, `network_task_id`, `sync_run_id` (each nullable, exactly one set for its method), `external_key` (nullable; the provider's or file row's id; unique per tenant, mission, source and external key, so a re-run or re-import never duplicates), `company_name` (1 to 160), `country` (FK `app.country`), `website_host` (nullable, lowercase host), `public_identifier` (nullable), `size_band`, `counterparty_types`, `nomination_note` (at most 500, internal, accepted only from manual staff entry, never from a file, a connector or a partner), `name_key` (computed with the ADR-079 name-key rule), `warnings` (includes `personal_name_check` when the company name has no legal-form word, the ADR-079 rule), `nomination_source_id` (the `source_record` of this nomination, kind `observation` or `document`), `observed_at`, `retention_until`, `licence_scope` (`internal_only` or `publication`, copied from the current `data_rights_policy` `permitted_reuse` at intake; `publication` for staff research from public types), `created_by`, `created_at`, `command_id`.

Personal data, said exactly. The table has no column for a person's name, email, phone or other contact detail. `company_name` and `nomination_note` are refused when they hold an email shape (`[^[:space:]@]+@[^[:space:]@]+\.[^[:space:]@]+`) or a phone shape (a run of 7 or more digits, optionally starting with `+`, that may contain spaces, dots, dashes or brackets), with "Remove contact details; personal data cannot be recorded here." `public_identifier` and `external_key` are not checked for phone shapes, because registration numbers look like them. A company name can still be a sole trader's name, which is personal data; it raises `personal_name_check` for staff to look at, as ADR-079 does at ingestion. So company-level data is the design limit, not a guarantee that no personal data is ever present.

`app.supply_candidate_review`: append-only decisions per candidate: `QUALIFIED`, `WRONG_FIT`, `DUPLICATE`, `EXPIRED`, `REJECTED_SOURCE`, with `reason_code` and reason. For candidates from a partner, the reviewer must differ from the submitting contributor and from the task's assigner (ADR-028 independence).

`app.supply_candidate_match`: append-only `MATCH`, `NO_MATCH`, `REVERSE` decisions linking a candidate to one `app.organisation` id, with `reverse_of` pointing at the exact earlier decision (the ADR-017 pattern). A MATCH is refused unless the organisation passes the ADR-079 same-context rule, is not suppressed and is not under a current do-not-contact row (section 3.6). A MATCH is also refused, with "This company was recorded from a licensed or unclassified source. Record it from a public source first.", when the organisation's current ADR-079 rights record has source type `licensed_dataset` or `other`. An organisation with no rights record (`unrecorded`, which is every organisation ingested before S1) is not refused. The refusal lives in the supply match function only; the ADR-079 wrapper and the 8-argument ingest are not changed and still never refuse.

### 3.4 Imports and sync runs

`app.supply_import_batch`: file digest, row count, accepted and rejected counts, per-row result codes (row number and reason code, never the row text), source version, profile version, mission, actor. Unique per tenant, mission, source version, profile version and file digest, so the same file for the same brief returns the first result, and the same file for another mission or brief is a separate batch.

`app.supply_sync_run`: source version, profile version, status (`queued`, `running`, `stopped`, `failed`, `completed`), counts, `last_success_at`, `last_error` (`timeout`, `too_large`, `refused_host`, `refused_address`, `bad_status`, `schema`, `rate_limited`, `stopped_by_staff`), lease columns copied from `communication_dispatch` (`attempts` 0 to 3, `lease_until`, `lease_id`, `available_at`). It is the one mutable table in the module, guarded like `communication_dispatch`, which is updated only inside its lease and finish functions (`migrations/0009_controlled_communications.sql:255`, `:262`; `migrations/0028_operations_control_center.sql:200`). ### 3.5 Seller decisions, buyer observations, release

`app.supply_seller_decision`: `tenant_id`, `mission_id`, `target_id`, `workspace_id` (the seller workspace that owns the mission through `owned_request`), `decision` (`APPROVED_MODE_A`, `APPROVED_MODE_B`, `DECLINED`), `decline_reason` (`NOT_A_FIT`, `ALREADY_KNOWN`, `OTHER`), `report_version` (the published report version the seller saw), customer principal, command id. `app.supply_contact_release`: target, contact chain id, seller workspace, the Mode B seller decision id, the acceptance evidence (a `buyer_response` id with status INTERESTED, or an `ACCEPTED_INTRODUCTION` observation id), the consent observation id (`CONSENTED_TO_SHARE_CONTACT`), `source_id` (a `source_record` of kind `observation` written with the release, the evidence a later fee entry cites), owner or admin with fresh MFA. The seller reads released contacts only through one SECURITY DEFINER function `customer.supply_released_contacts(workspace)`, which repeats every check at read time: the release, the inactive-contact and opt-out check, `valid_until`, the do-not-contact row, and both controls. A contact withdrawn or corrected after release stops being shown; a corrected version is not shown until staff release it again. It does not read `app.private_contact_state` directly, because that view is `security_invoker` and has no opt-out status (`:232-243`).

`app.supply_partner_reveal`: the seller's decision to let the partner on one task see their identity: seller workspace, mission, network task id, brief card id and version, customer principal, command id. It is keyed by task (a task has one assignee); the customer side never sees or sends a partner principal id, and the server resolves the assignee from the task's ASSIGN event. Owner or admin of the workspace with a fresh customer session proof. The seller is never shown the partner's name; the choice reads "Let the Corridra research partner working on this brief see your company name." (D2, D7).

## 4. Owner decisions 1 and 2 resolved by design

### Slice B ships first and unchanged (packet OD-1)

The packet recommended building ADR-079 slice B "with supply fields added in the same file". This record chooses to build slice B exactly as ADR-079 designs it, as S1, and to put every supply field in the supply module. Reasons:

1. Dependency direction. Slice B is a file in the real-use ladder, which every optional installer applies first. A supply column with a key into the supply module would make the ladder depend on an optional module installed later. A plain column with no key would be a second, unchecked copy of what the candidate row holds.
2. No accepted design changes. Adding columns to the rights record changes ADR-079's design and would need its own reviewed amendment. The owner asked that nothing break by mistake.
3. The right register. The rights record is per organisation and about identity. A licence or agreement is per source, and `app.data_rights_policy` already models it (fact 7). ADR-079's rejected-options table says it "stays the route for V3-05-043 and a licensed dataset (Phase 2)" (ADR-079 line 151).

How the registers relate, with no third register:

| Register                                                        | Unit                | Answers                                                               | Written by                                |
| --------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------- | ----------------------------------------- |
| `customer_private.organisation_source_rights` (ADR-079 slice B) | one organisation    | which public source type this identity came from, warnings, review-by | the ingest wrapper, rights adjust         |
| `app.data_rights_policy` (ADR-025)                              | one `source_record` | licence, permitted reuse, retention, jurisdictions, transfer          | staff, per agreement-backed supply source |
| `app.supply_source_version`                                     | one supply source   | status, kind, connector settings; points at the `source_record`       | staff                                     |

A supply candidate reads its licence scope from the second register at intake and copies it into its own row, so a later licence version does not silently rewrite history. V3-05-043 stays PARTIAL.

### The global organisation catalogue (packet OD-2)

Problem: `app.organisation` has no tenant and is listed to staff of every tenant (fact 4), and ADR-079 says the rights record never changes who sees an organisation in customer search. Licensed or partner data written there could leak beyond its licence.

Decision: nomination is not identity. A supply candidate stays in its tenant-scoped row. To become a target, staff MATCH it to an organisation that already exists, or first ingest the company through the existing ingest with the ADR-079 wrapper, from a public source of one of the five public types (`government_registry`, `company_website`, `trade_body_list`, `event_list`, `staff_research`). The supply screens offer only those five types for this step. The existing ingest already demands a `PUBLIC` `public_record` source with an `https://` locator (fact 5). The partner's or platform's own data stays in the candidate row and in self-declared claims in the staff tenant.

How it is held, and what is left. This is a staff rule. It is backed by one SQL refusal in the supply module: a MATCH to an organisation whose current ADR-079 rights type is `licensed_dataset` or `other` is refused (section 3.3). No refusal is added to the ADR-079 wrapper or to the 8-argument ingest; both keep their "never refuses" behaviour and their hashes. Residual risk, said plainly: a staff member can still ingest a partner-tipped company and choose a public type that does not fit, use the ADR-079 rights adjust path (ADR-079 line 139) to change a `licensed_dataset` or `other` type to a public type before matching, or call the 8-argument function directly (the organisation then reads `unrecorded`, which the match does not refuse, because every organisation made before S1 is `unrecorded`). Each leaves the rights record and its versions, the actor and the source locator on record for review, and the S3 test suite proves the refusal for `licensed_dataset` and `other` and the pass for `unrecorded`.

Consequences: ADR-079's search rule, eligibility helper and rights rule are untouched. A candidate that staff cannot confirm from a public source cannot be targeted; it stays visible to staff as "not confirmed" and counts in quality as such. A direct path for licensed rows into the shared table is owner decision 18, default no, and no slice depends on it.

### Scope of the earlier records

This record does not amend ADR-017 or ADR-079; it stays inside what they say.

- ADR-017 line 7, "No supplied URL is fetched", is about the source locator given at ingestion. That stays true: no supply path fetches a `source_record` locator. ADR-017 line 19 lists what Part 05 did not introduce ("No AI enrichment, crawler, automatic email, buyer outreach, production contact import ..."); it states that part's scope. The connector here is not a crawler (one fixed host, path and query per source, JSON only, no HTML), imports no contact, and ships locked.
- ADR-079 line 117, "Phase 1 adds no registry import, scrape, API call or provider", is ADR-079's own Phase 1 scope. ADR-079 line 422 leaves "Automatic registry import or provider lookup" to Phase 2 because it "Needs vetted sources and licence review. Provider activation is a closed gate." This record keeps those conditions: the `connectors` and `platform_kind` controls ship closed, a source needs a current `data_rights_policy`, and hosts are set by the owner only.
- A connector never fetches a `source_record` locator and never writes `app.organisation`; it writes candidate rows only.

### 6.1 Connector contract (declarative)

A connector is data, validated by one strict schema in `packages/domain/src/supply-sources.ts`, stored in `supply_source_version.connector`:

| Setting       | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `host`        | exact lowercase hostname, `https` on port 443 only; the pair of `host` and `auth.secretName` (or `NONE` for no auth) must appear exactly in the owner's deployment setting `CORRIDRA_SUPPLY_CONNECTOR_HOSTS`, a comma-separated list of `host=SECRET_NAME` pairs (for example `api.example.test=CORRIDRA_SUPPLY_SECRET_TEST`), no wildcards; any other pairing is refused, so a staff member cannot send one provider's secret to another host               |
| `path`        | fixed path starting with `/`, no `..`, no query                                                                                                                                                                                                                                                                                                                                                                                                              |
| `query`       | map of parameter name to a fixed value or a placeholder: `{productCategory}`, `{counterpartyTypes}` and `{sizeBand}` come from the current staff-approved brief card version (keys only, never free text), and `{country}` comes from the mission's route assignment; values are URL-encoded; no other input reaches the URL, and no profile line, note or seller detail is ever sent                                                                        |
| `auth`        | `none`, `header` (header name plus `secretName`) or `bearer` (`secretName`); `secretName` must match `^CORRIDRA_SUPPLY_SECRET_[A-Z0-9_]{1,40}$` and is read from the environment at call time; the value is never stored, logged or returned. A header name must match `^[A-Za-z][A-Za-z0-9-]{0,39}$` and must not be `Host`, `Cookie`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `TE`, `Trailer`, `Upgrade` or any `Proxy-` header |
| `pagination`  | `none`, `page` (parameter, start, size at most 100), `offset`, or `cursor` (response JSON pointer, parameter)                                                                                                                                                                                                                                                                                                                                                |
| `rateLimit`   | minimum interval between requests, 1000 ms or more; a `429` with `Retry-After` up to 60 seconds waits once, otherwise the run stops with `rate_limited`                                                                                                                                                                                                                                                                                                      |
| `items`       | JSON pointer to the array of rows                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `fields`      | map from candidate field to a JSON pointer; only company-level candidate fields can be targets; mapping a personal field is a schema error                                                                                                                                                                                                                                                                                                                   |
| `externalKey` | JSON pointer to the provider's row id, used for idempotency                                                                                                                                                                                                                                                                                                                                                                                                  |

Network safety, in one helper `packages/counterparties/src/safe-fetch.ts` built on `node:https` and `node:net` (no new dependency):

- Refuse a host and secret pair not on the allowlist before any lookup.
- Resolve the host; refuse if any address is loopback, private (RFC 1918), link-local (including 169.254.169.254), carrier-grade NAT, multicast, unspecified, reserved, IPv6 unique-local or link-local, or IPv4-mapped forms of these. Connect to the checked address through a custom `lookup`, so a second resolution cannot swap it (DNS rebinding).
- Refuse every redirect (`redirect` treated as an error), as the JWKS read does.
- 10 seconds per request in total; 2 MiB per response, counted while streaming and aborted when exceeded (stricter than the JWKS read, which checks after reading).
- Accept only `application/json` (or `text/csv` for a file-style endpoint). `text/html` is refused: there is no HTML parser and no scraping path.
- Every row is validated against the candidate schema; a bad row is rejected with its reason code and is not stored.
- Errors stored and logged are the reason codes above, with the run id; never the URL query, the response body or the secret.

Which sources need no code: any HTTPS JSON API with header or bearer key auth, page, offset or cursor pagination and a JSON array of rows; any CSV or XLSX file through file import. Which need a small reviewed adapter, one file each in `packages/counterparties/src/supply-adapters/`: OAuth 2 token exchange, signed requests (HMAC or cloud signatures), XML or SOAP, GraphQL, push or webhook delivery, SFTP, and non-standard pagination or rate headers. S6 builds no adapter.

Connectors send brief card keys and the route country off-platform. That is an external transfer: it needs the `connectors` control, the source's `data_rights_policy` with transfer status reviewed, and the owner's agreement. Each connector request names the card version it was built from. S6 proves the runner with sample data and one allowlisted test host only.

## 7. Partner flow

A partner organisation is recorded as an organisation (ingested from a public source like any company) plus a `partner_organisation` supply source, and acts only through its named members, each an invited contributor person under ADR-057 (fact 13: a profile is a person). There is no partner-organisation login.

1. Staff write a brief card version: `app.supply_brief_card` (`profile_version_id`, `version`, `card` jsonb, `approved_by`, `approved_at`, `superseded_by`). The card is a projection of one profile version holding only the allowed fields (route as origin and target country, optional region; product category in generic words; counterparty types; size band; channels; required certifications; order-size band; price positioning; must-haves and nice-to-haves lines that staff approved word by word; candidates wanted; deadline; event month and country). Never: seller name, brand, logo, website, address, registration numbers, exact capacity or prices, customers, exclusions, documents, photos, contacts, quote, fee, other partners, unreviewed text. A SQL check rejects any key outside the allowed list. Cards are reissued, never edited.
2. Staff create the network task (`supplier_research` or `introductions`) on the mission's route assignment through one supply wrapper that calls the existing network task command and writes `app.supply_task` (task id, card id, card version) in the same transaction. The task configuration keeps exactly its 21 required keys (`network-real-use-migrations/0001_real_invited_execution.sql:59-60`); the card reference lives only in `app.supply_task`. Values: `market` and `workCountry` are the target country of the route; `language` and `capabilities` are chosen by staff from the assignee's network profile; `sector` is the card's product category key; every free-text field (instructions, location, evidence, effort, data handling, cancellation and dispute terms, and the reason) is one of the module's fixed sentences, such as "Read the brief card for this task." The wrapper checks these values in SQL. The existing contributor read `app.network_my_tasks` returns the configuration and every event reason and detail verbatim (`:113-120`), so nothing from the profile or the seller is copied into the task, and the `supply_task_event_guard` (section 3.6a, S5) keeps later staff-written event text to fixed sentences too, for the life of the task: a reveal changes only what `app.supply_my_card` returns, so there is no point at which free staff text becomes safe. The contributor reads the card through one new SECURITY DEFINER function `app.supply_my_card(task)`, under the same assigned-task access, which returns the card and returns the seller's company name only when a `supply_partner_reveal` row exists for that task.
3. The contributor submits candidates through one narrow function: up to 25 structured rows per submission (the candidate fields), bound to the task and card version. A stale card is refused with "This brief was updated. Open the new version." Each row becomes a `supply_candidate` with method `partner_submission`.
4. Staff qualify each candidate (`supply_candidate_review`), match it to a public-sourced organisation (section 4) and target it. The partner sees their own submissions and each one's review outcome (qualified, not used), never other partners' candidates, attribution, quality or the seller.
5. Seller identity reaches a partner only after the seller approves that partner for that task (`app.supply_partner_reveal`, section 3.5). The seller sees the partner only as "the Corridra research partner working on this brief", never by name.
6. Reward: one reward per completed, independently reviewed task, at the task's reward rule amount, through the existing `contribution` (task key `network:<task id>`), reward rule and one CONTRIBUTOR_REWARD credit. The REVIEW event keeps its exact seven detail keys (`network-real-use-migrations/0001_real_invited_execution.sql:83`); the number of qualified candidates is not written on it but derived for staff from `supply_candidate_review` joined by `network_task_id`, for information only. This is what the network module allows today: a contribution is unique per mission, task and contributor (`migrations/0022_policy_and_service_economics.sql:14`), one credit per contribution (`:23`), and the reward guard requires the task's own rule and a completed, reviewed task (`migrations/0027_restricted_execution_network.sql:184-187`; `network-real-use-migrations/0001_real_invited_execution.sql:124-130`). A reward per qualified candidate would need its own reviewed forward change to the network module (owner decision 12). Payouts stay closed.

## 8. Seller decision, Mode A, Mode B and the fee

Shortlist. Staff publish the shortlist through the existing report path, whose SQL publication functions are not edited. On a supply mission only qualified, matched candidates can become targets (the `supply_target_guard`, section 3.6a), so only they can reach the shortlist; other missions' reports are unchanged. The seller approves or declines each buyer (`supply_seller_decision`). On a supply mission only an approved buyer may receive an introduction (Mode A) or a release (Mode B): the release function checks it, and `supply_contact_guard` checks it at introduction, send and retry.

Mode A, the default. The existing ADR-018 path: policy and template versions, queue and dispatch checks, opt-out, buyer link, meeting truth. On a mission that is not a supply mission it is identical with the module on or off. On a supply mission the only addition is the seller-approval refusal above. The buyer's contact stays with Corridra. Paid by the quoted service fees. No intro fee (owner decision 5).

Mode B, locked. Available only when the engagement's accepted quote holds an intro-fee term. Sequence, each step a record: the seller chose Mode B; the buyer accepted the introduction (their own `buyer_response` INTERESTED, or in real mode a staff observation with the buyer's message as evidence, owner decision 4); the buyer consented to share contact details (an observation, same evidence rule); staff release the contact (`supply_contact_release`, which names all three). The seller then arranges the meeting. A Mode B meeting is recorded only as an observation of kind `MEETING_REPORTED_BY_SELLER` or `MEETING_OBSERVED_BY_CORRIDRA`. A release is never a meeting, and a meeting is never a deal.

Fee lifecycle. Nothing is called earned before state 4.

| State                 | Record                                                                                                                                                               | Words shown to the seller                                                                                                                                                                    |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Disclosed           | intro-fee line on a quote version the seller has viewed (`service_quote_view`), inside the digest                                                                    | "Introduction fee: [amount] per buyer introduction you arrange yourself, at most [n]. Charged only if the buyer accepts, agrees to share contact details and Corridra releases them to you." |
| 2 Agreed              | `service_order_intent` for that quote version (order intent only)                                                                                                    | "Agreed in your accepted quote. Nothing is due yet."                                                                                                                                         |
| 3 Triggered           | `supply_fee_trigger` after all four observed steps                                                                                                                   | "Introduction released. The fee applies to this introduction."                                                                                                                               |
| 4 Recorded as earned  | staff SERVICE_FEE ledger row for the engagement's mission, citing the release's source record, linked by `supply_fee_ledger_link`, exact minor units, quote currency | (staff only)                                                                                                                                                                                 |
| 5 Invoiced, collected | existing invoice records; collection stays closed                                                                                                                    | existing invoice words                                                                                                                                                                       |

A decline, opt-out, missing consent or missing release means no trigger. The amount before state 4 is labelled estimate. The quote shows the line every time; it is never folded into another line. Fee shape is a flat amount per triggered introduction (owner decision 6), not an ADR-073 commission, so no base or rate is invented. Reversal is a compensating ledger row with a reason, within the window in owner decision 7.

## 9. Attribution

`app.supply_attribution` is a view `WITH (security_invoker=true)`, the convention of `app.service_margin` and `app.network_performance` (`migrations/0022_policy_and_service_economics.sql:78`; `migrations/0027_restricted_execution_network.sql:249`), not a table: for each tenant, mission and organisation (after the ADR-017 tenant attribution view maps merged pairs), the credited candidate is the earliest MATCHed candidate by `created_at`, then id; every other matched candidate is "corroborating" (owner decision 10). A REVERSE of a match or of an ADR-017 merge changes the view and rewrites nothing. Staff see per buyer: credited source, kind, method, source record, observed date, candidate time, corroborating sources. Readable by `research.read`; never by a customer or a contributor.

## 10. Display rule

Seller (report and Sell board): "Buyers in this list were found by Corridra. Company details are as reported by their source and have not been verified by Corridra unless marked Verified." Each buyer shows its trust state and observed date. The supplier is never named. The quote and the brief state, without amounts: "Corridra may work with research partners and data providers, who are rewarded by Corridra, not by you or the buyer." (owner decision 8). The buyer introduction states that the seller pays Corridra for the introduction (owner decision 9); the words are added to the approved template as a new template version, through the existing approval. Full provenance stays internal. No customer projection includes a supply source, partner, platform, attribution or quality field; a projection test scans every customer JSON for those keys.

## 11. Quality measures

One read function `app.supply_quality(tenant, route_id, from, to)`, staff only (`research.read`), real tenants read real records only (same-context rule), never computed for synthetic data in a real session. For a source S on a route R, let T(S) be the targets whose credited candidate (section 9) came from S, on missions assigned to a pack of route R.

| Measure                | Numerator                                                                                                                                               | Denominator                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Reachable rate         | targets in T(S) with a `communication_receipt`, a `buyer_response` or a `supply_buyer_observation`                                                      | targets in T(S) with at least one `app.communication`                        |
| Reply rate             | introductions to T(S) with a `buyer_response` or an observation of any kind                                                                             | introductions (`app.communication` rows) to T(S)                             |
| Meetings held (Mode A) | `meeting_outcome` HELD for meetings of introductions to T(S)                                                                                            | introductions to T(S) accepted (INTERESTED response or ACCEPTED observation) |
| Mode B meetings        | observations `MEETING_REPORTED_BY_SELLER` and `MEETING_OBSERVED_BY_CORRIDRA`, each counted on its own line, never added to the Mode A line              | releases to T(S)                                                             |
| Wrong-fit rate         | candidates from S whose latest review is WRONG_FIT, whose target's latest assessment is UNSUITABLE, or whose seller decision is DECLINED with NOT_A_FIT | candidates from S with any review, assessment or seller decision             |

Every rate is shown as numerator over denominator. Below the minimum sample (owner decision 14, default 10) only the counts show. Measures are never shown to customers or partners and are not a product (V3-08-013 stays NOT VERIFIED). Indexes on `(tenant_id, source_version_id)`, `(tenant_id, mission_id)` and the existing target and communication keys keep each call bounded per route and date range.

## 20. Quality bar

- Clean: one schema per shape in `packages/domain`, one service owner (`packages/counterparties`), the import parser reused, no copies of event, command or control code.
- Secure: identity and role checked in SQL and services; RLS with the real-use pair; connector allowlist, address checks, no redirects, limits, secrets by name only; no personal fields.
- Easy to use: staff research works with no agreement or setup; every refusal has a plain sentence; safeguards sit on money, release and personal data only.
- Durable: commands idempotent; append-only rows; runs checkpointed and resumable; every external call bounded and recoverable.
- Maintainable: tests per acceptance check, each failing on the base; installer and owner steps written in the runbook in the slice that needs them.
- Easy to change and scale: routes and kinds by pack configuration; any country pair; role-agnostic profile; bounded batches in the background.
- Observable: run state, last success, last error and backlog visible to staff; the recovery log line names the run id only.
- Fast enough: indexed per tenant, mission and source version; pages of at most 100 rows; quality reads bounded by route and date.
