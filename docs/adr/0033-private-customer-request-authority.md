# ADR-033: Private customer requests through the canonical mission engine

Status: backend/migration/API implemented, tested and source deployed with exposure closed (PR68). Customer interface acceptance is separately tracked; full mission administration remains missing. This decision grants no admission or activation. It amends ADR-032 only for the next separately tested synthetic request capability.

V3-06-004 requires persistent customer-owned access. The existing public request factory already creates canonical missions; the existing receipt function already limits progress to status, received time and operator replies within the original retention period. Reuse both. Do not create another mission backend, infer ownership from email or company text, or expose staff/source/commercial records through a customer workspace.

## Authority and privacy

A fresh independently verified provider session, pinned issuer and active admitted customer principal remain necessary. Add a separate offline synthetic request admission and a separate default-off server flag. Workspace admission, signup and invitation acceptance alone do not grant this capability. Production remains hard-disabled and D01-D06/D08 remain closed.

New submission requires active membership in the selected synthetic workspace, checked under the same workspace-access advisory lock used by invitation/revocation commands. The creator alone owns the request resource. Neither the workspace owner nor another member, organiser or participant receives that private resource. Keep the workspace reference as immutable provenance, without making workspace membership an implicit sharing rule.

Leaving the workspace prevents new submissions there. It does not transfer or delete the creator's existing requests. Existing private reads require fresh active customer proof, continuing request admission, an unrevoked resource grant and the original receipt retention. Independent resource revocation and principal disablement deny reads; no account recovery, re-invitation or repeated command may revive a revoked resource. This distinction must be visible in acceptance tests and later customer copy.

The current capability-based client-publication interface remains independently authorized. A private request binding is not a CLIENT_PROGRESS publication and cannot disclose quotations, contact details, negotiations, contracts or financial observations. Those require separately reviewed grants. Customer proof continues to yield no staff actor; staff MFA, app.actor_id, app.member_role and existing RLS remain unchanged.

## Trusted submission and atomicity

Extend the existing server-verified proof boundary rather than trusting browser identity fields. An auth-side short-lived submission attestation binds the fresh proof hash and issuer/subject, selected workspace, command UUID, normalized existing brief digest, namespaced factory UUID, payload hash, original receipt digest and notice version. Restricted runtime SQL may consume a valid attestation, but cannot create or alter one. Auth SQL cannot grant request admission or write a resource binding. Cap the attestation lifetime at the original proof/provider expiry using the database clock.

Derive the namespaced factory UUID from trusted context; do not accept a browser's canonical request key or mission ID. The original receipt digest must remain private and immutable. Existing receipt reads use the stored original digest, so signing-key rotation does not invalidate already bound requests. Do not recompute a historical digest using a new signing secret. Retry an existing command by its stored binding and validated brief digest before deriving any new key material; preserve this behavior across rotation.

The narrow new database command obtains the admitted principal/request-admission row locks, command lock and workspace-access lock, then rechecks proof, admission, membership and attestation after waiting. Call unchanged app.submit_mission and insert the creator resource binding in the same transaction. A factory failure or binding/audit failure rolls back both. Preserve the existing global intake deduplication lock and establish a documented lock order before implementation to avoid a new cross-command deadlock.

Same principal/command and same input return the existing authorized binding without extra records. Conflicting input is rejected. A duplicate result with no ID creates no binding and must not be resolved by searching payloads, emails or organisations. A returned ID must match the attested namespace/request key and original receipt digest before binding. Existing anonymous missions and another creator's resources cannot be claimed. Lost responses use the exact command; no receipt secret is placed in a URL or browser storage.

## Events, retention and blast radius

The configured intake service remains the genuine executor of the original mission command. New resource events separately record the verified customer initiator, workspace provenance and command. Do not manufacture staff sessions or reinterpret existing mission events. A request remains a request; canonical status is displayed without inventing acceptance, a meeting or a deal.

Implementation will add one reviewed optional customer migration and new private module tables/functions/grants only. Preserve all 29 core migrations, customer modules 0001/0002, their registries and original rows/functions/policies/ACLs. Existing core records are created only through the unchanged canonical factory after explicit non-production synthetic admission. No money, provider setting, production schema or historical event/source record is changed by this design.

Do not copy the request brief, contact details or operator replies into a new perpetual customer store. Read bounded progress through unchanged app.mission_receipt with the original private digest. Retention expiry and existing source/legal restrictions remain binding. Resource reference metadata and audit retention need explicit treatment in the implementation report; a new binding cannot extend access to expired source content.

## Required acceptance and rollback

Before exposing UI, test fresh and populated additive upgrades, every old row/function/policy/ACL/receipt, restricted runtime/auth grants, actual canonical factory/event reuse, owner/member/organiser isolation, missing admission, forged issuer/subject/workspace, revoked membership versus retained private resource reads, expired proof/attestation after locks, disable/revoke serialization, same/conflicting/concurrent retries, no-ID duplicates, rollback of case and binding, signing-key rotation, receipt expiry and zero staff/source authority. Keep all original assertions. Run full static/security/unit/database/public/protected/build checks on the exact head.

Deploy additive schema before the compatible backend, with flags off. Disabling exposure or redeploying the retained application rolls back availability; preserve canonical cases, resource/audit history and migrations. Do not drop tables or rewrite records. The isolated child still requires separately evidenced intake-destination readiness and private authenticated provider/browser acceptance. This design does not authorize either configuration or real-data activation.

## Forward implementation detail (18 October 2026)

Lock order is principal row SHARE → request-admission row SHARE → principal/command advisory → existing customer.access.workspace advisory → existing corridra:intake advisory. The unchanged factory reacquires its own transaction advisory lock reentrantly. Proof and attestation are rechecked after waiting. New binding events use their own aggregate per request; workspace provenance does not publish private content. The original source/receipt retention controls progress, while immutable binding metadata stores only identifiers, digests and time. Offline admission remains schema-owner-only and repeated admission cannot re-enable a disabled row.

## Amendment, 11 November 2026: a removed member sees no workspace request (fail closed)

Owner decision, 11 November 2026. The owner was asked whether a person who has left a workspace, or was removed from it, keeps reading the requests and reports they made there, and answered: "No, remove access (Recommended)". The answer is verbatim; the question is paraphrased from the build brief, and the ledger entry is written by the conductor (S28). Meaning, as recorded: requests and reports made in a workspace belong to that workspace. Once a person is no longer a current member they see none of them, even the ones they wrote. Items made outside any workspace stay theirs.

Scope line. This amendment applies to every path that reads, lists, starts, accepts, confirms, sends or shares something because the signed-in person is the author of a request made in a workspace, or the holder of a saved report that was delivered for such a request. It does not change who can submit (that already needs current membership), staff paths, the problem report functions of ADR-078, or any path that already starts from a workspace the person must currently belong to.

What it replaces. Two statements above are replaced for the paths listed below: "Leaving the workspace prevents new submissions there. It does not transfer or delete the creator's existing requests. Existing private reads require ..." and, under required acceptance, "revoked membership versus retained private resource reads", which now reads "revoked membership versus no private resource reads". Nothing is transferred and nothing is deleted. An independent resource revocation and a disabled person still deny reads as before.

The rule. A current member of a workspace is a person with a `customer.membership` row there (the original owner, a transferred owner, an owner who stepped down to admin) or a `customer_private.workspace_member` row with no `workspace_access_revocation` row for that member. This is the rule `customer.collaborative_workspaces` already applies. Leaving and an owner's revoke write the same revocation row (ADR-051), so one rule covers both. A personal workspace belongs to its author through a membership row and cannot be left, so requests made there stay the author's. `owned_request.workspace_id` is not null, so every request is in some workspace; "outside any workspace" means the personal workspace, and for saved reports a report that was saved by bearer link and was never delivered for a request this person wrote.

Paths covered (each adds the same condition, and each refuses with the same SQLSTATE and message as an unknown id on that path, except for the exceptions listed after the paths):

- Requests: `customer.private_requests`, `customer.request_retry` (the replay inside `submit_private_request`), `customer.private_request_detail`, `customer.private_request_moves`, `customer.complete_pending_request`, `customer.record_request_received`, `customer.my_request_withdrawals`, `customer.withdraw_request`, `customer.restore_request`.
- Mail and notices: `customer.my_mission_mail_mutes`, `customer.set_mission_mail_mute`, `customer.my_notification_mutes`, `customer.set_notification_mute`. A message already queued for a removed author is suppressed when it is claimed, and nothing new is queued for one, by extending the two block-reason helpers that the enqueue, claim and validity functions already ask. Timing: production was verified on 11 November 2026 from install run 42950597177 (request withdrawal 2 applied, mission mail 3, notifications 5, move 1, decision cards 1, commercial readiness 10, customer 3, real-use 13; response revision not installed), so the prerequisites of mail 0004 and notifications 0006 are present and one `apply=yes` run with `real_use_action=install` advances them. Only a database whose prerequisite is absent (mail or notifications installed without request withdrawal) cannot advance them; there the installer's refresh reports them as behind and the run ends red after everything else is applied.
- Assigned reports: `customer.assigned_missions`, `customer_private.assignment_summary` (which `customer.accept_assigned_mission` calls).
- Saved reports (ADR-036, ADR-040, ADR-076): `customer.saved_missions`, `customer_private.saved_mission_summary`, `customer.saved_mission_action` (which the decisions, book and specification functions call first), `customer.save_mission_invitation`, `customer.remove_saved_mission`, `customer.company_portfolio`. A saved report is the person's own unless its link was delivered for a request this person wrote; in that case the report follows that request's workspace.
- Decision card state: `customer.decision_card_state` is covered by a new customer-decision-card-migrations 0002, which is in the base installers list and so advances on every `apply=yes` run. It does not call `customer_private.link_workspace_current`, because that helper lives in real-use 0014 and the decision-card module runs in the base run, where it would not exist on a base-only apply; the same rule is written inline (the assignment joined to the request this person wrote, then `workspace_member_current` from customer 0004), with identical meaning because a link has one assignment. Creating, previewing and resolving a card are already covered through `decision_card_workspace` (which needs a current writer role) and `saved_mission_action`.
- Customer inbox: commercial-readiness file 0012 alters the RLS read policy `inbox_customer_read` on `app.inbox_notification` (command, roles `corridra_runtime` and permissive kind unchanged; only the USING expression is replaced) and adds one definer function, `app.inbox_notice_visible(recipient, type, key, payload)`. It sits in the `app` schema because `corridra_runtime` has no USAGE on `customer_private`; EXECUTE is for `corridra_runtime` only (revoked from PUBLIC and `corridra_auth`). It answers true for any recipient other than the signed-in customer and looks only at requests that recipient wrote, so it is no oracle. Notice types covered: `REQUEST_RECEIVED` (key `request:<id>`), `REPLY_POSTED` (href `/account/requests/<id>`), `REPORT_PUBLISHED` (key `assignment:<id>`, resolved to its request) and `QUOTE_SENT` (href `/account/service-requests/<workspace>/<id>`, followed by workspace membership). A customer recipient does not see a covered notice whose request author is no longer a current member of the request's workspace; a re-admitted member sees it again. Other types, notices outside any workspace and staff notices are unaffected. The update policy `inbox_customer_mark` and the staff-side writers are unchanged, and a hidden notice cannot be marked read. The guard fingerprints the policy by command, permissive kind, role names and normalised qual and with-check parts (literals, casts, schema names, parentheses, quotes and spaces removed), which are stable between PostgreSQL 16 and 18.
- Participant side lookups of the person's own requests: `customer.programme_mission_choices`, `customer.programme_mission_summaries` (not the organiser view) and `customer_private.programme_mission_scope` when sharing.

Exceptions to "the same SQLSTATE and message as an unknown id" (each concerns only the caller's own ids and reveals no other person's data): (a) `customer.enqueue_mission_mail` returns `{queued:false, reason:'removed'}` to the removed author, and the staff-side `customer.enqueue_move_notifications` returns the reason `removed`, because the denial is carried by the block-reason helpers (the six functions that call them cannot be rewritten, see Design); (b) a replay of an earlier `save_mission_invitation` command answers `Saved mission unavailable`, where a fresh unknown link answers `Link unavailable or expired`; (c) in `request_retry` the existing `Command conflicts with original request` check still comes before the membership check, so a reused command id for another workspace or brief conflicts as before.

Stop-only actions stay allowed for a removed member: withdrawing an objective they shared into a programme, and the no-sign-in mute links in old emails (`mute_mission_mail`, `mute_notifications`). Reads, starts, accepts, confirms, new sends and new shares are denied. In the participant summary a link to a request the person can no longer read appears as unavailable (id and version only, no request id, no summary), the form it already takes for an expired or revoked source, so the withdraw action stays reachable.

Deliberately unchanged, as scope lines and not as gaps: the person's own programme registrations and participation; the organiser views (`programme_mission_summaries` with manage, `programme_projection_owner`); capability-token paths (`claim_notification`, `notification_recipient`); every path that takes a workspace as its target (drafts, programmes, service requests, billing, invoicing, pricing, exports, organisation profile and links), which already needs current membership; staff paths; `customer_private.service_request_context`, because a service request is created under a workspace the person must currently write to.

Re-admission. A new invitation creates a new member row (one row per invitation), so access to the person's earlier requests returns by itself. A revoked or removed row is never reactivated, and removal deletes no data. Items that were withdrawn or revoked as requests stay dead, as before. A message that was suppressed at claim while the person was removed is not revived.

Consequences. (1) Stranded work: the request, its progress and the team's replies stay in the canonical mission and staff can still work them, but nobody on the customer side reads a removed author's request, including the workspace owner, because ADR-033 gives the creator alone that resource. (2) A workspace that should see its members' requests is a different feature and a separate owner decision; this amendment does not build it. (3) Erasure path, DECIDED by the owner on 11 November 2026: "Yes, add an erasure path (Recommended)". The option text, as relayed by the orchestrating session on 11 November 2026, was "a removed member can ask staff to erase their personal data in their former workspace's requests. Staff handle it through the existing erasure queue, and the person still can't see the requests. A follow-up PR after the access fix." It is built in a follow-up PR after the access fix; this PR does not build the erasure path. Until that follow-up PR lands the stated state is: A removed member cannot withdraw their former workspace request or start an erasure request reaching it. This widens ADR-078 gap 2. The decision covers the erasure path only; withdrawing a former workspace request is not decided by it. The quoted option text reaches this repository only as relayed by the orchestrating session on 11 November 2026; the verbatim owner answer is the first quotation. (4) The saved-report cap: `save_mission_invitation` counts the rows now hidden from a removed member, so a person with 100 or more rows can meet `Saved mission limit reached`; recorded, not changed. (5) The ADR-078 report, list and self-removal functions are not touched; a removed member can still file, list and remove the words of their own problem reports. (6) Installations that have only the base customer modules and not the real-use schema keep the old list bodies of functions the real-use schema replaces, because it checks the text of the earlier bodies; real requests cannot exist there. Only the replay inside `request_retry`, `record_request_received`, the inbox policy and the base helpers apply there.

Design. Three read-only helpers in customer migration 0004: `customer_private.workspace_member_current(workspace, person)`, `customer_private.workspace_ids_current(person)` (one set per call, for list filters) and `customer_private.request_author_current(request)`. Lists filter in the WHERE clause and in the next-page probe and never raise; they evaluate the person's workspace set once, as `workspace_id = ANY (ARRAY(SELECT ... workspace_ids_current(actor)))`. A new submission already checks membership under the `customer.access.workspace:<id>` advisory lock that a leave takes, so a leave and a submit serialise there and nothing changes in that path. The other write paths (withdraw, restore, mute, save, remove) take no new lock. The saved-report paths check membership inside the `SELECT ... FOR SHARE` that reads the row; withdraw, restore and the two mute functions check it in a separate statement after the row is read. Either way the write orders before or after a concurrent leave as a whole, and anything stored just before the leave is hidden again by the read rules above. `customer_private.request_result`, `customer.submit_private_request`, `customer.enqueue_mission_mail`, `customer.claim_mission_mail`, `customer_private.notification_valid` and `customer.enqueue_move_notifications` are not rewritten: later optional modules (request withdrawal, workspace lifecycle, mission mail 0003, notifications 0005) check their exact text before patching them, so a rewrite would stop a fresh install. Their guards stay valid and each path is covered through its callers or the block-reason helpers. New files only, nine SQL files: customer 0004, real-use 0014, commercial readiness 0011 and 0012, move 0002, request withdrawal 0003, mission mail 0004, notifications 0006 and decision card 0002. Decision card 0002 and commercial readiness 0011 and 0012 are in the base run and advance on every `apply=yes` run; the rest advance as described under Installer. Each fingerprints the live function parts it replaces (body hash, settings, volatility, argument types, execute grants; never `pg_get_functiondef`), has the three states absent, matching and changed, and refuses on a changed function without replacing any.

Installer. No new workflow input. `real_use_action=install` additionally re-runs the migrators of the optional modules that are not in the base list (request withdrawal, move records, mission mail, notifications) only when their registry already exists, and never writes a control row or switch. Real-use 0014 itself applies through any real-use-dependent action, but `real_use_action=install` is the one that refreshes the optional modules. The first refresh records a module's hard error as behind, with the module name and message, instead of aborting, and the next-step text is built only from the behind rows. On the verified production state one run of `apply=yes` with `real_use_action=install` moves customer 3 to 4, real-use 13 to 14, commercial readiness 10 to 12, decision cards 1 to 2, move 1 to 2, request withdrawal 2 to 3, mission mail 3 to 4 and notifications 5 to 6, and ends green. A mail or notifications module on another database that cannot advance because request withdrawal is not installed is reported as behind and that run ends with an error after everything else is applied; `mission_mail_action=install` and `notifications_action=install` remain the explicit way to bring them up.

Blast radius. Customers who have left or were removed from a workspace lose sight of the requests and reports they made there, and of the inbox notices that point at those requests, at the moment real-use 0014 and commercial readiness 0012 are installed. One RLS policy is altered (`inbox_customer_read` on `app.inbox_notification`, in commercial readiness 0012), guarded on normalised `pg_policy` parts that are stable between PostgreSQL 16 and 18; no other policy, table or grant changes. No row, event or money record changes; nothing is dropped; roles, MFA and staff identity are untouched. Rollback is a new forward file that restores the earlier function bodies and the earlier inbox policy, never an edit of an applied file; no such file is prepared in this PR. The installer report shows the real-use count going from 13 to 14, commercial readiness from 10 to 12, and one more applied file for each other module it advances.

Rejected options. Renaming `owned_request` and exposing a filtering view (breaks every reader and RLS binding at once). Rewriting `request_result` or `submit_private_request` (their text is fingerprinted by later modules). Transferring a removed author's requests to the workspace owner (it creates a second owner of a private resource, against this ADR). Deleting or anonymising the requests (loses the history staff still need). Row level security on `owned_request` (the readers are definer functions that bypass it).
