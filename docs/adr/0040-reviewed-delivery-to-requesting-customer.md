Request retention/revocation governs discovery and new acknowledgement. The UI distinguishes unavailable delivery from independently saved reports. This preserves separate authorities rather than merging them for navigation convenience.

## Amendment, 11 November 2026: the requesting customer must still belong to the request's workspace

Owner decision, 11 November 2026: "No, remove access (Recommended)" (answer verbatim; question paraphrased; ledger entry by S28). Requests and reports made in a workspace belong to that workspace; once a person is removed or leaves, they see none of them, including the ones they wrote. Items made outside any workspace stay theirs.

Scope line. This replaces "A fresh admitted request creator discovers only their own approved assignments" with "a fresh admitted request creator who is still a current member of the request's workspace", and extends "request retention/revocation governs discovery and new acknowledgement" with membership. While the creator is not a current member, `customer.assigned_missions` leaves the assignment out (list and next-page probe) and `customer_private.assignment_summary`, and so `customer.accept_assigned_mission`, refuse with `Assigned mission unavailable`, the text of an unknown assignment. The sentence that an accepted client report is an independent permission under the original link stands for the link and publication themselves, which are not touched; what the amendment closes is the removed creator's own account route to it (see the [ADR-036 amendment](0036-account-saved-commercial-reports.md#amendment-11-november-2026-a-saved-report-follows-the-workspace-of-the-request-it-was-delivered-for)). Another person who holds the bearer link keeps what they had. Staff approval and assignment are unchanged. A new invitation restores access. Full rule, consequences and rejected options are in the [ADR-033 amendment](0033-private-customer-request-authority.md#amendment-11-november-2026-a-removed-member-sees-no-workspace-request-fail-closed), including the decided erasure path. Erasure path, DECIDED by the owner on 11 November 2026: "Yes, add an erasure path (Recommended)", not built by the access fix (PR 410). It is built by erasure PR A and installed by the account lifecycle action; before that install the old state holds: A removed member cannot withdraw their former workspace request or start an erasure request reaching it. This widens ADR-078 gap 2. From that install a removed member who ever held a workspace can file the erasure request and staff can route and find it (a person who never held a workspace is still refused); withdrawing stays refused ("No, workspace decides (Recommended)"). See the [ADR-033 amendment](0033-private-customer-request-authority.md#amendment-11-november-2026-a-removed-member-sees-no-workspace-request-fail-closed) and ADR-078 decision 6.
