# ADR-091: AI assistance in real workspaces, behind a closed control

Status: Proposed 23 November 2026 for the owner decision of 23 November 2026 that opened "AI in real workspaces" (commercial-ready run, section 1, unit B10) with "AI provider: all, any provider I choose anytime". Built behind a control that starts closed. Nothing is installed, opened or verified in production by this record. The database tests ran on a local PostgreSQL 16; CI on the pushed head is the check for the rest. No requirement moves to VERIFIED on design alone. Update 26 November 2026 (records, decided by Guardian G65 on the owner's delegation): built and merged in PR 621 (`3122c5ca`, unit B10). The control `app.ai_real_control` starts closed; no install step (`ai_real_install`, smoke, `ai_real_enable`) is recorded as done, so AI in real workspaces is not active. This note changes no decision.

Amends ADR-089 forward for decision 1 (run tables stay sample only) and decision 5 (inference stays off in real workspaces until a further owner decision and ADR). This is that record. Everything else ADR-028 and ADR-089 decide stays in force. Those records are not edited.

## Context

- After ADR-089 a real workspace can hold a reviewed model policy and nothing else in AI. Three database points kept runs out of real workspaces:
  - `app.guard_ai()` (as replaced by `packages/db/ai-model-policy-real-migrations/0001_real_workspace_model_policy.sql`) refused a run, attempt, result, review or completion unless the workspace is a sample workspace.
  - `app.part4_enabled(uuid,text)` (as replaced by `packages/db/network-real-use-migrations/0001_real_invited_execution.sql`) returned false for the key `ai.enabled` in every real workspace.
  - `app.ai_output_grounded(uuid,uuid,jsonb)` (`packages/db/migrations/0026_governed_intelligence.sql`) checked access under the fixed sample purpose.
- The row policies for real workspaces on all six AI tables already exist (`real_use_add`, `real_use_read` in `packages/db/customer-real-use-migrations/0002_real_request_authority.sql`): a member reads only as owner, admin, operator or reviewer, under the workspace's own processing purpose, and writes only rows it creates itself.
- `app.ai_run_authorized` does not name a kind of workspace. It already requires, for any workspace: the acting member with a fresh authenticator check, `ai.enabled`, a current latest model policy named by the current route pack of the request, and for every cited statement a public source with an approved transfer, the reuse `AI_REVIEW`, no subject locations, no email address or phone number in the statement, and the policy's processing locations inside the source's rights review.
- `IntelligenceGateway` (`packages/intelligence/src/index.ts`) repeats the contact-detail and rights checks in the application before any provider call, sends only the cited statements, and accepts only output whose every fact quotes a cited statement. Every stored result carries the authority `UNVERIFIED_DRAFT` (a table check). A review by a person is a separate row; nothing in the product applies a result on its own or shows one to a customer.

## Decision

1. **One control, closed by default.** A new table `app.ai_real_control` holds one row per version (enabled, reason, time). No row, or a latest row that is not enabled, means closed. Only the offline installer writes it, as the schema owner, with a reason of 10 to 500 characters; the runtime role has no privilege on it. `app.ai_real_runs_open()` returns the one boolean and is the only thing the application and the guards read.
2. **Three functions are replaced, each after a hash check, and nothing else.**
   - `app.guard_ai()`: for the five run tables, a sample workspace is accepted exactly as before and a real workspace is accepted only when real use is allowed and the control is open, under the workspace's own processing purpose. The model policy branch and every other rule are byte-identical.
   - `app.part4_enabled`: in a real workspace the key `ai.enabled` can be true only while the control is open, and only when the latest `ai.enabled` setting of that workspace was written after the control was first opened. A setting written earlier never counts, so nothing goes live at the moment of opening. A pause and a later reopening keep a setting written after the first opening. `network.enabled` is unchanged.
   - `app.ai_output_grounded`: the access check reads the workspace's own processing purpose. Every grounding rule is byte-identical.
3. **A provider evaluated on sample data only never serves real work.** In a real workspace a run or an attempt needs a model policy whose `evaluationStatus` is `APPROVED_PROVIDER`. Sample workspaces keep both statuses. This is stricter than before and is enforced in the database, beside the same test in `SdkInferenceAdapter.ready`.
4. **Any of the three adapters.** Nothing in the database or the service names one provider. A real workspace uses whichever of `openai`, `anthropic` or `google` its current model policy names, each with its fixed deployment key name. No new provider, no key in code, no key value in any table.
5. **What must all be true before one real run.** The module is installed; the control is open; real use is allowed; the owner of that workspace has switched `ai.enabled` on after the control was first opened (owner role, fresh authenticator check, recorded as a setting version); the deployment has `CORRIDRA_AI_ENABLED`, the provider key and `CORRIDRA_<ADAPTER>_PROCESSING_LOCATIONS` covering every policy location; a current approved-provider model policy exists; the request's current route pack names that policy; and every cited statement passes the source rules in the context above. Opening the control alone starts nothing.
6. **Contact details stay out of provider calls.** `app.ai_run_authorized` and `IntelligenceGateway` are not changed, so a statement with an email address or a phone number, a source with subject locations, a private source or an unreviewed transfer still refuses the run before any attempt is reserved, in real workspaces as in sample ones. Real workspaces get one stricter rule on top, in `app.guard_ai()` and in `IntelligenceGateway` alike: a run is refused when a cited statement holds seven or more digits in a row, counting through spaces, dots, dashes and brackets, because that may be a phone number written without a plus sign or a keyword. Dates written YYYY-MM-DD are taken out first. A year such as 2026 has four digits and an amount grouped with commas such as 1,250,000 has at most three in a row, so both pass. An amount of seven or more digits written without commas, or grouped with spaces or dots, is refused; the member then works on that statement by hand. Sample workspaces keep the earlier rule only.
7. **A person reviews before anything is used.** A result is stored as `UNVERIFIED_DRAFT`. A review needs owner, admin, operator or reviewer with a fresh authenticator check and a run that is still authorized; an edit must stay grounded in the cited statements. No customer role reads any AI table, and no customer screen changes.
8. **Pause.** Pausing the control refuses new runs, attempts, successful results and reviews in real workspaces at once. Every record stays, append-only and readable by the same staff roles. Switching real use off has the same effect. For a run already in flight, the service reads the control again before each reservation and right before the provider call, so a pause in between stops the call. If the pause lands while a call is already on its way, its output is not stored: the two rows that end a run without output, a FAILED result and a MANUAL_REVIEW completion, are still accepted while the control is closed, so the run ends in a recorded state and never stays pending.
9. **Installation.** A second file in the existing family, `0002_real_workspace_runs.sql`, with `rollback/0002_restore_sample_only_runs.sql`. The existing choice `ai_model_policy_real` still installs the ADR-089 step only. Three new choices on the existing `field_modules_action` input (no new workflow input): `ai_real_install` (leaves the control closed), `ai_real_enable` and `ai_real_pause`. The installer refuses unless the real-use and the network real-use modules are installed. The rollback refuses unless the three functions are exactly the definitions this step installed and the control is closed; it keeps the control table and every AI record.

## Consequences

- New: `packages/db/ai-model-policy-real-migrations/0002_real_workspace_runs.sql`, its rollback, `packages/db/src/ai-real-runs-migrate.ts`, `packages/auth/src/ai-real-configuration.ts`, the installer and workflow lines, and the tests `tests/integration/ai-real-install.test.ts` and `tests/integration/ai-real-runs.test.ts`.
- `IntelligenceService.run` answers a real workspace plainly (`AI_REAL_OFF`, 403) while AI is off for it. The database refuses in any case.
- The time test in `app.part4_enabled` compares the creation time of the setting with the creation time of the first opening. Only the owner of a workspace, with a fresh authenticator check, can write that setting.
- While the control is closed nothing changes for anyone: a real workspace behaves exactly as after ADR-089, and a sample workspace behaves exactly as before in either state.
- The order for production is: merge, deploy, `ai_real_install`, smoke, then `ai_real_enable` on the owner's word, then the workspace owner switches AI on for that workspace. The database enforces the last step: a workspace switched on earlier stays off until its owner switches it on again.
- One note written for ADR-089 is no longer complete once the control is open, and its owner updates it: the comment and source note of the `run` entry in `apps/web/lib/consequence-preview.ts` (connecting a provider still makes no provider call and switches nothing on). The workflow description of `ai_model_policy_real` stays true for that choice.
- Real provider cost: every attempt reserves its worst case against the policy's daily budget and the optional request budget before the call, as in sample workspaces. Amounts are estimates in USD minor units; no payment is made by Corridra code.

## Rejected options

- **An application switch only.** A setting in the web application would leave the database open to any other caller of the runtime role. The control is in the database, where the guards read it.
- **Open on install.** The owner asked for nothing to run until merge, deploy and smoke are done, so install and open are separate steps.
- **Remove the sample-only check without a control.** That would make the per-workspace setting the only lock and would give the owner no single place to stop AI for all real workspaces.
- **Let real workspaces use a policy evaluated on sample data.** That would send real statements to a provider nobody approved for real work.
- **Replace `app.ai_run_authorized`.** It already applies to any workspace; changing it would put the source and contact-detail rules at risk for no gain.
