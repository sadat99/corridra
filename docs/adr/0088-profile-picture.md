# ADR-088: Profile picture

Status: Accepted, 17 November 2026, by Guardian 18 (`session_0187kU9tHYa9McabQ3qneMBG`) under the owner decision recorded in ADR-086. Built in unit CI-U1P. The database module is tested on PostgreSQL 16 and is NOT installed anywhere; the Guardian asks the owner, then runs the install (`field_modules_action = profile_picture`) after merge. The picture ships switched off: `apps/web/lib/profile-picture-capability.ts` holds `profilePicture: false` with an empty probe record until a preview probe proves upload, read, replace and remove against the private store.

Authority: owner words, 17 November 2026, first hand to Guardian 13, recorded in ADR-086: "ensure propfile allows user's profile picture sophisticated ways." ADR-086 decision 7 fixes the frame: a separate unit on the personal details module, on private object storage, in its own table keyed by principal; the personal details validator accepts no picture key; no AI anywhere; sharing stays private preview. Guardian 18 decisions of 17 November 2026: add `sharp` 0.35.5 (already in the lockfile through `next`) as a direct dependency of `apps/web`; the capability switch is its own file; visibility is the person only. ADR-020, ADR-033 (as amended), ADR-044, ADR-056 and ADR-086 apply unchanged.

## Decision

1. **Own module, references only.** `packages/db/customer-profile-picture-migrations/0001_profile_picture.sql` adds `customer_private.profile_picture_object` (one row per stored picture: storage backend, object id, SHA-256 and size of each file, state `reserved`, `current` or `retired`; at most one `current` per person), `profile_picture_head` (the person's picture version), `profile_picture_command` (one command id per decision, with a keyed one-way hash of the request) and `profile_picture_erasure` (one row per staff erasure run, no picture data, append-only). Row security on, every grant revoked from the runtime and auth logins. The picture is current state, not history: replaced and removed pictures are retired and their rows deleted once their files are gone. The installer (`migrateCustomerProfilePictures`, registry `customer_profile_picture_migrations`, hash-guarded) refuses unless every personal profile file is applied, naming `field_modules_action=personal_profile`.
2. **Self only.** `customer.profile_picture_view()`, `customer.profile_picture_reserve(command, expected, request, storage)`, `customer.profile_picture_commit(...)`, `customer.profile_picture_remove(command, expected, request)` and `customer.profile_picture_purged(objects)` take the person from the signed-in session (`customer.actor_id()`), never from an argument, and use the ADR-086 refusals (disabled, closed in the undo window or final, an erasure request not declined: 42501), the same workspace refusal (23514, nothing written) and the account, profile and picture advisory locks in that order. A stale version is "Picture changed; reload before saving" (23514); a replay answers the first result; the same command with another picture, by another person or of another kind is refused. Another person cannot commit, purge or overwrite someone else's object.
3. **Who sees it: the person only.** No staff read, no workspace read, nothing public. Today no customer screen shows another customer's account name (team rows show owner-set labels), so a read by people in the same workspace would be a control with no screen; it is a later unit, tied to the first screen that shows other people's names, with its own decision.
4. **Private storage, no public address.** `packages/evidence/src/avatar-storage.ts` writes to the same reviewed stores as evidence (the private EU Blob store or the EU S3 bucket, chosen by `EVIDENCE_STORAGE_PROVIDER` and configured by the existing settings; no new setting) under its own path `avatar/<object id>/<large|small>`, never overwriting, with delete. The evidence router and its quarantine paths are unchanged; the Blob configuration checks and the S3 region list are shared helpers. The only read is `GET /api/account/picture?size=large|small` for the signed-in person: the bytes are checked against the stored hash and length and served as `image/webp` with `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, a `default-src 'none'; sandbox` content policy and same-origin resource policy. No provider URL ever leaves the server. `GET ?scope=view` answers the version only.
5. **Checked and redrawn on the server.** The real bytes decide the type: JPEG, PNG or WebP only; SVG, GIF, TIFF, HEIC and anything else are refused; an animated PNG (`acTL`) or animated WebP (VP8X flag or `ANIM`/`ANMF`) is refused; the decoder must agree with the sniffed type. At most 8 MiB, each side 128 to 8000 pixels, at most 40 million pixels (decoder limit too), a 10 second decode limit. The picture is redrawn by `sharp` (Node runtime) to two square sRGB WebP files of 512 and 96 pixels, applying the camera orientation; no metadata is written, so EXIF (location included), XMP, ICC and comments are gone. The uploaded bytes are never stored. The browser frames a square first (move and zoom inside a circle), which only helps the person; the server check does not rely on it.
6. **Malware scanning is deferred.** The V3 ledger records real admission under ADR-056 "with scanning deferred", and no scanner is deployed for this path. The control in its place is the strict decode and redraw above: nothing the person sent is stored or served, only pixels the server drew. When a scanner is deployed and proven on production, it joins the Merge Gate for this path.
7. **Order of an upload, and limits.** Origin check, capability, declared type, size, command headers, the real-bytes sniff, then the hourly budget (`app.intake_budget`, 20 uploads per person per rolling hour, keyed by an HMAC of issuer and subject with the server secret), then the redraw, then reserve (at most three unfinished uploads per person in an hour: 54000, answered 429), the two private writes, then commit. A file write that fails, or a commit refused after both writes, deletes both files at once and answers 503 or the refusal; only if that delete also fails does the reservation stay, offered for deletion after an hour. Replace and remove answer the retired objects; the server deletes their files and then their rows. A file that cannot be deleted keeps its row and is offered again by the person's next change.
8. **Events carry ids only.** `customer.profile_picture.changed` with `action` (`set` or `removed`), the object id and the version, through the ADR-086 event writer (audit, outbox and delivery in the same transaction, the account chain workspace). Never image data, a hash, a storage reference, a name or an email.
9. **Retention, closure and erasure.** A picture is kept until the person replaces or removes it. A closed account cannot read or change it (all reads are refused), so closure hides it; the undo window keeps it. When staff move an erasure request to in progress or completed in the erasure queue (`/api/workspace/customer-erasure-queue`), the route calls `customer.profile_picture_erase(command, erasure_request)` (staff privacy authority, request in scope, in progress or completed), which retires the current picture and every reservation older than one hour (at most 100 objects per call) and removes the person's picture head and commands, then deletes the stored files and calls `customer.profile_picture_erase_purged`. Sending the same transition again retries any file that could not be deleted; the answer carries `profilePicture: { retired, pending }`. The command id is derived from the request and the target state. Moving a request to completed is refused (409, checked by `customer.profile_picture_erase_ready_at(erasure_request)`) while the person has a reservation younger than one hour, so the completed sweep always includes it; apart from that wait it never fails or undoes the transition.
10. **Switched off by code.** `profilePicture: false` hides the picture row on My Profile, keeps initials in the avatar menu and makes every method of the picture route answer 404 before anything is read. It changes only by a reviewed change with a probe record. With the module not installed the routes answer 503.

## Blast radius

- New: four tables and thirteen functions in one additive file; one installer reached only by `field_modules_action = profile_picture`, never by a base run (one new workflow choice, no new workflow input). `sharp` 0.35.5 becomes a direct dependency of `apps/web` (no new package in the lockfile).
- Application: `packages/auth/src/customer-profile-pictures.ts`; `packages/evidence/src/avatar-storage.ts` (and two exported helpers in `blob.ts` and `adapters.ts`, behaviour unchanged); `/api/account/picture` (GET, POST, DELETE); the erasure queue route calls the picture erasure after a transition; `apps/web/lib/profile-picture-image.ts`, `profile-picture-capability.ts`, `profile-picture-client.ts`; the picture row on My Profile and the picture in the avatar menu; private header rules in `apps/web/next.config.ts`.
- Existing objects: no table, policy, grant, trigger or function is changed or replaced. The personal details validator still accepts no picture key.

## Rollback

Revert the application code; the tables stay (additive, no down migration). Setting `profilePicture` back to `false` hides every control and makes the route answer 404; stored files stay private and unreachable. To remove stored pictures after a rollback, staff use the erasure path per person, or the files under `avatar/` are deleted from the store with the owner's approval.
