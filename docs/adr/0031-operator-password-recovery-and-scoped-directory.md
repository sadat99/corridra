# ADR 031: Operator password recovery and a scoped member directory

Status: implementation under verification. Live delivery and owner setup acceptance are separate.

The owner requested working signup, sign-in and password recovery for the applicable audiences, with understandable administration and preserved permissions. Customer accounts retain managed Neon Auth. Staff identities retain the existing independent Better Auth password and authenticator. Private buyer, client, programme and contributor access retains its existing scope and invitation contracts. No account migration, automatic identity linking or public staff signup is introduced.

Operator password recovery uses the pinned Better Auth one-use token store, a 30-minute expiry and an exact same-origin callback. Only verified staff identities with an enabled principal receive mail. Unknown, suspended and pending identities receive the same generic successful request response without delivery. Pending staff invitations use ADR 030 first-password setup instead. Password reset changes no membership, principal state or authenticator. Existing sessions are revoked; subsequent sign-in still requires MFA. Lost authenticator and suspension recovery remain reviewed offline procedures. This supersedes only the offline password-recovery restriction in ADR 030.

Credential forms use native POST so a pre-hydration submission cannot put passwords in a URL. Operator sign-in and initial setup refuse duplicate in-flight submissions. Operator sign-in preserves entered details on transport failure and focuses its error. These changes do not create an alternate sign-in or bypass the existing authenticator.

The transport sends identity mail through the existing Resend service, independently of mission communications. Deployment-only `CORRIDRA_OPERATOR_RECOVERY_ENABLED`, `OPERATOR_RECOVERY_EMAIL_KEY` and `OPERATOR_RECOVERY_EMAIL_FROM` enable it. Missing configuration hides credential collection and disables recovery endpoints. The transport fixes its provider destination, validates recipient and reset destination, times out and never returns provider bodies. Tokens, addresses, passwords and credentials are excluded from logs and browser evidence. No provider or database management key enters the application. Customer identity remains configured in Neon; configuring operator recovery does not change its password or SMTP settings.

Migration 0029 appends an immutable credential-change security event through a restricted security-definer trigger. It retains no password, hash or token. Existing identity rows, histories and grants remain unchanged. Apply this additive migration separately to the explicitly verified live synthetic branch after populated upgrade and restricted-role tests; builds never migrate. Application rollback keeps the audit trigger and disables the new recovery entry points if needed.

A verified customer session may reveal its already approved pending invitation through the existing protected setup endpoint. A client hint directs that person to setup without granting access or making operator sign-in depend on the customer provider. It refreshes when the page regains focus, uses no persistent storage and disappears on denial or unavailable service. The account component is keyed by the current authenticated identity.

The member directory resolves display names only after the current workspace `audit.read` check and only for principal IDs returned by that workspace's restricted membership query. It exposes no provider-wide customer directory or email list. Owners select an existing member and an explicit intended role. The existing `members.manage` permission, fresh MFA, tenant isolation, last-owner guard and immutable membership history remain authoritative. Admins can inspect the permitted audit, while only owners can change roles. Creating staff invitations remains the reviewed offline procedure. Workspace administration cannot manage Neon provider credentials, erase evidence, change historical money or open customer operations.

Acceptance must distinguish synthetic backend/browser tests, a saved SMTP delivery test, an actual customer reset request and the recipient's private inbox/password/MFA completion. None alone proves all-role production acceptance.
