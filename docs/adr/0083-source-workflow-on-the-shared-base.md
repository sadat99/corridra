# ADR-083: The sourcing workflow on the shared base

Status: Proposed. Reviews pending (product, designer, independent architecture and security review). Designed only: nothing is implemented, tested, deployed, enabled or approved by this record. No SQL, application code, migration, installer change, workflow input or switch change accompanies it. No requirement moves to VERIFIED on design alone, and the whole of V3 stays PARTIAL. Date: 13 November 2026.

Related: ADR-082 (supply sources for counterparty candidates) is merged on main (`0b87d4a`, PR 476) with status Accepted for build, locked ready to implement; it is not built. This record cites it as accepted for build, not as built. Sequencing follows owner decision 1, option b, per Orchestrator 9: slice S6 of this record starts only after ADR-082's own build.

## Owner request

On 13 November 2026 the owner asked for the buying (sourcing of products and machinery) module to be built "exceptionally efficient and effective", with exceptional focus on the Bangladesh to China workflow, while being 100 percent configurable for any other direction (Bangladesh to Malaysia, France to America, any country to any country), at the same sophisticated grade as the selling module, with different functions, all on the same base: "the best efficient, effective, simplest, synced, integrated, safe, secure". The owner shared a Bangladesh to China example workflow earlier. Its field foundation is section 3 of the owner's Field-Validated Commercial Workflow directive. That prose is not in the repository: only its scenario table 01 to 16 is, in `docs/implementation/field-workflow-acceptance-2026-10-28.md` (rows at lines 19 to 34). This record cites that table and nothing beyond it. Any conversion or fee figures the operator reported in conversation are deliberately absent from this record and must never be written into it or into pack data.

## Context

The buying workflow already runs on the shared base. What is missing is a route-level description of it, requirement-anchored comparison, landed-cost visibility, samples, machinery after-award records and a few typed fields. Evidence, re-opened at main `0b87d4a`:

- Pack configuration is not free jsonb. The column is a jsonb object on `app.corridor_pack_version` with status DRAFT, TESTING, LIMITED, ACTIVE or PAUSED (`packages/db/migrations/0020_versioned_corridors.sql:30-32`), but the trigger `app.guard_corridor_configuration` requires all 18 named keys, refuses any other count (`count(*)<>18`), and requires arrays of at most 50 strings except `reviewRequired`, `aiPolicyRef` and `pricingRef` (`packages/db/migrations/0026_governed_intelligence.sql:117-141`). Its current definition is the hash-guarded replacement at `packages/db/customer-real-use-migrations/0003_real_customer_modules.sql:426-444` (the guard at 426-427 hashes the previous definition; the replacement body starts at 428). On the application side `routeConfiguration` is `.strict()` with the same 18 keys (`packages/domain/src/corridors.ts:7-27`). A `sourcing` key is refused at both layers. Publication goes through the reviewed flow: an independent reviewer is required and the published pack's configuration must equal the proposal's (`0028_operations_control_center.sql:100-105`); `createRoute` is at `packages/missions/src/corridors.ts:182`.
- `compareOffers(offers, calculatedAt, context)` already returns NOT COMPARABLE for missing terms (including `toolingMinor`, `setupMinor`, `packagingMinor`, `shipping`, and for machinery installation, commissioning, warranty, training and spares), expired offers, an inconsistent total, stale evidence and differences of requirement id, currency and scope terms (`specification`, `quantity`, `moq`, `unit`, `incoterm`, `shipping`, `leadTime`, `paymentTerms`, `warranty`, `installation`, `commissioning`, `training`, `spares`) between offers (`packages/domain/src/commercial-missions.ts:309-392`). It compares offers with each other only: each offer carries a `requirementId` but no pinned requirement version is passed in. `offerContext` switches machinery handling by mission type key (`:305-308`). `paymentTerms` is one free-text field.
- Offer terms are a closed set held in at least six places that must stay equal, as `packages/db/customer-real-use-migrations/0020_offer_commissioning_term.sql` states ("so the four lists stay equal") when it added `commissioning` with `recipient-reply-review-migrations/0002_commissioning_term.sql` and `recipient-response-revision-migrations/0002_commissioning_term.sql`. The places: (1) `app.guard_commercial_mission`, created at `0023_commercial_mission_execution.sql:112-116`, restated at `customer-real-use-migrations/0003_real_customer_modules.sql:396`, and live as replaced by 0020 (string values up to 1000 characters; the live list includes `commissioning`); (2) `app.recipient_detail_respond` (core `0025_scoped_product_experience.sql:115-122`, also replaced by 0020); (3) `app.recipient_detail_body_check` (`recipient-response-revision-migrations/0001_response_revision.sql:82-97`), in an optional module, so its replacement is conditional on that module being installed; (4) the CHECK `recipient_reply_review_ask_terms_check` on `app.recipient_reply_review`; (5) the cardinality CHECK `recipient_reply_review_check1` (a bound of 1 to 19 terms; the list is already 19, so any added key breaks it unless the bound is raised); (6) `app.reply_quotation_prefill` names (`recipient-reply-review-migrations/0003_reply_quotation_binding.sql:135,175-180`); plus zod `offerTerms`, `.strict()` with `toolingMinor`, `setupMinor`, `packagingMinor`, `shipping` (INCLUDED, EXCLUDED, NOT_SUPPLIED) and `commissioning` (`commercial-missions.ts:119-141`). The four reply-side places (2 to 5) live in the reply review and response revision modules. TypeScript holds more copies: `replyTermNames` (19 keys) and `askTerms` as `z.array(z.enum(replyTermNames)).min(1).max(19)` in `packages/domain/src/reply-review.ts:17-37,66`; the reply form field list with kind and group per key in `apps/web/lib/reply-terms.ts:30-50`; the English labels at `apps/web/lib/reply-words.ts:133` and the Chinese labels at `:245` (native-review gated); and the operator labels in `apps/web/lib/reply-review-view.ts:33`. Value rules are also held in three more places beyond names: `app.guard_commercial_mission` (real-use 0003:396-402: minor-unit regular expression, quantity regular expression, the shipping enum, the Incoterm enum, the `validUntil` timestamp cast), `app.recipient_detail_respond` (`0025_scoped_product_experience.sql:122-124`, a generic `LIKE '%Minor'` rule) and the prefill function. The prefill function also has a per-key shape rule (minor-unit regular expressions, text length 3 to 1000, `unit` 1 to 80; `0003_reply_quotation_binding.sql:175-181`), so a new key needs a shape rule, not only a name.
- Money conversion exists once: `fxObservation` (source, observedAt, from, to, numerator, denominator, `RATIONAL_HALF_UP`) and `deriveConversion` (`packages/domain/src/economics.ts:25-36`), "derived reporting only: original ledger currency and amount are never replaced".

The installer declares exactly 25 inputs (lines 9-144), the limit enforced by `tests/workflow-inputs.test.mjs`.
- The paid ADR-055 "Supplier sample check" service has the key `supplier-sample-check` (`packages/db/customer-service-request-migrations/0001_contextual_service_requests.sql:253`).
- ADR-082 is on main (`0b87d4a`, PR 476): Accepted for build, locked ready to implement, not built. Its owner decision 17 builds Sell only and proves Source reuse with a SUPPLIER-role fixture.
- The scenario table already lists tests for the 16 field scenarios (`docs/implementation/field-workflow-acceptance-2026-10-28.md:19-34`), among them the China to Bangladesh supplier case and BD/CN, BD/ES, ES/BD, JP/KE, CN/BD configured TESTING routes (rows 12 and 16).

Conclusion: no new engine is needed. Every decision below reuses an existing record, function or review flow and adds optional, additive, versioned structure. The pack and offer term lists are closed by database guards, so each added key is a reviewed forward migration, not data alone.

## Decisions

1. Route profile. A new optional key `sourcing` (with its own `profileVersion`) inside the existing pack `configuration`, as the 19th permitted key. Two options were compared. (a) Extend the configuration: one forward migration replacing `app.guard_corridor_configuration()` plus an optional field on `routeConfiguration`. (b) A separate versioned profile record referenced from the pack: a new table, RLS, its own review and publish path and a second equality check. Option (a) is chosen because it is smaller and keeps the reviewed flow exactly as it is: the publication guard already requires the published pack's whole configuration to equal the proposal's (`0028_operations_control_center.sql:100-105`), so the profile is reviewed, independently approved and published with the pack and needs no second flow. Packs without the block parse and behave unchanged; unknown top-level keys are still refused. The replacement guard exempts `sourcing` from both the exact-count check (`<>18`, `0026_governed_intelligence.sql:128`) and the array-of-strings loop (`:129-134`, restated at real-use 0003:444), and validates it separately as a bounded object. Size: a proposal is held in `app.configuration_proposal.proposed_pack` under `CHECK(octet_length(proposed_pack::text)<=8192)` (`0028_operations_control_center.sql:20`) and publication requires `configuration IS NOT DISTINCT FROM proposed_pack->'configuration'` (`:103`). This record keeps that CHECK unchanged and gives the `sourcing` block a budget of 4096 octets, enforced by the guard, so the 18 existing keys and the proposal envelope (status, version) keep about 4 KB, far more than a pack's 18 short arrays need. The S1 test asserts the BD to CN fixture's whole proposal is at most 8192 octets and its `sourcing` block at most 4096, and the PR records the measured sizes. If a representative profile cannot fit, S1 stops and a separate additive migration widening that CHECK is reviewed on its own; it is not assumed here. Why no seed: pack selection and the assignment guard use only the date (`packages/missions/src/operations.ts:214,365`; the guard refuses `effective_from>now()`), the guard at `0026_governed_intelligence.sql:127` refuses a version whose `effective_from` is not strictly later than every earlier one, and `createRoute` writes version 1 as DRAFT with `effective_from=now()` (`packages/missions/src/corridors.ts:167`). A seed with a future date would become current by itself when the date passes, so it would not be a switch. With only the 18 keys present, behaviour is identical to today. Merge rule: `resolveConfiguration` (`packages/domain/src/corridors.ts:41-81`) merges layers through fixed allowed and required key lists and re-parses; `sourcing` is global only, set on the pack root and carried through unchanged. A layer that carries `sourcing` is an error ("Sourcing profile belongs to the pack root"), like the policy bindings, never silently dropped. The block holds category contexts, required requirement fields per category, applicable landed-cost elements, default Incoterm guidance (a hint only, never a term), sample steps, supplier reply languages, document kinds and readiness field lists. The Bangladesh to China reference pack is TESTING status (owner decision 2). This record ships its contents as a reviewed document and a test fixture, not as a database seed: nothing is written to any tenant until the owner opens it. At that time it is proposed through the reviewed flow with an independent reviewer as pack version 2 or later of the BD to CN route, with `effective_from` set when proposed. This is the opening step; it is configuration, not launch approval. A property test generates country pairs in both orders and asserts a valid pack and the identical engine path; the codebase gets no country branch. Rejected here: a per-country module.
2. Requirement-anchored comparison. Extend `compareOffers` with an optional pinned requirement input and check each offer against it, on top of the existing peer checks. "Pinned requirement version" means the exact requirement id, version and SHA-256 digest of its fields that the comparison names (the same pin ADR-072 uses); it is the requirement on file, and it is a customer-confirmed specification only when an ADR-072 confirmation exists for that pin. What `compareOffers` already returns today (`commercial-missions.ts:339-392`): NOT COMPARABLE for missing terms, expired offers, an inconsistent total, stale evidence and differences of requirement id, currency and scope terms between offers. Five checks are new. (a) Differs from the pinned requirement (S2). (b) Structured payment mismatch (S2). (c) Offer price versus the prior accepted or pinned offer on the same requirement, shown as a disclosed difference in original currency and minor units, derived, never a decision, never a ranking and never a reason to call an offer better (S2). (e) Certification: each document kind or certification term the pack lists as applicable is supplied, excluded or not stated on the offer; an offer whose certification status is not stated is NOT COMPARABLE with the reason "Missing: certification". Owned by S3 and gated like (d). (d) Unsupplied landed-cost element, owned by S3 because the element keys arrive there; until S3 checks (d) and (e) are off, gated on the pack's applicable-element list being present, so S2 cannot mark every pinned offer NOT COMPARABLE. V3-02-040 (a low price must never conceal missing costs, different scope, installation obligations, uncertain certification or incompatible payment or delivery terms) is covered by checks (a) to (e) together, not by cost alone. One function serves team and buyer. It never names a winner or recommends. Without the input the function behaves as today (the current behaviour is the floor).
3. Landed cost elements. Goods, tooling, packaging, inland freight, export clearance, sea or air freight, insurance, duty and tax, port and clearance, inland delivery, installation and commissioning, certification, bank and FX charges, agent fee, spares. Each is supplied, excluded or not stated per offer. Today the terms already carry `toolingMinor`, `setupMinor`, `packagingMinor` and a `shipping` state of INCLUDED, EXCLUDED or NOT_SUPPLIED; those keep their meaning. Offer terms are not open jsonb: the closed list lives in the six places and zod listed in Context, and a new key needs a forward replacement of every one of them in the same slice. The live quotation guard already includes `commissioning` (added by `customer-real-use-migrations/0020_offer_commissioning_term.sql`), so the lists are equal today and the new migrations hash the post-0020 live definitions, not the 0003 text. The reply-side replacements (places 2 to 5, including the raise of the 1 to 19 cardinality bound) require the ADR-081 reply review migrations installed; the response revision replacement runs only when that optional module is installed. If a module is absent, its replacement is skipped for now, and the slice states so. Optional modules install from fixed files, so a later install of one leaves its list behind: the rule is that every later install of an optional module is followed by a reviewed catch-up re-run of the S2 and S3 replacements for that module. The `sourcing_workflow_install` action is idempotent and re-applies every replacement whose module is present. Every new enum-typed key (payment instrument, landed-cost element states, who you deal with) needs a value rule in all of those places, not only a name. A test reads the live definitions and asserts that all places list identical keys and identical value rules, after every install order (reply review before or after the sourcing module, response revision installed or not). The TypeScript copies (reply-review.ts, reply-terms.ts, reply-words.ts, reply-review-view.ts) change in the same PR; new keys get an English label with the pending-native-review marker and no machine-written Chinese. Amounts use exact minor-unit patterns and states use INCLUDED, EXCLUDED, NOT_SUPPLIED. A derived view sums supplied same-currency elements only when every pack-applicable element is stated (supplied or excluded); if any applicable element is "not stated" no total is shown, only the element rows and the line "Totals are not shown because some costs are not stated." The compare table shows no total row across suppliers whose counted element sets differ. The view lists its assumptions and is labelled "derived, not an offer". Conversion happens only through `fxObservation` and `deriveConversion` with rate, source and date shown (`economics.ts:25-36`). Samples reuse the paid ADR-055 "Supplier sample check" service by reference, with no change to it (`customer-service-request-migrations/0001_contextual_service_requests.sql:253`, key `supplier-sample-check`); portfolio reuse follows ADR-038. Incoterm guidance per route comes from the pack. "Agent fee" means only a third-party agent fee quoted by the supplier, never a Corridra fee.
4. Structured payment terms. Optional keys beside the free text `paymentTerms`: deposit share, balance trigger, instrument (T/T, L/C at sight, usance), due days. They are new allow-listed offer term keys, so decision 3's rule applies (all six places and zod together). A mismatch between offers or with the requirement is a flag, not a verdict on merit.
5. Samples and trials. A buyer sample comes before any meeting or award, so it cannot hang off the sell-side `app.commercial_record` chain: that table is bound to `app.opportunity`, which needs a meeting and carries the revenue status ladder LEAD to CASH_COLLECTED, with `external_reference` unique per kind (`0011_commercial_followthrough.sql:5-26`). Samples are therefore an additive append-only state record keyed to the mission and the supplier offer, with states requested, sent, received, tested, passed, failed, waived, and a link to a SAMPLE `commercial_record` only when one already exists. It creates no opportunity, no amount or currency, no revenue status and no trade value, and implies none. Labels read "Passed (as entered)", "Failed (as entered)" and "Waived". Entries are declarations with a source and are never verification.
6. Machinery after award. Records for installation, commissioning, acceptance test, warranty start, warranty claim and spare-part request, as additive append-only records keyed to the mission and the accepted supplier offer (the same shape as decision 5, extended by a forward migration in S5), with no opportunity, revenue or amount. Records only: no engineering or legal claim and no machinery app (V3-02-039).
7. Supplier candidates only through ADR-082's candidate record and structured profile. ADR-082 (on main, Accepted for build, locked ready to implement, not built) is role-agnostic and uses the word "supply" for its module and for its Sell-side first build; for a buyer mission the nominee is the SUPPLIER-side counterparty (profile `role` SUPPLIER), and "supply candidate" there means a candidate seller of what the buyer wants. ADR-082 owner decision 17 builds Sell only and proves Source reuse with a SUPPLIER-role fixture test; this record's S6 adds the buyer-mission staff nomination surface on the same commands and tables (owner decision 7), a scope extension of ADR-082 with no second layer. This is decided (owner decision 7 below): the surface is built; the fallback is fixture-only proof if that part of ADR-082 is not built. V3-02-023 and V3-02-024 stay NOT VERIFIED either way. Identity status comes from `packages/counterparties/src/index.ts:57`; source rights follow ADR-079 slice B. Platform and partner source kinds stay locked off. Starts after ADR-082's build (owner decision 1).
8. Supplier-side RFQ by reply page in Chinese. Sample only (`@example.invalid`, SYNTHETIC or MANUAL channel) until outreach opens; no real supplier is contacted. Five questions: what, how many, price and terms, lead time, anything you cannot do. One-tap decline with an optional reason. The Chinese copy is marked "pending native review" (owner decision 3); native review stays a closed gate. It rides ADR-081's reviewed reply path and its switch.
9. Buyer-side Bangla behind the language release. A marked fallback shows where a string is missing. With the release off, English is unaffected.
10. Field partner tasks reuse the existing task kinds (`packages/network/src/schema.ts:17-29`) with independent review (ADR-028). The pack's sample steps may name the task kind to create; this link is built in S4. No payouts.
11. Four readiness levels: understood, enough to research, enough for comparable quotes, ready to commit. Pure functions of the requirement fields and the pack's field lists, listing what is missing. No percentage, never stored. "Ready to commit" never authorises a purchase. The existing `draftReadiness` stays unchanged.
12. One clarification thread per requirement version through the existing delivery questions. The specification changes only on customer confirmation through the existing ADR-072 path: staff request the confirmation, fresh MFA, a pinned publication, then the customer acknowledges the exact fields. A supplier-proposed change can only start that path; nothing is written to the requirement by the thread, and an unconfirmed reply changes nothing. Persistence uses existing records: a supplier-proposed change arrives as a reviewed reply (ADR-081 reply review, decision ASK or a recorded offer revision); the customer's `Accept Change` is written as the customer's own response on the existing reviewed delivery question (the self-declared delivery response ADR-072 describes, which stays a response and never becomes a confirmation) and sets the existing next action for the team; the team then starts the ADR-072 request. Nothing else is written, and the requirement is untouched. The builder first confirms a customer can write that response from the Room page; if none fits, S2b gets an additive migration and says so. Supplier messages shown "via Corridra" come only from reviewed replies and sample channels until outreach opens.
13. Starting point drives the first step: a mapping from the seven starting points to a first step and to the pack's questions. The selection remains a customer declaration, not evidence.
14. "Decided not to proceed": typed reason codes (price, specification mismatch, supplier not responsive, quality or sample failed, timing, compliance or certification, found another route, internal decision, other) carried as an optional `reasonCode` in the existing `details` jsonb of the mission command row. `app.mission_command` already has `details jsonb NOT NULL` (`0007_mission_core.sql:61`) and `packages/missions/src/index.ts:441-452` stores the whole parsed command there, so S9 needs no migration for the code and main is unchanged when the key is absent. `missionCommand` is one `z.object` for all twelve actions (`packages/domain/src/missions.ts:145-165`); a refine restricts `reasonCode` to `close`, `pause` and `cancel`. Queue and read views read `details->>'reasonCode'`. The existing mandatory free-text `reason` (3 to 500 characters) keeps carrying words, including for "other"; no second text field is added. S9 adds no event write. `reasonCode` lives only in the immutable `app.mission_command.details` row (`mission_command` has the immutability trigger at `0007_mission_core.sql:159` and the `guard_mission_child` BEFORE INSERT guard at `:170,178`); the mission event trigger `app.record_mission()` sits on `app.mission` and writes only the event id, status and version (`:101-113`). No reason, code or text enters any event. Staff read the code from the command row; `app.mission_command` is readable only under the staff-side real-use read (`customer-real-use-migrations/0002_real_request_authority.sql:282`), so the customer Room page has no read path to it. The customer sees only "Decided not to proceed" with the date and the words they typed themselves; showing the typed reason to the customer is a later item needing a reviewed customer read function. States: `index.ts:328-329` refuses any command on a CANCELLED or CLOSED mission, and `resume` works only from ON_HOLD (`:385-390`), so the code rides on `pause` (then `resume` with the original gaps intact) or on `cancel` (then a new request, never a resume), and on `close` only from COMMERCIAL_PIPELINE (about `:363-368`). No fault attribution. History is kept and resume rules are unchanged.
15. "Who you deal with" on the supplier offer: factory direct, trader, agent, Corridra service partner (labels settled by the designer). It is a separate field on the supplier offer terms (a new allow-listed key, decision 3), not an ADR-073 arrangement: ADR-073 arrangements attach to service-quote versions and describe bundled supply, separate fee, conditional commission and hybrid terms with the actual seller, payer and recipient. No mapping between the two is created. A screen may show a service quote's ADR-073 arrangement next to the offer's field only when both exist, and then needs the ADR-073 module installed. Cost and markup stay staff-only (ADR-073). The value "Corridra service partner" describes a facilitator only: the offer then names a separate actual seller, and the partner is never recorded as the seller. Corridra is never principal seller. "Corridra's service fee is separate" is shown only when a service quote record states it.
16. Team queue grouped by who acts next (customer, supplier, Corridra team, partner, waiting on a date), derived from existing records: an open delivery question or a pending specification confirmation means the customer; an RFQ with no reply or an open offer request means a supplier; an open network task assigned to a partner means a partner; a next action with a future due date and no open item above means waiting on a date; anything else is the Corridra team, by the mission's existing owner and next action. The filter runs on the server before pagination. The builder re-reads these records and states any that cannot be derived.
17. Lead partner grouping: design only. Build is blocked until the owner opens it.
18. Acceptance tests for scenarios 01, 03, 05, 06, 07, 10, 12 and 16, plus the buyer-mission nomination test for decision 7, named in the Slices section, each landed in its own slice with a red-first record (not a merged failing test). They do not replace the existing tests in the scenario table.

## Slices

Common to every slice: ships with its switch off and its control closed; one or two PRs; leaves main releasable; additive forward migration only, installed by the reviewed installer after merge, never by a build. Installer: `.github/workflows/install-customer-modules.yml` declares exactly 25 workflow*dispatch inputs (lines 9-144), the maximum `tests/workflow-inputs.test.mjs` allows, so a new input is not possible. The only feasible route is three new values on the existing `field_modules_action` choice (lines 66-90), `sourcing_workflow_install`, `sourcing_workflow_enable`, `sourcing_workflow_pause`, mapped in the workflow `env` to one action variable read by `scripts/install-customer-modules.ts`, as the `contact_changes*_` values are. ADR-082 plans three values (`supply*sources*_`) on the same options array: whichever PR merges second rebases and appends its values; the two sets are disjoint. The first installing slice (S1) therefore lists the workflow file, `scripts/install-customer-modules.ts`and`tests/workflow-inputs.test.mjs`in its Files. App switch`CORRIDRA_SOURCING_WORKFLOW`, unset means off, registered in `apps/web/lib/ux-switches.ts`and`apps/web/lib/owner-switches.ts`. Migration folder `packages/db/sourcing-workflow-migrations/`with its own migrator and registry, refusing unless the customer real-use module that holds the current guard definitions is installed; file numbers are the next free ones at build time. Each visible slice must passUI/UX.v3 (`docs/agents/ui-direction.md`)and`tests/design-system-guard.test.mjs`, at 320, 390 and 1440 wide, and show loading, empty, conflict, error and revoked states. Each slice states positive and denial cases. Rollback for every slice: switch off hides the surface and keeps all records; pause control refuses new commands while reads stay.

Each slice lands its own acceptance test (listed under the slice and in the next section). "Fails on today's code" means a red-first record: the builder commits the test, shows it failing against the pre-slice code in the PR description and the work log, and it passes in the same PR.
