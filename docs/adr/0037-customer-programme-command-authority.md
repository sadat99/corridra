# ADR-037: Scoped customer creation of canonical programmes

Status: locally implemented and tested;full exact-head CI/release pending. Governing V3 requirements: independent organiser programme creation and customer workspace authority. This is a new SaaS command,not a navigation repair. No admission,provider,real operation or gate activation. Full independent Delegation OS remains MISSING.

## Actual baseline and conflict boundary

The existing engine stores programmes in app.delivery_programme. Its insert guard requires app.actor_id/app.can_access/member_role,and the shared event trigger requires an actual staff actor or an explicitly owner-session bootstrap service. Customer proof intentionally yields no staff actor. Reusing a staff session,setting an MFA flag,granting a broad service membership,disabling a guard or creating a parallel programme/mission backend would violate the existing contract. Do none of these.

Add only a new narrowly scoped customer command for canonical programme creation in a synthetic customer workspace. Workspace owner/admin authority is checked from existing collaborative_workspaces under the exact workspace-access lock. Admitted verified provider proof remains the identity boundary. No participant/private commercial records are granted by programme administration. Organisation linking,participant onboarding,dates/agenda/economics remain separate unimplemented commands.

## Scope of the unavoidable forward extension

An explicit optional module may extend only app.delivery_guard and app.record_change with a fail-closed branch for the exact new programme command. Preserve their old signatures,owners,ACLs,all old staff logic and sharing/MFA clauses. Keep app.actor_id/member_role/can_access/fresh_mfa and every RLS policy unchanged. Preserve original migration files and records. The new migration must assert the known immutable old function body hashes before extending;unknown drift is a conflict,not permission to overwrite. CREATE OR REPLACE is a forward compatible capability extension,not a rewrite of migration history or an alteration of old records. No old trigger/table/column is dropped.

The execution grant is private and one-use,created only inside the security-definer canonical programme creation port after provider admission/current workspace owner-admin checks. Bind it to proof hash,current backend PID,transaction ID,exact canonical table OID,complete normalized row digest,workspace,actual admitted customer initiator and configured active service executor. Use an unreturned random nonce in a transaction-local setting;delete the grant before returning. Runtime/auth cannot mint/read grants. Guard and event trigger verify the full tuple,fresh proof and wall-clock expiry. Matching a table name or trusting a caller-set setting alone must never authorize anything.

The actual migrated delivery guard is SECURITY DEFINER and stays so;catalog inspection confirms its existing attributes and source hash. It consults the private helper only when the new execution setting is present. A raw runtime caller cannot execute the helper directly;invoking the original trigger with a fabricated setting fails the private full-tuple grant check. Without the setting,the original staff predicate and every business/sharing validation run unchanged. The only accepted new relation is app.delivery_programme;temporary lookalike tables,sharing,source,money and unrelated records cannot use the grant.

The event trigger records the real service executor and an explicit customer initiator/workspace/command authority. It does not impersonate a staff person or credit their MFA. All old staff/bootstrap event payloads remain unchanged when there is no valid customer execution. Canonical row,event,audit,outbox and immutable customer ownership/command binding commit atomically;any failure/expired proof rolls back all of them. No historical event or money record is updated.

## Rollout and acceptance

Separate explicit optional installer/receipt,unchanged three-module customer base;default-off customer-programme flag requires synthetic workspace mode and nonproduction. No cloud installation before exact-head acceptance. New page/API require the same fresh proof and role checks;all account links stay relative and programme access lives under existing workspace cards,not a sixth top-level navigation item. UI may create/list actual sample planning programmes only. Missing participant/agenda/meeting/economics operations must be stated and have no pretending controls.

Mandatory database tests:owner creation/exact/concurrent retry;member/other-workspace/unadmitted/anonymous denial;fabricated setting/proof/table/row denial;unchanged staff owner/operator/viewer/MFA/sharing and direct RLS denial after upgrade;actual service/customer event attribution and atomic rollback;proof expiry while waiting;immutable bindings;only the two reviewed function definitions change while old signatures/ACLs/policies/rows/receipts remain intact. UI tests must cover scoped creation/list,recovery/conflict/deny/malformed/hide/restore,keyboard/axe/three widths. These are not real provider acceptance. Full required exact-head CI and gated READY deployment precede source release. Actual provider session/full organiser journey/real activation remain independent acceptance requirements.
