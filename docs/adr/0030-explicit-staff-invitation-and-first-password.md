# ADR 030: Explicit staff invitation and first-password setup

Current amendment: [ADR 031](0031-operator-password-recovery-and-scoped-directory.md) supersedes only the offline existing-staff password-recovery restriction. First invitation, lost MFA, suspended identity and expired-invitation boundaries remain.

Status: V2 access completion; actual provisioning and release evidence are separate.

Customer identity and staff identity remain separate. A customer email matching an operator email never grants membership. The owner explicitly requested founder/admin access and supplied the email and operating country. Owner includes admin capabilities; one membership has one role per workspace.

The offline invitation procedure requires an existing active owner, fresh operator MFA, a synthetic tenant and an explicit target role/country. It creates a disabled staff principal with an unknown random password, a country-scoped membership, the existing immutable membership audit/outbox event and an invitation approval security event. It refuses existing staff identities. Only the trusted offline schema-owner procedure can issue the invitation; no runtime endpoint receives its connection or grants membership.

The existing live intake workspace has technical synthetic owners and no human owner. A separate one-time **offline first-human-owner bootstrap** is authorized by the owner's explicit role, email and country instructions. It requires schema-owner administration, the exact synthetic intake destination, an already independently verified managed customer identity, and no historical non-synthetic owner membership, including revoked/disabled owners. It uses the existing audited bootstrap service actor and records the explicit approval reference. It does not claim an unavailable owner's MFA, reset their identity or disable their authenticator. Every existing owner and record is preserved. After the first human owner exists, this bootstrap refuses further use; ordinary invitations require fresh owner MFA. No runtime endpoint can call this procedure.

A seven-day namespaced invitation is retained in the existing identity-provider verification store. The protected setup endpoint obtains a fresh verified customer session directly from the trusted Neon provider, fixes the email from that session, and accepts only a new password. It does not accept user IDs, email, roles, countries, workspace IDs or invitation authority from a browser. No invitation secrets are sent in email, URLs or chat.

The restricted auth connection can set the first credential only for the exact invited, disabled, unverified, never-authenticated staff identity, with no authenticator/session history and the exact original pending-disabled timestamp. An owner suspension after invitation cannot be undone by setup. A transaction and advisory lock serialize consumption. Password hashing uses the existing Better Auth function. The invitation is consumed atomically with activation; repeat, expired, unverified and other-email requests fail closed. This is not a general password-reset or privilege-recovery endpoint. Password setup does not create an operator session or MFA assurance. Separate password sign-in and real authenticator enrollment/verification remain mandatory for any workspace access. Existing memberships, country policies, retention rules and real-data gates remain unchanged.

Account/API responses are uncached. Writes require the exact application Origin and a bounded body. No passwords or provider tokens are logged. Failed setup retains the invitation and disabled identity transactionally. Expired invitation recovery remains an offline owner-reviewed procedure; existing staff account recovery remains the separately audited offline process.

No migration or new queue/storage service is required. Tests exercise restricted auth/owner pools, invitation authority and audit, country scope, expiry, one-time consumption, actual provider password sign-in and continued denial before MFA. The live recipient sets their own password and authenticator; acceptance must never use or collect their password or recovery codes.
