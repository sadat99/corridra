# ADR-032: Customer workspace authority, preserved staff security

Status: forward implementation under verification; synthetic-only, production disabled. Initial conflict assessment retained below.

V3 requirements V3-06-002 through V3-06-006 need customer-owned workspaces, memberships, persistent missions and independent delegation administration. Existing customer identity remains Managed Neon Auth; staff identity remains self-managed Better Auth with TOTP. Neither email equality nor a customer account can create staff authority. This amends forward from ADR-003 and ADR-020 without replacing their staff permissions.

The intended model reuses app.tenant and canonical app.organisation. Customer memberships must be separate from app.membership, whose identities and authorisation require staff MFA. Do not add customer alternatives to app.actor_id, app.member_role or existing evidence/source/financial RLS. A trusted server checks the current provider session and verified email before issuing any bounded customer database proof. Runtime SQL cannot mint or inspect those proofs. Customer database access must independently enforce current membership and selected tenant; caller-supplied subject, email, organisation, role or tenant is never proof of authority.

First implementation packet is limited to synthetic workspace provisioning and owner listing. Additive tables/functions must enforce atomic provisioning and retry conflict semantics, reuse one organisation identity within its rights boundary, append audit/events, and grant no source, staff, financial or other tenant access. Do not expose creation controls until the API and restricted-role tests work. Production remains disabled behind a dedicated flag; real-data gates do not open with a passing test or deployment.

Subsequent separately verified packets add invitations/membership revocation, explicit mission ownership/access, programme administration and participant scope, and exact-currency organiser economics. Existing managed delivery links, publications, exports, cancellation, recovery and all expert routes remain valid. Existing mission/delegation domain services remain the commercial engine. No billing provider, new CRM or second mission backend is required by this decision.

Required acceptance includes fresh install and populated additive upgrade; original migration/source hashes; unverified, expired and revoked customer sessions; forged subject/tenant and cross-tenant denial; customer-to-staff denial even with matching email; last-owner protection; atomic duplicate/conflicting retries; pool context cleanup; and the full original integration and browser regressions. Actual received OTP, sign-in/out, reload and revocation are separate provider acceptance, not inferred from anonymous get-session200.

## Unresolved acceptance conflict

`tests/integration/foundations.test.ts:73` asserts exactly29 rows in migrations.applied after the current migration runner. Adding a required migration changes that count. The owner's V3 execution rules prohibit editing, skipping or weakening an original test to make it pass. No migration or test has been changed to circumvent this assertion. A separate migration stream, silently limiting old fixtures to old migrations, falsifying migration history or suppressing that suite solely to evade the assertion would not resolve the preservation requirement. This conflict blocks the additive-schema packet under the literal current instructions. Independent V3 work that requires no new migration can continue; no additional general release approval is needed.

## Rollback and blast radius

This proposed decision changes no auth implementation, RLS policy, migration or data. When implementation becomes possible, deploy schema additively before enabling the customer flag; disable the flag and redeploy the compatible application to roll back exposure. Retain new canonical records and audit/history, and leave all historic migrations immutable.

## Forward resolution, 17 October 2026

The initial blocking assessment above assumed that customer authority must be installed by every core migration invocation. Customer identity instead has an independently approved provider, admission policy and rollout lifecycle. Core staff-only installations must continue to operate without installing or configuring customer authority. This warrants an explicit optional module, rather than changing an original test or silently filtering its fixtures.

`migrateCustomerAuthority` explicitly installs the unchanged core and then the additive `packages/db/customer-migrations/` module. Its separate `customer_migrations.applied` registry records every module file and SHA256, rejects changed/missing/reordered history, and uses the existing migration advisory lock. No core migration, runner, registry receipt or original test is altered. New integration acceptance enumerates the entire module directory, verifies repeat/fresh installation, and compares all populated core-table digests, function definitions, policies and ACLs before/after installation. The original core test still checks exactly its original29 migrations; full CI also runs the new module's independent tests. A separate registry without this genuine deployment boundary and preservation evidence would not resolve the initial concern.

The first packet implements admitted synthetic customer tenant provisioning and owner listing only. `customer_private` holds the pinned Frankfurt issuer, explicit synthetic-subject admission and short-lived opaque proofs. `corridra_auth` can attest a fresh provider session but cannot grant admission, modify the issuer or extend a proof. Restricted runtime access uses fixed-path functions and self-scoped RLS in `customer`; existing staff identity and app RLS functions/policies are unchanged. Owner grants and provision commands are immutable. Revocation disables the customer principal; repeat admission does not reactivate it. Invitations, member changes and last-owner transfer require a later reviewed additive capability.

Each command reuses `app.tenant` and records exactly one existing domain-event/audit/outbox chain. A real service principal is the executor and the separate customer initiator is explicit in the event payload. This does not manufacture staff authority or reinterpret historical events. No private company input is inserted into the globally readable organisation catalogue: the response explicitly returns `organisationId: null`. Canonical organisation linking, persistent mission access and independent organiser administration remain missing.

Blast radius is limited to new module objects, their grants and a default-off customer API/service. Core tables receive new records only when an explicitly admitted synthetic customer invokes an enabled non-production service. No cloud schema or production flag is changed by this source packet. The existing foundations remain usable without customer configuration because the provider is resolved lazily. `CORRIDRA_CUSTOMER_WORKSPACES_ENABLED` requires `DATA_ENVIRONMENT=synthetic` and is hard-disabled for Vercel production even if set. There is no creation UI or commercial activation claim. Actual provider OTP/sign-in/reload/revocation and customer browser acceptance remain separately unverified.

Rollback exposure by disabling the customer flag and deploying the previous compatible application. Retain additive schema, tenants and append-only history; do not drop module objects or rewrite records. Independent D01-D06/D08 remain binding.

## Forward client-context boundary, 17 October 2026

Before exposing workspace controls, bind their mounted UI context to the actual freshly resolved provider subject. The optional `x-corridra-customer-subject` request header is a rejection condition only: a mismatch returns409 before proof creation or database writes. It never supplies identity, admission, role or tenant authority; those still come from the existing fresh provider check and restricted database proof/RLS. Missing/unverified/expired sessions remain denied, and matching an unadmitted subject still grants nothing. Bound malformed context is rejected400. Existing clients without this optional header retain their current service behavior.

This boundary prevents a draft mounted for account A from being submitted or a list rendered under account B after a session switch. Customer client drafts and responses must also be scoped to the server-provided subject and clear on denied/changed identity; no credentials, OTPs or workspace data are persisted. No SQL, migration, staff identity, RLS, provider configuration, money, event or activation change is needed. Actual private managed-provider session acceptance remains separately unverified; keep the existing customer feature flag off until accepted.

The mounted context also carries optional `x-corridra-customer-issuer`. Issuer and subject together identify the account: a same-subject collision after an approved provider/environment change must not attribute an old page's request to the new identity. A mismatched issuer returns409 before proof creation or database writes, and malformed or oversized issuer context returns400. Both headers remain rejection-only; the actual configured provider, verified fresh session and pinned database admission remain authoritative. Old callers without either optional header retain their existing behavior. No issuer, provider setting or database authority is changed by this guard.

## Forward synthetic collaboration, 17 October 2026

The next additive customer module supports owner-issued single-use invitations, acceptance by an independently admitted verified customer, and owner cancellation or membership revocation. Invitations grant only member access to the synthetic workspace shell. They grant no staff, source, company, mission, offer, financial or programme authority. Original immutable owner grants remain untouched and cannot be revoked through this capability; owner transfer and delegated administration remain missing.

Keep invitation and grant history immutable in new private tables. Store only a hash of a server-generated256-bit token. Return the raw token only on first issuance; an idempotent retry returns the existing invitation with no recoverable token. A lost token requires owner cancellation and a new invitation. No email delivery, provider organisation plugin, automatic admission or new identity is introduced. Tokens are accepted in a bounded POST body, not a server URL. Expiry uses the database clock. Accepted membership survives invitation expiry; cancellation applies only before acceptance. Revoked membership cannot be resurrected by replaying an old invitation or command.

Command and workspace locks serialize duplicate requests and acceptance/revocation. Recheck the short-lived proof after waiting and lock the initiating principal against concurrent disablement. Append one existing event/audit/outbox chain per actual access change using the real service executor and explicit customer initiator. Owner-only invitation/member listings paginate and expose no provider subject or email. Existing owner-only database functions remain unchanged; a new explicitly named listing includes active invited members. Install the module before enabling its server version; exposure remains off while actual private provider acceptance is unverified.

Required tests cover a populated additive upgrade, original migration/function/policy/ACL preservation, concurrent single-use acceptance, same/conflicting retries, lost-token recovery, expiry/cancellation/revocation, last-owner protection, cross-workspace/member/forged-context denials, direct SQL grants and staff/source isolation. New API controls remain unavailable until their backend and denial tests pass. No cloud migration or feature activation is authorized implicitly by a source build.
