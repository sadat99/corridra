# ADR-013: Temporary private EU Blob storage with an S3 migration path

Status: accepted by the user's explicit instruction on 2026-10-05; implemented and adapter acceptance verified. Synthetic scope only.

The user chose private Vercel Blob in Frankfurt (`fra1`) for now, with S3 retained as the planned destination. This changes the storage implementation, not evidence authority, tenant authorization or quarantine. The complete supplied documents remain immutable.

Use `ObjectStorage` for server-side put/get. `EVIDENCE_STORAGE_PROVIDER=vercel-blob` selects Blob; `s3` selects the existing encrypted conditional-create S3 adapter. Blob uses its server-only read-write token, explicit store ID, fixed private access, create-only writes and uncached bounded downloads. Keys are internal paths, never caller-controlled URLs. Both adapters retain the 4 MiB limit and the evidence service checks SHA-256 before scanning or downloading. Bytes become downloadable only after a real clean scan, and verification still requires an independent reviewer with fresh MFA. No direct client upload, public URL or token is returned.

New immutable object references are `vercel-blob:<store-id>:quarantine/<tenant>/<object>` or `s3:<bucket>:quarantine/<tenant>/<object>`. The router strips the reference before storage access and rejects unexpected stores/buckets. Existing unqualified S3 paths remain readable from the configured legacy bucket. These strings use the existing immutable `object_key` field; no schema migration or historical rewrite is needed.

Switch new uploads to S3 while retaining Blob reads with `EVIDENCE_BLOB_READS_ENABLED=true`. The offline copy tool verifies each source hash/size, conditionally creates the S3 object under its unchanged logical path and verifies the copied bytes. It resumes only when an existing target has exactly the expected hash/length. It neither edits evidence records nor deletes Blob originals. After a complete reconciled manifest, `EVIDENCE_MIGRATED_BLOB_STORE_ID` directs the old immutable references to their S3 copies without requiring the Blob token. A missing/corrupt copy fails closed. Clear the transitional read flag when removing Blob credentials. See the [runbook](../runbooks/evidence-storage.md).

The selected Blob store was empty and is dedicated to the Part 03 synthetic PR. It is scoped only to that branch in Vercel. Actual SDK private read/write, duplicate denial and anonymous 403 are verified; the probe was deleted. The owner confirmed Frankfurt/private in the dashboard. The administration API still returns 404/403, and an environment region string alone is not residency evidence.

Tradeoffs: Blob reduces current setup work and integrates with Vercel, but its token grants broad access to the dedicated store. It does not provide the S3 IAM boundary, bucket versioning, lifecycle or object recovery policy already planned. Create-only application writes do not stop a storage administrator from deleting bytes. Before production evidence, move to the reviewed private EU S3 deployment and verify retention, backups, object recovery and any legal holds. While Blob is temporary, use synthetic data only, inspect orphan/expired objects offline and do not claim an automatic 35-day Blob lifecycle. Scanner deployment remains a separate prerequisite; selecting Blob does not enable unscanned uploads.
