# ADR-072: Customer confirmation of a pinned specification

Status: bounded implementation locally verified; exact-head CI, release and managed-provider acceptance pending.

The customer must be able to confirm the exact commercial requirements they reviewed. An ordinary reply, staff selection, comparison verdict or AI explanation cannot establish that confirmation.

Extend the existing reviewed client delivery flow. An owner or admin with fresh MFA requests confirmation against the requirement already disclosed by their own current publication. A metadata row binds the existing delivery question to the immutable requirement ID, version and SHA-256 digest of its original declaration and structured fields. No original publication, requirement, source, question or applied migration is changed.

A fresh admitted customer who can access the saved `CLIENT_PROGRESS` report reviews those exact fields and explicitly acknowledges the confirmation. The SQL command checks the pinned ID, version, digest, current requirement and route assignment, retained source, active publisher, original link and fresh customer proof. It then records the existing self-declared delivery response and a typed confirmation atomically, with the confirming customer principal retained privately. A generic response remains a response. It does not become a typed confirmation even when its words express agreement. A different authorised recipient of the same reviewed link does not inherit the confirming person's identity.

The two metadata tables are append-only, have RLS enabled and grant no direct access to runtime or authentication roles. Narrow functions enforce the original staff/customer boundaries. Request creation and confirmation share the existing corridor and commercial-mission locks so stale scope cannot win against a concurrent requirement or route revision. Exact retries are idempotent; changed commands conflict. After waits and event insertion, wall-clock source/link expiry and actual customer or staff authority are checked again. The original delivery event, audit and outbox mechanisms retain identifiers without copying the specification into event payloads. Confirmations preserve an explicit customer declaration, not independent technical verification.

A later requirement revision does not rewrite an earlier confirmation. The previous request becomes non-actionable and a newly reviewed publication must disclose the new scope. Customers can use the existing delivery question to request changes; further rounds use existing questions, requirement revisions and reviewed publications. Closing or cancelling a question, removing a saved report, revoking its link or publication, withdrawing access or expiring the source denies new confirmation. No purchase, order, contract, invoicing, collection, payment, outreach or AI authority follows from confirmation.

Installation is separately optional through the existing protected customer-module workflow using `field_modules_action=specification_confirmation` (or `both`), with `apply=yes` and exact-source checks. The installer first installs the existing real-use helper contracts without enabling real use. The new application switch, `CORRIDRA_CUSTOMER_SPECIFICATION_CONFIRMATION_ENABLED`, defaults off and requires the saved-report/workspace/delivery gates. Signed-in real reports retain their existing independent owner switch. No production installation or activation is authorised by source acceptance.

Rollback disables the application switch or deploys compatible source. Retain additive metadata, customer declarations, migration receipts and event history. This change does not make Corridra a buyer's purchasing authority and does not claim machinery safety, legal review or commercial readiness.
