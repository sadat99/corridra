# ADR-018: Controlled introductions and meeting truth

Status: Part 06 implementation; validation and release evidence are recorded separately.

The complete requirement baseline is mapped in [the Part 06 scope](../implementation/part-06-scope.md). Existing tenant, purpose, classification, country, MFA and relationship visibility rules continue to apply. The runtime remains synthetic. Real email, customer contacts and legal approval are not inferred from an operator's synthetic policy approval.

Communication policy and templates are immutable approved versions. Owner/admin approval requires fresh MFA. Each introduction records the exact versions, human sender, recipient contact, target, purpose, approved minimal presentation and expiry. A current jurisdiction/channel policy, current relationship/contact/source, active mission and opt-out checks are required at queueing and dispatch. Synthetic delivery has no external email transport; manual contact can be recorded with the same policy checks. An email adapter must receive separately evidenced permission, reviewed policy, sender-domain readiness and an idempotent provider transport before activation.

Buyer links use 256-bit HMAC capabilities derived from an immutable command identity and the existing server secret; only SHA-256 digests enter PostgreSQL. This permits an authenticated original sender to recover the same link after a lost response without retaining plaintext tokens. Links use a URL fragment and POST bodies, never server URL parameters. The generic GET/HEAD page cannot read private data or record decisions. The buyer read capability returns only the approved introduction. Decisions serialize under the link row lock. A duplicate of the same decision returns the original outcome; changed replay is rejected. Expiry, revocation and opt-out take precedence over replay. Further information can be supplied through a new reviewed introduction, rather than silently reusing a consumed decision.

Anonymous response and worker capabilities are narrow SECURITY DEFINER functions with fixed search paths. They cannot select a tenant, impersonate a human session or write unrelated records. Events identify a provisioned service principal as capability executor, with the introduction and response identifiers retaining buyer provenance. The existing intake service principal is reused only for synthetic tenant capability execution; no additional privileged runtime role is introduced. Public reads and decisions use shared PostgreSQL budgets and exact-origin POST checks.

Meeting commands preserve the canonical vocabulary and enforce both application and SQL transitions. Acceptance records either the exact Interested buyer response or an explicit human observation. Participants, approved brief, reason and owned next action accompany proposals; scheduling uses an absolute timestamp, IANA timezone and matching local wall time. Invalid DST gaps and incompatible offsets are rejected. Ambiguous wall times require an explicit offset. Held and no-show outcomes require the scheduled time to have arrived; a held outcome atomically creates a follow-up owner and deadline. Outcomes remain operator observations, not independent verification or sales. Rescheduling retains the earlier schedule in immutable command history.

Mission commands extend TARGETING to OUTREACH to MEETINGS to FOLLOW_UP, with prerequisite records and hold/resume/cancel. Commercial progression remains Part 07. Paused/cancelled missions block new contact, buyer decisions and scheduling; decline/cancel can close already proposed meetings.

Delivery continues from the transactional outbox through an adapter to Vercel Workflow. PostgreSQL checkpoints own leases, stable effect identity, bounded retry, suppression and dead-letter triage; duplicate workflow starts cannot duplicate the effect. Workflow arguments contain identifiers only. Steps derive a separate job capability and use restricted connections; no session or buyer token is persisted in orchestration inputs. Database receipts demonstrate the synthetic channel. Real providers must honour the same stable idempotency key, including recovery after an ambiguous acknowledgement. Rolling back a deployment never authorizes a resend. Operators can stop new introductions/dispatch, revoke links and inspect/retry failed work without deleting history.

Workflow 5.2.0 bundled documentation is the implementation reference: Next.js `withWorkflow`, identifier-only `start`, Node-dependent step functions and durable `sleep`. Local and deployment execution are verified separately. Actual provider regional/data terms and readiness remain release prerequisites for real contact.
