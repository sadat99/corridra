# ADR-052: Canonical organisation linking with evidence and protected staff review

Status: bounded implementation, synthetic only, default off (`CORRIDRA_CUSTOMER_ORGANISATION_LINKS_ENABLED`). V3-06-002 and V3-06-011 stay PARTIAL for the whole product.

## Context

ADR-044 gave every workspace a private, self-reported company profile and left `organisationId` null, because `app.organisation` is the globally readable canonical catalogue and anything a customer typed there would become visible across tenants and could be merged by name. The missing bridge is a rights-safe way to say "this workspace's company IS that canonical organisation", decided by staff from evidence, without customer input ever writing to or leaking across the catalogue.

## Audit (what already exists and is reused)

- **Catalogue.** `app.organisation(name, country)` is readable by the runtime role with no row security, and its only creation path is `app.ingest_public_organisation`, which needs a staff member, a PUBLIC `public_record` source in the staff tenant and a current `app.public_identifier` (domain, address, identifier). Searching exists only for staff (`organisation_search_idx`, public identifiers behind staff row security). The approved customer company view (ADR-038) deliberately returns tenant-specific digests and no raw organisation id.
- **Staff identity and roles.** Staff are `identity.principal` members of `app.membership` with the roles owner, admin, operator, reviewer and viewer. The existing `trust.verify` permission (owner, admin, reviewer plus a fresh authenticator check) already guards source, claim and evidence verification, and `app.intake_destination` names the one tenant that receives customer-originated work. The operator console already carries on-demand panels under `/api/workspace/*` (account delivery, decision disclosures). The research claim, evidence and verification tables are tenant-scoped, file based and need a scanned upload, so they are not reused for customer claims.
- **Customer side.** Workspace roles come from `customer_private.organisation_profile_role` (owner and admin write, member reads, revoked or disabled reads as none; ADR-051 made invited admins writers). Idempotent commands, the workspace lock, the event chain, session proof expiry and the `CustomerSessionBoundary` service pattern come from ADR-032, ADR-044 and ADR-051.

Nothing here replaces any of that. The module only adds tables, functions, one customer route, one staff route and two screens.

## Decision

An optional module installed by `migrateCustomerOrganisationLinks`. It first installs the profile and member-role modules. All its tables are in `customer_private` with row security on, no grant to the runtime or auth logins, and `app.reject_rewrite()` on every one. Access is only through SECURITY DEFINER functions.

- **Claims.** A workspace owner or admin files one claim: the workspace's company is an existing catalogue organisation (`EXISTING`, named by id) or a proposed new one (`PROPOSED_NEW`). The claim snapshots the profile revision it is about (a foreign key to the immutable revision) and stores normalised matching keys computed in SQL. At most one claim per workspace is open at a time (checked under the workspace lock and again by a trigger). Filing names the profile version it saw; a changed profile is refused.
- **Evidence.** Up to eight text items per claim, each a typed statement (registration, website, trade reference, authorisation), `Synthetic ` text and an optional reserved-host URL. Items are appended with a version check while the claim is open. There are no files or uploads.
- **Immutable history.** Every state change is an appended `organisation_link_event` row (filed, evidence added, evidence requested, creation approved, approved, rejected, withdrawn, link ended). A trigger allows only the legal transitions. Command receipts are appended, so an exact retry returns the original answer and the same command id with other content conflicts.
- **The link ledger.** An approved link is a numbered, append-only row per workspace (`linked`, `unlinked`, `linked`, ...). A trigger forces alternation, so at most one link is active. A newer approval supersedes the old link by appending an `unlinked` row and a `link_ended` event on the old claim. Staff can also end a link with a reason. Nothing is deleted or rewritten.
- **Customer search.** A writer with a saved profile can search by name, at least three letters, ten rows at most, same country as the profile, and only the public catalogue: organisations with a current public-record identity. The result is name and country (plus the id needed to file). Never the raw table, identifiers, domains, addresses, tenants or claims. The route applies the existing request budget.
- **Deduplication.** Matching is deterministic and computed in SQL: a normalised legal name (lower case, no leading "synthetic", no punctuation, no legal-form words, no spaces) plus country, and the website host (www removed) against current public identifiers. It runs across canonical organisations and across other workspaces' open or actively linked claims. Staff see the candidates, with how many other workspaces are already linked. A customer never sees a candidate, a count, another workspace or another claim, and a match is never disclosed to another tenant.
- **Two workspaces, one organisation.** Staff decide explicitly. Approving a link to an organisation another workspace already holds is refused unless the reviewer confirms a shared link. Then both workspaces are linked to one canonical identity as separate contacts; they stay separate private tenants and neither learns of the other. Otherwise the reviewer rejects the second request with a reason. Approvals on one organisation are serialised by an advisory lock, so two reviewers cannot both slip past the check.
- **Staff review.** Existing staff authority only: an owner, admin or reviewer of the enabled intake tenant with a fresh authenticator check, enforced by `withTenant(..., 'trust.verify')` in the service and again inside SQL (role, intake tenant, synthetic tenant, fresh MFA). Operators, viewers, other tenants and stale checks are denied. Decisions are approve (link to a catalogue organisation), approve for creation, request more evidence, reject and revoke, each with a mandatory reason and an optional internal note.
- **Creation.** A customer claim is never written into the catalogue. The only creation path, `app.ingest_public_organisation`, needs a public-record source that a customer statement cannot be, so a proposed new organisation can be recorded as **approved for creation** (a staff to-do state). Staff then create the record in the existing research screens and return to link it; the new organisation appears in the claim's candidates. The module never calls the creation path itself.
- **What the customer sees.** Status next to the profile and in the workspace list: none, pending (waiting for review, or approved for creation), needs more evidence, approved with the canonical organisation name, or rejected. Owners and admins also see their evidence, the history and the staff reason text meant for them. Members see only the status, the approved company name and the label. Internal staff notes and staff identities are never returned to a customer.
- **What verification means.** An approved link is labelled "Company link reviewed by Corridra staff from the evidence supplied (synthetic test)". It does not verify the person, does not make the profile revision verified, and exposes no private profile content to another tenant. ADR-044 behaviour is unchanged: the profile view still says self-reported, unverified and `organisationId` null, and later profile edits are reported as "changed since the link was reviewed" without touching the link.
- **Events.** One domain event, audit and outbox chain per real change (`customer.organisation_link.*`), carrying ids, versions and state only. Customer changes are attributed to the service executor with the customer as initiator; staff decisions are attributed to the staff principal.

## Synthetic-only boundary

Free text from customers must begin with `Synthetic ` and URLs must use reserved example, test or invalid hosts. The module moves no money, sends no email or outreach, stores no file or document and reads no real registry. The flag needs the workspace flag, a synthetic environment and a deployment permitted by the explicit production opt-in in [ADR049](0049-synthetic-production-opt-in-and-open-admission.md). Gates D01 to D06 and D08 stay closed. Scanning, legal and security hardening remain deferred by owner decision.

## Blast radius and rollback

New objects only. A populated-database test proves no existing function, table, policy, ACL or row changes and that `app.organisation` and the profile revisions are unchanged by every flow. Roll back by unsetting the flag; the additive tables and history are retained. Links already approved are not shown while the flag is off.

## Not included

File evidence, real registry lookups, a customer-initiated unlink (staff revoke, or a newer request that supersedes), automatic creation of canonical organisations, email notice of a decision (outreach is gated), per-mission profile snapshots and sharing a linked identity with counterparties.

## Required acceptance

Populated install preservation, repeat install and history-mismatch refusal; direct SQL denial for the runtime and auth logins on every private table and helper; owner and admin write, member read, outsider, revoked and disabled denial; forged workspace and role denial; expired proof; stale versions; exact retries and conflicting command ids; races (two filings, two reviewers on one organisation); immutability of all history tables; event content privacy; synthetic-only validation; staff role, intake tenant and fresh MFA checks; customer non-disclosure of candidates; browser protocol tests with keyboard and axe at 320, 390, 768 and 1440.
