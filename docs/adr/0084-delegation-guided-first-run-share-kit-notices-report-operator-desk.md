# ADR-084: Delegation: guided first run, share kit, notices, published report, operator desk

Status: Proposed, reviews clean, awaiting owner merge approval. Design only, 13 November 2026. Nothing in this ADR is implemented, tested, deployed, enabled or live. Every slice ships locked and off, installs and every closed control stay separate owner steps, and no requirement becomes VERIFIED.

Authority: the owner's 13 November 2026 request for a Delegation module so good that organisers "come back ... and bring others" (the Disney standard) with visual approval, and the owner's "approve all" of the four delegation decisions D1 to D4 proposed by lane D1 (artifact `VpCDnKJSVsJva5r5wDKkWm`), both relayed to this lane by Orchestrator 9 and not verified first hand by this lane (the Guardian verifies the words). V3 contract section 2 Product 3 steps 1 to 13 and section 6 (self-service delegation, participant onboarding, templates). Product vision 2.1 section 13 (institutional loop, no spam, no recruitment commissions) and section 20 (not a travel agency, not an outreach engine). Look: UI/UX.v3 (`docs/agents/ui-direction.md`) wins; the artifact visuals are the approved target, read through it.

Not decided here: the install of any migration, any switch value, Bangla and Chinese words (native review gate), online fee collection (closed, no provider, no legal review), real outreach, and D01 to D06 and D08.

## Context

An organiser can already create a programme, publish a reviewed public page, take applications, invite, register, set terms, places and fees, coordinate tasks, record attendance and read a private results report (ADR-043, 047, 075, 080). Lane D1 found, from file evidence and fresh screenshots on main `6cb0abc` (sample data), that the parts exist but the organiser journey does not carry a person from "I want to run a delegation" to "I shared a link and people are applying":

- The public entry sends organisers to the wrong page. `apps/web/app/trade-missions/organise-entry.tsx:46` links to `/account/delegations`, whose page (`apps/web/app/account/delegations/page.tsx`, title "Delegation registrations") is the participant page. The organiser route is `/account/delegations/organise` (`organise/page.tsx`, `WorkspaceChooser kind="programmes"`).
- Create is a form, not a guided run. Nothing shows what the organiser is building.
- A published page can be copied or opened in WhatsApp or Facebook (`share-row.tsx:5-50`), with no preview image, QR, printable flyer or calendar file. Pages are not indexed (ADR-080 decision 10, owner 11 Nov), so the forward is the whole distribution.
- Applications and decisions produce no notice. ADR-080 line 83: "Not built: it is outbound mail and stays behind the existing mail gates."
- The room overview is 1,525 px tall at 1440 with many "Not measured yet" tiles, against the one-screen desktop budget.
- There is no publishable or printable results report; the signed-in report is for the organiser alone.
- Corridra staff can read applications (ADR-080 amendment) but have no programme-level desk.

The module has no real organiser or delegate behind it (ADR-080 follow-through, main risk). A code change can make the journey possible and testable; it cannot make it proven.

## Decision

Build eight slices, S0 to S7, in the order below (the numbered decisions that follow map to S0, S1, S2, S5, S6, S3 and S4, then S7), each a small reviewable PR behind its own switch, reusing what exists. The reuse table is the main constraint: no new programme backend, no new identity, no new send path.

1. **One guided first run, ending on Publish.** One question per step, a live preview of the public page as the organiser types, a template choice on step one, "I am not sure yet" for dates, a draft kept in the browser session, and Publish as the last step. It composes the existing create command, the existing page editor and the existing templates. No field, id or payload changes.
2. **A share kit made only of published words.** A per-programme preview image, a QR code, a printable flyer, a calendar file and a quiet "Page made with Corridra Programmes" line. No tracking, no visitor logging, nothing sent by Corridra (ADR-080 decisions 4, 8 and 10 stay).
3. **Transactional notices, off by default, only to the account the event concerns.** An applicant is told of a decision on their own application; an organiser is told of new applications at most once an hour. Built on Notifications V2.
4. **A published results report.** An organiser-published, immutable, aggregate snapshot with trust labels, a minimum of five shared items per section, `noindex`, take-down and a PDF, off until the organiser publishes it, plus Create Next Edition.
5. **An Operator Delegation Desk.** Read-only metadata and counts for Corridra staff, owner or admin, fresh authenticator.
6. **Presentation slices** for the people board, the money view and the participant home over reads that already exist.
7. **A buying-trip template** after the ADR-082 build, so a delegation can be run as a sourcing trip without a second engine.

### S0 detail

- The link fix is the first commit and has its own test, red on main: a click on the entry action from the public trade missions page must land on `/account/delegations/organise`, not the participant page. The test also covers a signed-out visitor (the sign-in return path) and a participant-only account (the chooser's own behaviour), and states that the route `/account/delegations` is unchanged.
- First run: three steps of one to three fields (UI/UX.v3 form rule): (1) name and destination, with the template chooser; (2) dates and who it is for; (3) fee line and places, then Publish. Each step keeps its draft in the browser session, exactly as the existing editor does (`programme-page.tsx:248,260,327`, `window.sessionStorage`); nothing is stored on the server before Publish. A server-side draft would be a new command with a migration and an installer route, and is not part of this ADR (owner option). The preview is the existing `ProgrammePageView` in its existing `preview` mode (`programme-page-view.tsx:168` already branches on `preview`) fed the draft words. "Publish" is the existing publish command with the existing 180-day closing rule. Nothing is public before that press.
- A template adds tasks and planned costs and never people, fees or payments (the existing template rule).
- Overview: the next real decision first (for example "Answer 3 applications"), counts only and out of a total, "Not measured yet" kept only for values that truly are unknown, the vertical stage timeline kept on desktop (owner lock 12 Nov), one screen on desktop and 1.5 to 2 on a phone, measured on a production build. All new action labels are Title Case, written in the text and checked by `tests/browser/title-case-actions.spec.ts` (for example "Answer 3 Applications" when rendered as an action).

### S1 detail

- Preview image: Next.js `opengraph-image.tsx` for `/delegations/[address]`, built only from the published title, purpose, destination and dates, and the word "Sample" in a sample workspace. No private programme read. Unknown or closed-long pages answer the same single value as the page does (ADR-080 decision 4).
- QR: generated on our server from the page address, never by an external service (an external service would receive every address). Adding a dependency is a decision for the S1 builder and reviewers: a small pinned library in `apps/web` only, or an in-repo encoder; either way no network call.
- Flyer: a print view (title, destination, dates, who it is for, QR, the "stated by the organiser" sentence). It uses the published words only; it prints the fee line only as published, or omits it, and never converts or totals.
- Calendar: an `.ics` file. The page's `dates` field is free text (`packages/auth/src/customer-programme-publication.ts:32`, `0001:88`, 2 to 160 characters, for example "If the dates are not fixed yet, say so"), so a calendar file cannot be made from it. Decision: add optional structured `starts_on` and `ends_on` as a **sidecar table keyed to the page version**, not a new key in the copy. The key list in `programme_publication_copy_valid` (`0001:75-81`) is closed and enforced on immutable rows; replacing that function would be a hash-guarded replacement of an installed object, which this ADR rejects. A new read function is called only after the existing reader returned a readable page, takes the address and version, and returns the dates or nothing, so it adds no way to tell unknown states apart. Without structured dates the calendar action is not shown (a control without a working backend is not shipped).
- Attribution: one quiet line "Page made with Corridra Programmes" with a link to the organiser entry. No tracker, no referral code, no cookie, no count of who clicked (D1: no tracking). It is a link, not an invitation sent to anyone.

### S2 detail

- Applicant on decision: when an organiser records a decision on an application (events already exist: `customer.programme_application.decided`), the applicant's own account gets an inbox item and, if their email choice allows, an email. The email states the decision and the reason the applicant already reads in the account page (ADR-080 decision 6: declined always carries a reason). It contains no organiser private data.
- Organiser: at most one email an hour per organiser, which says how many applications are waiting and links to the board. **No scheduler exists** (`vercel.json` has no crons and the web app has no cron route), so a timed digest would need new infrastructure. This ADR therefore builds coalescing instead of a timer: the first new application in an hour sends one notice, later ones in that hour only raise the in-app count and are included in the next notice. The in-app count is the source of truth; the email is a nudge and may not reflect later applications. A true timed digest needs a cron and is left as an owner option.
- The recipient is the account the event concerns: the applicant for a decision, the workspace owner or admin for new applications. Never a third address. No notice goes to an address the person did not give to Corridra, none to a third party, no marketing, no reminder chain. Notifications V2 stays off by default (`notificationsOn`, `CORRIDRA_NOTIFICATIONS_V2`); the mission mail gates and `notificationEmailReady` are unchanged. A failed notice never breaks the action that caused it (the module's own rule).
- **Recorder function (new, publication module `0004`, which depends on commercial readiness).** ADR-080 decision 5 lets the organiser see an applicant's name and statement and nothing else of the person, and the applicant never sees the organisers' accounts. A notice therefore cannot be written by browser or route code that holds both sides' ids and emails. `app.inbox_record` only checks that the writer is signed in and takes the recipient as an argument (`commercial-readiness-migrations/0001_inbox_and_links.sql:37-48`), so the recipient is resolved inside a `SECURITY DEFINER` recorder, as other producers do (`app.record_reply_posted`, `0009_reply_posted_notification.sql:24-27`). The recorder runs in the decision or application transaction, resolves the applicant from the application row (decision notice) or the workspace owner and admin set (new-application notice), inserts the inbox row directly into `app.inbox_notification` with an `event_key` (the `event_key` column is added by `0002_request_received.sql:3`; the shape is the `ON CONFLICT ... WHERE event_key IS NOT NULL` insert of `0009_reply_posted_notification.sql:23-26`, because `app.inbox_record` has no event key parameter), and returns to server code only what the email send needs, never to the browser and never to the other party. Tests: the organiser session cannot read the applicant's account id or email, the applicant session cannot read any organiser's, and a recorder call by anyone else is refused.
- **Coalescing state.** The last-sent time for the organiser notice is read from the organiser's own inbox row (its `event_key` and `created_at`), checked inside the recorder under a row or advisory lock. A race may at worst send two emails.
- **Base run.** Readiness migrations apply in the installer base run on every base install, so `0013` reaches the database at the owner's next base install whether or not S2 is switched on, and a guard failure aborts that whole run. The CHECK is inline and unnamed in `0001:14`, so the migration finds it by its definition, not by a name.
- Event and inbox payloads carry ids and the kind only. Names, statements, decision notes and reasons never enter events or inbox rows (ADR-080 decision 8); email-only lines are not stored, as in `notify.ts:92-113`.

### S5 detail

- What it is: a snapshot the organiser publishes on purpose, read by anyone with the link. It is not a live read of the private programme.
- Sources and labels, one per figure: **Organiser recorded** (capacity, attendance, tasks; ADR-047 `ORGANISER_RECORDED`); **Participant reported** (satisfaction and outcomes the participant chose to share; `PARTICIPANT_REPORTED`); **Counted from Corridra records** (scheduled and qualified-held meeting counts, only from participants who permitted counts; ADR-075 decision 5). A participant-reported outcome is never written as "qualified".
- Minimum five: a section shows its figure only when at least five shared items stand behind it; below five it says "Fewer than five shared" and shows no number. The rule is applied when the snapshot is made, from complete server-side data, never in the browser. A suppressed row shows no number and no total or complement that would reveal it. Organiser-recorded aggregates are organiser statements and are labelled so; the five rule governs participant-reported and counted figures. A new snapshot applies the same rule to its own figures and shows no per-item change from the previous one.
- No money: fees, prices, payment status, organiser economics and trade values are not in the snapshot (the four money domains stay separate, ADR-060 and ADR-061; organiser economics stay private, ADR-046). No names, companies, contacts, notes or comments appear; no participant name is ever shown beside a comment.
- Storage: an immutable snapshot row, a version number, a closing time of at most 180 days (the page rule), an unguessable 64 hex token (the `delivery.ts:68` shape) and a take-down record. Taking down withdraws the latest snapshot; publishing again makes a new snapshot at the same address. The anonymous read answers one value for unknown, taken down, expired and switch off, writes nothing and records nothing about the visitor. `noindex, nofollow` in markup and header, as for the page. The report is served under `/delegations/<address>/results/<token>` (inside the existing `/delegations/:path*` noindex rule, `next.config.ts:50-52`). `apps/web/next.config.ts` is added to the S1 and S5 file lists with a `Referrer-Policy: no-referrer` header rule for the flyer, calendar and report routes (the global `/:path*` rule at `next.config.ts:38-47` sets `strict-origin-when-cross-origin`; the new rules must be ordered so the response carries `no-referrer`, and the header test proves it on the built app). These routes send `Referrer-Policy: no-referrer` and load no third-party resource, so the token and address cannot leak by referrer.
- PDF: a new function beside `reportPdf` in `packages/delivery/src/report.ts` that accepts only the stored snapshot and renders it with pdfkit. It cannot read the live programme.
- The organiser sees a preview of exactly what will be public and presses Publish; the confirmation states that the words are stated by the organiser and counted as labelled, and that Corridra has not verified them.
- Create Next Edition: saves a template from this programme and opens the guided first run on it, through the existing template and series code. It never copies people, fees, payments, applications or the report.

### S6 detail

- One read function `customer.staff_programme_desk(after_id, page_size)` modelled on `customer.staff_programme_applications` (ADR-080 amendment): owner or admin of the staff workspace in the session, a fresh authenticator check, a live session; operator, reviewer and viewer refused. It needs a permission row (proposed `programme.desk.read`) in the existing matrix; that is a change to permission code and is named in the blast radius. Its tests prove that operator, reviewer, viewer and non-staff sessions are refused and that the existing permission matrix snapshot is only extended by that one row.
- It returns metadata and counts only per programme: page state and version, closing time, applications by status, registrations and places, whether a report is published. No names, statements, emails, labels, prices, notes or ids of people. It writes nothing, including no audit row, as the comparable queue does (ADR-078), and no button changes anything.
- Staff of a sample workspace see sample workspaces; staff of a real workspace see real ones while real use is open.

### S7 detail

- A "Buying trip" template for the existing templates path: planned factory visits and host meetings as `PLANNED` page activities and as coordination tasks.
- A host or factory named on a page is the organiser's own statement. It is **not** linked to a company record, verified or matched by this ADR. Staff may nominate it as an ADR-082 candidate with role SUPPLIER through the ADR-082 flow ("nomination is not identity", `0082:90`); an organiser cannot create a candidate, and a nomination does not make an organisation, a verification or a supplier claim.
- The BD to China defaults come from ADR-083's optional `sourcing` profile (decision 1), as TESTING data. No country fork. Not started until ADR-082 and ADR-083 S1 are built.

## 3. Data

- Additive migrations only. Builds never migrate. Each file is installed only by the protected installer after the owner's environment approval, never by production SQL (AGENTS.md; ledger "No direct production database access").
- New objects (all in existing optional modules, none replacing an installed function or policy, so no existing function fingerprint changes; S2 is the one exception and replaces one installed CHECK): publication `0003` a page-schedule sidecar (S1); `0004` the S2 notice recorder function (below); `0005` results snapshot, take-down and read functions (S5); `0006` desk read function (S6); commercial readiness `0013` an additive replacement of the type list for new types (S2). The type list is a CHECK on `app.inbox_notification` (`0001_inbox_and_links.sql:14`); replacing a CHECK is a change to an installed object, so S2 does not install until its migration carries a hash guard on the live CHECK definition and a test proves that drift refuses the install, as ADR-083 decision 1 requires for its guard. If the installer base run cannot carry that guard, S2 stops and returns to the owner.
- Each new table: row security on, no grant to the runtime role, immutable rows, reads only through functions granted to the runtime role, exactly as ADR-080.
- Each module test compares, before and after install, every existing function definition with grants and owner, every policy, table grants, row-security flags, constraints and a digest of existing rows (the ADR-080 test shape), and finds no difference except the one named replacement (the S2 CHECK).

## 4. Blast radius, rollback and privacy
