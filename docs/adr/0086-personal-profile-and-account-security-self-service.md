# ADR-086: Personal profile and account security self-service

Status: Accepted by the owner, 17 November 2026. Built in unit CI-U1 (personal details module, name route, My Profile panel). The database module is tested on PostgreSQL 16 and is NOT installed anywhere; the Guardian runs the install (`field_modules_action = personal_profile`) after merge. Every account security control ships switched off: `apps/web/lib/account-security-capabilities.ts` holds `updateName`, `changePassword`, `listSessions` and `revokeSession` as `false` with an empty probe record until a preview probe proves each one.

Authority: owner decisions of 17 November 2026, first hand to Guardian 13 (`session_0187kU9tJQfEwdfzRzpPJJDu`), recorded verbatim. Mandate: "Commercial Identity and Complete Account Control". Answer "Approve both (Recommended)" to: (1) a small new private versioned table for personal details installed through the normal installer, (2) server-only actions for change name, change password and own sessions after a preview test; no AI in introductions; sharing stays private preview. Later the same day: "ensure propfile allows user's profile picture sophisticated ways." The picture is a separate next unit (CI-U1P) built on this module. ADR-020 (identity separation), ADR-033 (as amended 11 November 2026), ADR-044 and the crud standard (U-01, U-02, D-02, A-02, A-03) apply unchanged.

## Context

A signed-in customer could see their verified email and nothing else about themselves. The account page had no place for the few facts people expect to keep about themselves (what they do, where they work from, what they care about, how to reach them), and no server path to change the name the sign-in provider holds. The sign-in provider's own browser endpoints stay behind the existing proxy allowlist; widening it would hand account changes to the browser without Corridra's checks or record.

## Decision

1. **Optional, self-reported, append-only.** A new module `packages/db/customer-personal-profile-migrations/0001_personal_profile.sql` adds `customer_private.personal_profile_revision(id, principal_id, version, details jsonb, created_at)` and `customer_private.personal_profile_command(actor_id, command_id PK, revision_id, request)`. Row security is on, every grant is revoked from the runtime and auth logins, and a guard rejects every update and delete (decision 6 names the one exception). Each save is a new revision with an expected version and one command id per decision: a repeat of the same command replays the first answer, the same command with another payload (or by another person) is refused.
2. **Only these keys, none mandatory.** Lengths count characters (code points), the same on the server and in the database, and no text may hold a control character (C0 or C1) or a line or paragraph separator. `title` (1 to 80 trimmed characters, or null); `baseCountry` (a code in `app.country`, or null); `interests` (at most 10, each 2 to 60 characters, unique ignoring case); `contactMethod` (`EMAIL`, `IN_APP` or `NO_PREFERENCE`; there is no phone); `initialsPreference` (`NAME_INITIALS`, `EMAIL_INITIALS` or `NONE`). No completion percentage, no score and nothing verified: every read says `provenance: SELF_REPORTED, verified: false`, and the screen says so in words.
3. **Self only.** `customer.personal_profile_view()`, `customer.personal_profile_command(command, expected, input)` and `customer.personal_profile_history(before, size)` take the person from the signed-in session (`customer.actor_id()`), never from an argument. Another principal cannot name, read or replay anyone else's details. A closed account (undo window or final) and an account with an erasure request that was not declined are refused (42501). Invalid input, a stale version ("Profile changed; reload before saving") and a conflicting replay are 23514.
4. **Events carry ids only.** `customer.personal_profile.revised` (revision id, version) and `customer.account_security.changed` (a kind), each with its audit, outbox and delivery row in the same transaction, never a title, an interest, a name or an email. The event workspace is `customer_private.account_chain_tenant(actor)` from the account lifecycle module: the person's pinned chain workspace, else their earliest workspace, which is then pinned. A person with no workspace is refused before anything is written, with the words "Personal details need a workspace on this account. Create or join a workspace first." The module therefore refuses to install without the account lifecycle module and names that step.
5. **Account security only through server routes.** Name, password and the person's own sessions change only through Corridra server routes that call the pinned SDK server methods (`updateUser({name})` for the name; later units for the others). The auth proxy allowlist in `app/api/auth/[...all]` stays exactly as it is. Each change is recorded by `customer.account_security_note(command, kind, request)` with kinds `name_changed`, `password_changed`, `session_revoked`, `other_sessions_revoked`, replayed by person and command; `request` is a keyed one-way hash of what was asked (for a name, an HMAC with the server secret), so the same command with another name is refused (409) and the name is never stored. Before the provider is asked, the read-only preflight `customer.account_security_noted(command, request)` applies the account refusals, the workspace refusal (without pinning the chain workspace) and the replay check, under the same per-person locks as every other caller. The hourly budget key is an HMAC of the issuer and subject with the server secret. The route answers 404 for a control that is off before it reads the request, and the guard pins the same issuer as the session boundary (`CORRIDRA_CUSTOMER_ISSUER`, else `NEON_AUTH_BASE_URL`). Both routes are registered in the private header rules of `apps/web/next.config.ts` (no-store, no-referrer). A record that fails after the provider made the change answers success with a logged missing-audit code, never a 500 for a change that happened. Each control ships only when a constant set from a preview probe (revision, time, report hash) says it is proven; until then the route answers 404 and the screen hides it. Other devices are signed out by listing them and revoking each one: `revokeOtherSessions` and `revokeSessions` are banned. The name needs no recent sign-in and never uses the operator `STEP_UP_REQUIRED`.
6. **Erasure.** Staff only, `customer.personal_profile_remove_words(command, erasure_request)`, modelled on `programme_words_remove`: `staff_privacy_actor`, `erasure_in_scope`, the lifecycle and profile advisory locks, an erasure request in progress or completed, a cutoff, one no-words record row in `customer_private.personal_profile_erasure` per item. The title becomes "Removed at request" and the interests become empty in every revision and replay record; the guard allows exactly that change for an item with a record row and nothing else. `baseCountry`, `contactMethod` and `initialsPreference` survive erasure by design: they are fixed codes chosen from a list, not the person's own words. There is no application path that runs the removal; staff run it by the procedure in `docs/runbooks/neon-auth-accounts.md` ("Staff erasure: removing a person's words"), alongside `customer.programme_words_remove`.
7. **Out of scope.** No AI anywhere in introductions or profiles. No customer MFA or passkeys; operator MFA stays separate. Sharing stays private preview. The profile picture comes in a later unit (CI-U1P) on private object storage, in its own table keyed by principal: the validator here accepts no picture key, so picture data never enters these rows. Built as ADR-088 (CI-U1P).

## Blast radius

- New: four tables, seven private functions and six customer functions (including `account_security_noted`, the name route's preflight) in one additive file; one installer (`migrateCustomerPersonalProfiles`, registry `customer_personal_profile_migrations`) reached only by `field_modules_action = personal_profile`, never by a base run. No workflow input is added (the count stays 24).
- Application: `packages/auth/src/customer-personal-profiles.ts`; `/api/customer-personal-profile` (GET view or history, POST save; module missing answers 503 `module_unavailable`); `/api/account/name` (POST, server only); `apps/web/lib/account-provider-guard.ts`; `apps/web/lib/account-security-capabilities.ts`; the My Profile panel on the account Profile tab.
- Existing objects: no table, policy, grant, trigger or function is changed or replaced. The auth proxy, `lib/i18n/messages.ts` and `customer-optional-refresh.ts` are untouched.

## Rollback

Revert the application code; the tables stay (additive, no down migration). A name changed at the provider is not reverted by a rollback: the person renames again. Setting `updateName` back to `false` hides the name edit and makes the route answer 404.
