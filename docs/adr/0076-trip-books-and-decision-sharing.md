# ADR-076: Trip view, scoped books and decision sharing

Status: Trip view, status link, Books and decision card ACCEPTED (default off); the decision card's database module, service and routes are built behind the default-off switch and its screens are not yet built. Accepted 3 November 2026 and built behind default-off switches: the Trip view (CORRIDRA_UX_TRIP), the emailed status link in its narrower signed-in form (CORRIDRA_STATUS_LINK, item 5), and the Trip Book and Supplier Book (CORRIDRA_UX_BOOKS, items 1-3 and 6; the backend is merged in PR 257 as d1ddbcd and the download panel on the saved mission page (E2b) is merged in PR 258 as 4f2870e; installing the books database module and enabling the switch are owner-only). The decision card (CORRIDRA_SHARE_CARD, item 4) is ACCEPTED on 3 November 2026, under the same owner direction to take over Batch E and ADR-076 with full pre-approval including the necessary migration. Its database module is merged (PR 261), and its service and routes are built behind the switch (E3b step 3: the owner API /api/customer-decision-cards and the public read /api/decision-card). Its screens (the owner panel and the public /decision-card page, with the shared page chrome hiding) are NOT YET BUILT and follow in a later pull request. The module is NOT installed in production: the installation needs the owner's protected install run. Its field map and seven-day limit are the owner-approved defaults. The switch is off unless exactly 'true'. Building behind the switch is covered by this acceptance; enabling is not: enabling is an owner action that needs the recorded privacy review and the installed module. The books field map is accepted as the proposed default, under the owner's direction on 3 November 2026 to take over Batch E and ADR-076 with full pre-approval. Enabling any switch stays an owner action. The books' database module also needs the owner's protected install run.

Scope: Batch E, GAP-034/035/041. This extends ADR022 and ADR070 only as explicitly accepted here; existing identity, MFA, RLS, source revocation, approved publication and real-operation controls remain.

## Reused foundations

The saved commercial report already contains an approved itinerary with label, status, reviewed start/end/timezone/location and a scheduleChanged marker. The Room already composes that same report in Compare and Evidence views. Add Trip as another view with the existing CORRIDRA_UX_TRIP flag; no itinerary service, booking engine, canonical meeting change, schema or broader read permission is needed. A changed schedule suppresses stale appointment details. Existing report proof, refresh, expiry, visibility clearing and identity scope continue to apply.

Trip view (accepted). Trip is a fourth Room lens. It shows only when CORRIDRA_UX_TRIP is exactly 'true' and the Room itself exists (CORRIDRA_UX_ROAD). It renders only the reviewed itinerary block of the saved commercial report. When a schedule has changed, it shows the "The schedule changed" notice and none of the old details; delivery SQL 0016 and the report UI already enforce this, and RESCHEDULE_REQUIRED is treated as a changed schedule. It adds no read, query, schema or export, and shows no price, offer or contact. Switching between lenses does not fetch the report again.

CLIENT_PROGRESS currently forbids export. ADR022 requires explicit reporting/export permission; ADR070 is a proposal with an unset sharing expiry. A new button cannot override these boundaries.

## Disclosure contract (items 1-6 accepted; item 4: database module, service and routes built behind the default-off switch, screens not yet built)

1. Trip Book (ACCEPTED, 3 November 2026, built behind CORRIDRA_UX_BOOKS, default off): a PDF generated on request for the signed-in customer who owns one active saved mission. "Owner/admin" here means that customer: a saved mission has no workspace role, so workspace membership grants nothing, which is narrower than the earlier wording. Fields: the approved mission title, company and objective; per reviewed itinerary item its label and status and, unless the schedule changed or the status is RESCHEDULE_REQUIRED, its start, end, time zone and place. A changed schedule shows a notice only and none of the old details. No contacts, quotations, prices, notes, attachments, private identifiers, participant data, offers or financial values.
2. Supplier Book (ACCEPTED, 3 November 2026, same switch and authority): the mission title as the heading and, for each reviewed shortlist company in a fixed order, its country, fit, rationale, uncertainty, gaps and source-reported verification label. No offers, financial values, contact information, identifiers or unreviewed suppliers.
3. CLIENT_PROGRESS.allowExport stays false and the progress link is untouched; books use a separate purpose. A SQL function builds each book, key by key, from the same reviewed report the customer can already read, through the same ownership, revocation, expiry and retention gates, and copies named fields only. The PDF is rendered from that projection with the existing fonts, size limit and pagination, inside the database transaction before it commits, so a book that cannot be made leaves no record and no event. The PDF is not stored. Each new generation appends one immutable record to the existing saved-mission command ledger (kind, resource, publication, schema version, generation time and the SHA-256 of the projection, no content) and one delivery.book.generated event through the existing audit and outbox writer; the event payload carries no saved-mission id. The digest covers what is disclosed, not the file bytes. The same command id returns the same record with no second record or event; if the source changed, the retry is refused and a new download is needed. At most 30 new generations per customer and mission per hour. The download screen and the file both say that a downloaded file cannot be revoked after it leaves the system.
4. Decision card (ACCEPTED, 3 November 2026; the database module, service and routes are built behind CORRIDRA_SHARE_CARD, default off; the screens are not yet built, and the module is not installed in production). Only the saved-mission holder who is, at that moment, an owner or admin of the workspace that owns the request the report was delivered for can create a card. They explicitly select ONE currently reviewed SELECT, DECLINE or NEED_INFORMATION disclosure and see a preview of the exact fields before anything is created. The fields are the company, the decision, the rationale, the next action, the due date and one provenance label (source kind and claim status), and nothing else: never a quotation, price, contact, file, another decision or the requirement text. The card stores no copy of those fields. It stores only a digest of the previewed fields, and every read re-derives the fields live from the reviewed sources and shows them only while the digest still matches. A changed field, a withdrawn card, an expired card, a lost owner or admin role, lost access to the report, a withdrawn or removed saved report, a revoked request, lost publisher access, a source past its retention end, an unknown or malformed token and a disabled switch all answer one identical 'unknown'. The link carries a 43-character token in the URL fragment of /decision-card. The page sends it in a POST body and removes it from the address bar. The database keeps only the token's SHA-256. The same create command retried returns the same card and the same link. A card works for at most seven days and never beyond the earlier of the delivery link's expiry and the retention end of every source behind the decision. The page is read-only with nothing actionable, and its answers are no-store, no-referrer and noindex. GET and HEAD never disclose. Only the creator sees and withdraws a card; there is no team-wide sharing, and a creator who stops being an owner or admin makes their own cards unknown. At most five cards can be active per saved report. The creator sees the count of opens and the time of the last open; the count means page loads and can include automatic link checks. No visitor data is stored, so no per-open event is written. Cards exist for sample (synthetic) workspaces only: a real workspace always answers 'unknown' until the owner lifts that with the recorded privacy review and decides on the closed D06 and D08 gates, which this decision does not open. A saved report reached without a request assignment has no workspace and cannot create a card. Rollback: unset CORRIDRA_SHARE_CARD, every card answers 'unknown' at once and the additive tables stay inert.
5. Emailed status link (ACCEPTED, 3 November 2026, built behind CORRIDRA_STATUS_LINK, default off). This is narrower than ADR058 and replaces its anonymous 90-day link, which is not adopted. The button in the existing first request email (mission mail "request-received") opens the signed-in Room (/account/rooms/<id>) when CORRIDRA_STATUS_LINK and CORRIDRA_UX_ROAD are both exactly 'true', and the saved request page otherwise. The link grants no authority: a signed-out visitor is sent to sign-in and returned through the ADR067 exact-path allowlist, which applies when CORRIDRA_STATUS_LINK is on as well as when Pulse is on. There is no token, fragment secret, expiry, renewal, new table, retention change or ADR033 amendment. The email carries no request text beyond what mission mail already sends. Anonymous/unlinked requests keep their current receipt behavior. The existing mail transport, queue, deduplication and idempotency key are reused. Building the link does not authorize agent-triggered mail or provider activation, and turning on mission email stays a separate owner step. Rollback: unset CORRIDRA_STATUS_LINK and new emails link to the request page; emails already sent keep the Room URL, which answers not found if the Room is later switched off.
6. Default off: CORRIDRA_UX_BOOKS is a real switch, off unless exactly 'true', and the download route also answers 503 until the books database module is installed. CORRIDRA_SHARE_CARD is a real switch (a flag in the owner switch registry): off unless exactly 'true' ('TRUE' and '1' count as off), and it also needs saved reports and decisions on and the production lock off. Until the card database module is installed, the owner API answers 503 and the public read answers 'unknown'. The owner API answers 503 when the switch is off or the module is not installed. The public read is POST only (GET and HEAD answer 405 with Allow: POST) and answers one identical 200 body, {"state":"unknown"}, for every case that is not an open card, including a switch that is off and a module that is not installed. Its transport checks (origin, content type, a 512-byte body bound) run before the switch check, so the state of the switch cannot be observed from outside. Both routes answer no-store and no-referrer, the public one also noindex, and the public one sets no cookie. The link token is an HMAC-SHA256 of AUTH_SECRET, the issuer, the subject and the command id (43 characters, base64url); only its SHA-256 reaches the database, and the link is returned only while the card state is ACTIVE. Database refusals are mapped by SQLSTATE and message together: 23514 DECISION_CARD_CHANGED to 409 reason CHANGED, 53400 DECISION_CARD_CAP_REACHED to 409 reason CAP_REACHED, 54000 DECISION_CARD_RATE_LIMITED to 429, 42501 to one uniform 403, any other 23514 to 400, and 40P01 and 55P03 to a retryable 503 with Retry-After. Limits: create is limited per verified customer and per client, public reads per client and per token, and withdraw is never limited. The explicit acknowledgement (acknowledged: true) is required on create at the HTTP layer only; the database does not see it. CORRIDRA_STATUS_LINK is as item 5. No real provider calls, booking or payment expansion.

## Consequences

- Books are additive: one SQL function and no table. Rollback is switching CORRIDRA_UX_BOOKS off or reverting the code; the append-only history stays. The install report moves from `customer_book_migrations: not installed` to `1 applied` after the owner-approved protected run; until then the route answers 503 even with the switch on.
- The record is not a file archive: it proves what was disclosed and when (digest and time), and a book cannot be regenerated byte for byte from it.
- A book carries only text the PDF font can show. The three embedded PDF fonts have no Arabic, Thai, Devanagari or emoji glyphs, so a book with such text is refused with an honest 422 (reason UNSUPPORTED_TEXT) and nothing is recorded. Adding a font is a separate owner and asset decision. The PDF output is untagged, so no accessibility claim is made for it.
- The raw country code still shows on the on-screen mission experience view; the Supplier Book prints the country name. The screen is not changed by this decision.
- The decision card is additive: one new migration folder (`customer_decision_card_migrations`) with three tables in the private schema (card, withdrawal, open counter), all immutable or increment-only, no table grant to the runtime or auth roles, and five granted functions. Nothing existing is replaced. The install report moves from `customer_decision_card_migrations: not installed` to `1 applied` after the owner-approved protected run; until then the route answers 503 or 'unknown' even with the switch on.
- The card is not a snapshot. Because it holds no text, there is no second copy of staff-written text in an append-only table with no deletion path, and a later change to a source silently turns the card into 'unknown'. The cost is that a card can stop working without the creator doing anything; the creator sees it as not available and can withdraw it, and it can work again if the same content is approved again.
- The residual risk is that staff-written rationale or next-action free text could contain a price or a contact. The owner sees the exact text in the preview and must acknowledge it before the card is created. No scanner is added.
- What is stored: identifiers, digests, times and an open count. No decision text, token, address, browser string or cookie. The only visitor-derived value is the existing keyed hash used for rate limiting. Seven days is access expiry, not deletion, and no retention promise is made (D06 stays closed).
- Two audit events (created and withdrawn) go through the existing workspace access writer. Opens are counted, not evented, so anonymous traffic never writes outbox rows.
- The public page makes no session lookup and sets no cookie (the public read route already sets none; the page and the chrome hiding are not yet built). The shared header, footer and corner dock are hidden on exactly the /decision-card path by one shared pathname test used by the three shared components (the header stops its session calls, as it already does for the staff customer preview). Because this touches shared chrome, it needs the full operator suite and a real-build check that no get-session request and no Set-Cookie header occurs.
- ADR-070 asked for interviews before building. That condition is waived for building behind the default-off switch only, on the owner's direction. It is not waived for enabling.
- Accepted at the review of the service and routes (E3b step 3), stated here so no screen or copy promises more than is true. The per-token read allowance is shared by all visitors of one link, so a mail scanner or a team opening the link can use it up and give a recipient a rate-limit answer; that answer reveals nothing about whether a card exists. The rate-limit table keeps a keyed hash of the visitor address for an hour, so the page and the owner copy must not claim that nothing at all is stored about visitors. State and preview are not rate limited, because they are for signed-in customers only. A rotation of AUTH_SECRET makes an exact create retry answer 'changed': that is safe, and a new card is needed.
- Limitations: the owner who loses a link cannot see it again (withdraw and make a new one); after a full page reload an unconfirmed create is a new command, so at worst a second active card exists and counts against the five; the open count includes automatic checks.

## Rejected options

A dedicated generation table (a fallback if the owner later wants queryable history); the PDF in object storage (D05 is closed); an unguessable download URL (a second access path); extending the programme report type (it carries totals, outcomes and money); reusing the CLIENT_PROGRESS export permission; character substitution for glyphs the fonts lack.

Decision card: reusing the operator-created delivery link (it needs staff MFA, has a fixed audience, a thirty-day cap and covers a whole publication); a snapshot of the fields in the card; team-wide sharing or withdrawal by any admin; an Open button to count real people (the audience is a bank or co-owner and the fragment never reaches a link scanner); a per-open domain event; cards for real workspaces now; a scanner for prices or contacts in free text; a link longer than seven days; showing the link again after it is closed; waiving ADR-070's interviews condition for enabling.

## Amendment, 11 November 2026: item 1 and the books follow the workspace of the request

Owner decision, 11 November 2026: "No, remove access (Recommended)" (answer verbatim; question paraphrased; ledger entry by S28). Requests and reports made in a workspace belong to that workspace; once a person is removed or leaves, they see none of them, including the ones they wrote. Items made outside any workspace stay theirs.

Scope line. Item 1 says that for the Trip Book "a saved mission has no workspace role, so workspace membership grants nothing". That stays true for roles: membership still adds no right to another person's saved report, and the decision card (item 4) still needs a current owner or admin of the workspace. What it no longer means is that membership is irrelevant to the holder: a Trip Book or Supplier Book is made through `customer.saved_mission_book`, which reads the report through `customer.saved_mission_action`, so while the holder is not a current member of the workspace of the request the report was delivered for, the book refuses with `Saved mission unavailable`, the text of an unknown id, and writes no record. A report saved by bearer link with no such request stays the holder's. A new invitation restores it. No book already generated is altered. See the [ADR-036 amendment](0036-account-saved-commercial-reports.md#amendment-11-november-2026-a-saved-report-follows-the-workspace-of-the-request-it-was-delivered-for) and the [ADR-033 amendment](0033-private-customer-request-authority.md#amendment-11-november-2026-a-removed-member-sees-no-workspace-request-fail-closed), which also carry the decided erasure path. Erasure path, DECIDED by the owner on 11 November 2026: "Yes, add an erasure path (Recommended)", not built by the access fix (PR 410). It is built by erasure PR A and installed by the account lifecycle action; before that install the old state holds: A removed member cannot withdraw their former workspace request or start an erasure request reaching it. This widens ADR-078 gap 2. From that install a removed member who ever held a workspace can file the erasure request and staff can route and find it (a person who never held a workspace is still refused); withdrawing stays refused ("No, workspace decides (Recommended)"). See the [ADR-033 amendment](0033-private-customer-request-authority.md#amendment-11-november-2026-a-removed-member-sees-no-workspace-request-fail-closed) and ADR-078 decision 6.
