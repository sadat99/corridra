# ADR-076: Trip view, scoped books and decision sharing

Status: PARTLY ACCEPTED, 3 November 2026. ACCEPTED and built behind default-off switches: the Trip view (CORRIDRA_UX_TRIP) and the emailed status link in its narrower signed-in form (CORRIDRA_STATUS_LINK, item 5). PROPOSED, not built: Trip Book, Supplier Book (CORRIDRA_UX_BOOKS) and the decision card (CORRIDRA_SHARE_CARD). The export/share field map and seven-day expiry below remain proposed defaults for explicit owner acceptance before implementing those new disclosures. Owner authorized sequential batch implementation and merges. Enabling any switch stays an owner action.

Scope: Batch E, GAP-034/035/041. This extends ADR022 and ADR070 only as explicitly accepted here; existing identity, MFA, RLS, source revocation, approved publication and real-operation controls remain.

## Reused foundations

The saved commercial report already contains an approved itinerary with label, status, reviewed start/end/timezone/location and a scheduleChanged marker. The Room already composes that same report in Compare and Evidence views. Add Trip as another view with the existing CORRIDRA_UX_TRIP flag; no itinerary service, booking engine, canonical meeting change, schema or broader read permission is needed. A changed schedule suppresses stale appointment details. Existing report proof, refresh, expiry, visibility clearing and identity scope continue to apply.

Trip view (accepted). Trip is a fourth Room lens. It shows only when CORRIDRA_UX_TRIP is exactly 'true' and the Room itself exists (CORRIDRA_UX_ROAD). It renders only the reviewed itinerary block of the saved commercial report. When a schedule has changed, it shows the "The schedule changed" notice and none of the old details; delivery SQL 0016 and the report UI already enforce this, and RESCHEDULE_REQUIRED is treated as a changed schedule. It adds no read, query, schema or export, and shows no price, offer or contact. Switching between lenses does not fetch the report again.

CLIENT_PROGRESS currently forbids export. ADR022 requires explicit reporting/export permission; ADR070 is a proposal with an unset sharing expiry. A new button cannot override these boundaries.

## Proposed minimal disclosure contract

1. Trip Book: an explicit authenticated download for the currently permitted owner/admin of one owned saved mission. Include only its approved mission title/company/objective and reviewed itinerary label/status/time/place. Suppress changed schedules. No contacts, quotations, prices, notes, attachments, private identifiers or participant data.
2. Supplier Book: the same authority, with only the already reviewed shortlist company/country, fit/rationale, uncertainty/gaps and provenance/qualification labels. No offers, financial values, contact information or unreviewed suppliers.
3. Keep CLIENT_PROGRESS.allowExport=false. Books use a separate opt-in purpose and explicit field projection. Reuse existing PDF rendering/audit machinery; record immutable generation scope/version/digest and exact retries. A downloaded file cannot be revoked after it leaves the system; say that plainly at download.
4. Decision card: current owner/admin explicitly selects one currently reviewed SELECT/DECLINE/NEED_INFORMATION disclosure and previews the exact fields. Company, decision, rationale, next action, due date and provenance only. No quotation/price/contact/file/other decision. Public reading uses an unguessable fragment token, digest-only storage, read-only response, no-store/no-referrer, at most seven days and never beyond source access. Withdrawal, source loss and expiry answer as unknown. Sharing remains off until configured. No team-wide sharing.
5. Emailed status link (ACCEPTED, 3 November 2026, built behind CORRIDRA_STATUS_LINK, default off). This is narrower than ADR058 and replaces its anonymous 90-day link, which is not adopted. The button in the existing first request email (mission mail "request-received") opens the signed-in Room (/account/rooms/<id>) when CORRIDRA_STATUS_LINK and CORRIDRA_UX_ROAD are both exactly 'true', and the saved request page otherwise. The link grants no authority: a signed-out visitor is sent to sign-in and returned through the ADR067 exact-path allowlist, which applies when CORRIDRA_STATUS_LINK is on as well as when Pulse is on. There is no token, fragment secret, expiry, renewal, new table, retention change or ADR033 amendment. The email carries no request text beyond what mission mail already sends. Anonymous/unlinked requests keep their current receipt behavior. The existing mail transport, queue, deduplication and idempotency key are reused. Building the link does not authorize agent-triggered mail or provider activation, and turning on mission email stays a separate owner step. Rollback: unset CORRIDRA_STATUS_LINK and new emails link to the request page; emails already sent keep the Room URL, which answers not found if the Room is later switched off.
6. Default off: retain CORRIDRA_UX_BOOKS, CORRIDRA_SHARE_CARD and CORRIDRA_STATUS_LINK until their real backend and focused permission/revocation/retry/browser proof exist. No real provider calls, booking or payment expansion.

## Required evidence

Trip reuses current report/Room regressions plus direct Trip rendering, empty/changed schedule, expiry/denial and off-path browser checks. For the accepted Trip view (E1): registry tests that CORRIDRA_UX_TRIP is a flag that is off unless exactly 'true' while BOOKS and SHARE_CARD stay planned; browser tests of the Trip lens showing only itinerary label, status, time and place, with objective, totals, offers and evidence forms absent; no Trip button when the switch is off; a changed or RESCHEDULE_REQUIRED schedule showing no stale details; empty itinerary, no saved report, denial then recovery; one report request across Compare, Trip and Evidence; and layout at 320, 390, 768 and 1440 pixels with no sideways scroll, 44 pixel targets and no axe violations. For the accepted status link (E3a): pure-function tests of the link path and the allowlist switch (both switches exactly 'true' gives the Room, anything else gives the request page; 'TRUE' and '1' count as off); the sign-in return chain accepting only the exact Room path and falling back for any other target; and a real-database mail flow with a recording sender that shows the Room link when both switches are on, the request page link otherwise, no request text or secret in the message, the verified owner as the only recipient, one mail with the same idempotency key after a retry, and no mail for anonymous or synthetic-data requests. New exports/shares require restricted real SQL/service tests for current ownership/role and source authority, field exclusion, exact retries/audit, expiry/revocation and no signed-out expansion beyond the deliberately issued card. Use current renderers and existing isolated fixtures; keep genuine provider/recipient acceptance separate. Frozen CI/CodeQL and automatic deployment verification remain mandatory per batch.
