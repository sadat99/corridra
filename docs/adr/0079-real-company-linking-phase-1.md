## 1. One shared provenance rule

### Decision

There is one rule, named `same context`. A row may be seen by, matched against, or linked by a caller only if the row's own provenance flag equals the provenance of the caller's anchor.

It is expressed once, as one SQL helper: `customer_private.organisation_link_same_context(p_row_synthetic boolean, p_anchor_synthetic boolean)`. It returns true when both values are not null and equal. A missing flag is false. The row flag is `app.organisation.synthetic` for an organisation, and `app.tenant_is_synthetic(tenant_id)` for a claim, a workspace or a ledger row. Nothing else decides provenance.

The anchor is the one thing that differs by caller, and it is always one of the sites below:

| ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Staff paths (candidates, queue, review, decide, suppress, redact, closed-claims lookup, rights read and adjust) and customer search | `customer_private.synthetic_context()`, the session context | One session has exactly one context. For search it is correct only after the writer role check has run (fact 6)                                                                                                                                                                                                             |
| Customer link state (view, overview, command replay), including its label                                                           | `app.tenant_is_synthetic(p_target)`, the workspace itself   | The overview shows many workspaces in one session and never calls the role function. A session anchor would read as real for all of them, and a real-mode person's synthetic workspace would lose its linked name. The label ('(synthetic test)' or not, `0003:2325`) also follows the workspace, not `synthetic_context()` |
| Ledger guard                                                                                                                        | `app.tenant_is_synthetic(NEW.tenant_id)`, the row's tenant  | There may be no session at all (a fixture, a repair). Which context wins. For staff and search the session's context wins, and there is no second side. A real reviewer sees only real claims, real workspaces and real organisations. A synthetic reviewer sees only synthetic ones. A real customer session on a real workspace searches only real organisations; on a synthetic workspace it searches only synthetic ones. This replaces today's behaviour where a real claim is offered synthetic organisations. For a customer's own link status the workspace's own provenance is the anchor.

One session has exactly one context. `synthetic_context()` has no argument. It reads session settings that are set once per request. For a customer, `customer_private.organisation_profile_role(target, actor)` sets the workspace and therefore the context. The build must call the rule only after that role check has authorised the target (as `organisation_link_search` does at `0001:352`). The replaced command function validates its input in two steps: shape checks first (they do not need the context), then, after `lock_workspace_access` has called the role function, the checks that depend on provenance (note and statement length, the `Synthetic ` prefix, URL pattern). Today those provenance-dependent checks run first (`0003:1169-1196`) with an unset context.

Existing rows. No existing row is altered. A cross-provenance ledger row, claim or organisation link, if one exists (none is expected: `decide` has enforced equality since `0003`), keeps its bytes. It stops appearing in search, candidates, counts and queue counts, and it no longer affects a decision. The workspace that holds such a link keeps its status (approved), but the organisation name is not shown. The count of such rows is proven by an integration test on a fixture. The install prints nothing about it: no notice handler exists in the installer, so a notice would not be seen.

### Rejected options

| Option                                            | Reason                                                                                                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Filter only in the UI or the service              | Names and workspace ids would already be in the database answer and in the JSON. A bug or a second caller would leak them. Isolation has to hold in SQL.      |
| Rely on `decide` to keep the two sides apart      | `decide` guards writes only, and its own count has no test. The candidates, queue and review read without it, and that is exactly where the leak (fact 3) is. |
| Repeat the comparison inline at each call site    | Many copies drift. One helper is hash-guarded and tested once.                                                                                                |
| One session-only anchor for every caller          | Breaks the customer overview (fact 7) and cannot work in the ledger guard, where there may be no session.                                                     |
| A provenance column on the claim or ledger tables | Those tables are append-only and the value is already derivable from the tenant. A second copy could disagree.                                                |
| Separate tables or schemas per provenance         | Large rewrite of a working module. It buys nothing the one rule does not.                                                                                     |
| Let a reviewer see both sides with a label        | This is the leak. Real legal names must not reach a synthetic session and the reverse.                                                                        |

### Not covered by this rule

The staff counterparties catalogue (fact 11) and any other reader of `app.organisation` outside the link module still list real and synthetic organisations together and ignore suppression. They are used by authorised research staff, and fixing them is a different module. This is stated, not hidden. It is a Phase 2 item and open owner choice 14.

### Blast radius

- Auth: no role, grant or login changes. A reviewer sees fewer rows, never more. Slice A adds three helpers (the rule, `suppressed`, `redacted`), none granted to the runtime or auth logins.
- RLS: no policy on an existing table changes. Slice A adds two empty tables (suppression, redaction) and the attempts table (see decision 3) with row security on, no policy and no grant. The ledger guard is a trigger function, replaced under a hash guard.
- Migration history: adds a file to `customer_real_use_migrations.applied`. No existing file or hash changes.
- Events: no new event. A staff decision that the ledger guard refuses writes nothing (the whole transaction rolls back, so no half event).
- Money: none.
- Rollback: additive SQL is not undone. Back out functions by a new forward file that restores the previous function text (known in git, hash known). With the flag OFF nothing customer-facing is reachable meanwhile. The evidence URL CHECK is the one exception (see shipping).

## 2. The real organisation source and the lightweight rights record

### Decision

Phase 1 adds no registry import, scrape, API call or provider. Real organisation rows come only from staff ingestion through the existing path. Until the owner names real sources and who vets them, the real catalogue is empty, and real search returns nothing. That is today's state, stated plainly.

Proposed source types (defaults the owner may change). Each type has default rights fields. The last column shows which defaults raise a staff warning.

| Source type (proposed) | Default basis note (staff text, not a legal clearance)        | Default review-by | Default warning                         |
| ---------------------- | ------------------------------------------------------------- | ----------------- | --------------------------------------- |
| `government_registry`  | Public register entry. Register reuse terms not checked here. | 12 months         | none                                    |
| `company_website`      | The company's own public website.                             | 6 months          | none                                    |
| `trade_body_list`      | Member list published by a trade body or association.         | 12 months         | none                                    |
| `event_list`           | Exhibitor or attendee list published for an event.            | 6 months          | none                                    |
| `staff_research`       | Other public research by Corridra staff.                      | 6 months          | none                                    |
| `licensed_dataset`     | Dataset used under a licence. Licence terms not checked here. | 12 months         | `licence_not_checked` (always raised)   |
| `other`                | Source not classified.                                        | 3 months          | `source_not_classified` (always raised) |

Two more warnings apply to every type. `personal_name_check` is raised when the company name contains no legal-form word from the existing name list (the words removed by `customer_private.organisation_link_name_key`). The name may then be a sole trader, which is personal data. It is a prompt to look, not a judgement. `previously_hidden` is raised when the normalised name plus country, or the public identifier, matches an organisation whose latest suppression row is `hidden`. Without it, re-ingesting a hidden company would create a new organisation row with a new id and silently bypass the takedown. So when the match is found the wrapper does two things: it returns the warning to the ingester, and it also appends a `hidden` suppression row for the new organisation id, with a reference that points at the old suppression row. Only owner or admin can show the new row. This is the carry-over of an explicit staff takedown. It is not a rights-record refusal, and the ingestion itself still succeeds. The match is same-context only, so nothing is learned across provenance. It is not tenant-scoped: an ingesting operator of another tenant learns only that a hidden organisation with that name exists (no reason, no reference). This is accepted. The wrapper writes the carry-over suppression row on behalf of an ingest-role operator who is not link staff. That is an accepted exception to "suppression uses the link staff authority". The wrapper generates its own command id for that row and uses a fixed reference text ("Carry-over of suppression row" plus the old row id, about 50 characters), which meets the 3 to 120 character rule. It is computed after the 8-argument call has checked the caller's authority. A direct call to the 8-argument function gets neither the warning nor the carry-over (a stated residual). An unknown or missing source type is stored as `other`.

The rights record. A new append-only table `customer_private.organisation_source_rights` (purpose: one row per version per organisation) holds source type, basis note, a personal-name flag, warnings, a review-by date, the staff tenant and source record it came from, the staff actor, and a reason (required from version 2). For adjust rows it also holds the command id and the request JSON, with a unique key on staff actor and command id, so a retry returns the original answer. The latest version is the current one. Nothing is updated.

Written in the same transaction as ingestion. A new wrapper `app.ingest_public_organisation_with_rights` (the eight existing arguments plus a source type) calls the unchanged 8-argument `app.ingest_public_organisation`, then appends version 1 of the rights record. One function call is one atomic step: the organisation, its identifier, its source row and its rights row exist together or not at all. The wrapper returns the new organisation id and the list of warnings, to staff only. The 8-argument function is not replaced, not re-hashed and keeps its signature. Its one call site (`packages/counterparties/src/index.ts:282`) moves to the wrapper in the build, with a feature check so staff ingestion keeps working in an environment where the wrapper is not installed yet.

What "never refuses" means, exactly. The rights insert has no CHECK that can fail: an unknown source type is coerced to `other`, and every other field is a fixed default or computed text. The wrapper adds no refusal of its own. If the insert somehow failed (an infrastructure fault), the whole ingestion would abort with it, by design, because it is one transaction. "Captured at ingestion" is a convention enforced by the call site, not an invariant: the 8-argument function stays directly callable by the runtime login (`0003:718`). An organisation made by a direct call has no rights row and reads as `unrecorded` to staff. It is still searchable. The rights record never changes who sees an organisation in customer search (the carry-over suppression row above is a staff takedown, not part of the rights record).

Adjust and read. `app.adjust_organisation_source_rights` appends a new version with a mandatory reason. Authority is the ingest roles (owner, admin, operator) of the tenant that ingested the organisation, and the organisation must pass the rule. The tenant is the one in the rights row, or for an `unrecorded` organisation the one in `app.organisation_source` (`0003:731`); in that case the call writes version 1 with the reason. A read function returns the current record and history under the same authority. The database authority is the ingest roles (`research.manage`: owner, admin, operator, `packages/domain/src/index.ts:85`, used at `packages/counterparties/src/index.ts:178-183`). The service routes for rights adjust and read therefore require `research.manage`, not `trust.verify`. Suppress and redact keep `trust.verify` plus their database checks. A reviewer who is not an ingest role is denied rights adjust. A caller from another tenant, from the other provenance, or about an unknown organisation gets the same message: "Organisation unavailable".

Suppression, the one explicit exception to "never changes visibility". A new append-only table `customer_private.organisation_suppression` holds `hidden` and `shown` rows per organisation, each with a reason, a ticket-style request reference, the staff actor, the command id and the request JSON (unique key on staff actor and command id). The latest row decides. A hidden organisation is not returned by customer search or exact match, cannot be filed against, is not offered as a staff candidate, and cannot be newly linked (the ledger guard refuses). History and existing links are kept. A suppressed organisation's name still appears in an existing link, in open claims and in stored receipts. Suppression is not erasure.

Authority is asymmetric on purpose. To hide, any link reviewer (owner, admin or reviewer of the intake tenant, fresh MFA, `customer_private.organisation_link_staff()`) may act, because hiding is the safe direction. To show again (reverse a takedown), the caller must be owner or admin, with a request reference. Both take the organisation lock `decide` uses (`0003:138`), so a hide and an approval cannot interleave.

Not `app.data_rights_policy`, and V3-05-043 stays PARTIAL. The rights record is a defaults-based note. It is not a licence, jurisdiction, transfer or retention decision, and it does not satisfy, replace or close V3-05-043. It makes no legal clearance claim. Review-by dates are recorded and nothing acts on them in Phase 1.

### Blast radius

- Auth: no new role. Ingest authority is the existing one inside the unchanged function. Rights adjust and read use the ingest roles. Suppression uses the link staff authority, with owner or admin for `shown`. One accepted exception: the wrapper appends the carry-over `hidden` row on behalf of an ingest-role operator who is not link staff (it is a copy of an earlier staff takedown, not a new decision). No grant to the runtime or auth logins on any table.
- RLS: two new tables, row security on, no policy and no grant, `app.reject_rewrite()` on update and delete. No existing policy changes.
- Migration history: adds a ladder file. The wrapper is a new function. No hash guard is needed for the 8-argument function because it is not touched.
- Events: no event for a rights row, and rights adjust writes none either (the row names the actor and time, like ingestion today). One event chain for each suppression change (`customer.organisation_catalogue.*`), payload ids, version and state only, never the reason or the reference. An organisation has no tenant, so the event is written in the acting staff session's tenant (for the carry-over, the ingester's tenant). The new event helper copies the `0003` form of `organisation_link_domain_event` (`0003:2229-2256`: the `synthetic` field comes from `synthetic_context()`), not the `0001` form, which hard-codes `synthetic` true and a synthetic executor.
- Money: none.
- Privacy: sole-trader names are personal data in a global table that is readable by the runtime role. Suppression hides a name from customers and from the link module's staff views. It does not remove it from `app.organisation` or from the staff counterparties catalogue.

## 3. Combined search with anti-enumeration

### Decision

`customer.organisation_link_search(uuid, text)` is replaced. The signature and the answer shape stay exactly `{workspaceId, expiresAt, organisations:[{id,name,country}]}`. The existing per-IP request budget stays as the outer layer (today at `apps/web/app/api/customer-organisation-links/route.ts:47` for the GET, `:66` for the POST). Search writes an attempt row, so it is a POST, not a GET. The customer route's POST path takes `scope: "search"` in the JSON body and is guarded by the route's existing POST checks: the `Origin` header must equal `APP_ORIGIN` (`route.ts:61-62`), the content type must be JSON (`:63`), the body is bounded (`:65`, 8192 bytes), then the per-IP budget runs (`:66`), then the search. The response shape stays exactly `{workspaceId, expiresAt, organisations:[{id,name,country}]}`, with `deliveryHeaders` (no-store). In the build, the GET `scope=search` branch of the route (`route.ts:47`) is removed; GET `view` and `overview` stay. The service method `search()` in `packages/auth/src/customer-organisation-links.ts` keeps its SQL call. The client call in `apps/web/app/account/profile/company-link.tsx` (lines 245-262) changes from a GET to a POST. A search that fails the origin, content-type or size check gets an ordinary error response, not the neutral empty list, and the existing screen shows "The company list could not be searched. Try again." (`company-link.tsx:255-262`).

Order inside the function:

1. Existing checks, unchanged: signed in, writer role on the target (this also fixes the context), term 3 to 80 characters with no control characters, saved profile with a country. These raise errors. They say something about the caller, not the catalogue.
2. Take an advisory lock for the actor.
3. Delete this actor's attempt rows older than 24 hours.
4. Count the actor's own rows. If the count is at or over a cap, skip the lookup and answer with the empty list. Nothing is inserted.
5. Otherwise insert one attempt row (actor id and time only), then run the lookup.
6. Fill the 10-row cap with exact-lane rows first, then fill the rest from the name lane, then de-duplicate by id, then order the final set by name and then id. The displayed order carries no lane information.

Every branch builds `expiresAt` by calling `customer_private.organisation_link_expiry()`, including the rate-limited branch.

Lookup lanes. Exact lane: same-country, eligible organisations whose normalised name equals the normalised legal name from the saved profile; or whose public identifier host (without `www.`, both sides) equals the host of the saved profile website; or whose normalised name equals the normalised typed term. The host lane uses only the saved profile website. Typed text drives the name lanes only. This differs from the earlier product default of treating a typed web address as a host (open choice 4), because a typed host would let any writer ask "who owns this domain?" with no link to their own company. A name key shorter than 3 letters, from the profile or from the typed term, never takes the exact lane. Name lane: the existing case-insensitive "contains the term" test. Only organisations that pass the eligibility helper count (same context, current identifier, not suppressed). The caller's own country is always the filter. The answer has no lane label, no total, no "more results" flag and no reason.

Rate limit. Per actor (the person), across all their workspaces. Caps are 10 searches in a rolling 10 minutes and 60 in a rolling 24 hours. Both are defaults the owner may change. They are constants in the replaced function. Changing them is a new hash-guarded replacement, not a settings table. The count reads the actor's own rows in `customer_private.organisation_link_search_attempt`: `id`, `actor_id`, `created_at`, and nothing else, with an index on `(actor_id, created_at)`. No term, no result, no workspace, no foreign key, so account closure and erasure are never blocked by it. The table has no grant to any login. A trigger rejects UPDATE. A BEFORE DELETE trigger rejects deleting any row younger than 24 hours, so rows are immutable inside the window. DELETE of older rows is done only by the definer search function, which removes that actor's rows older than 24 hours while it holds the actor lock. This bounds the table without a scheduler. The advisory lock makes delete, count and insert atomic per person, so two parallel searches at the cap cannot both pass.

Privacy of the attempt table. The rows are personal data (a pseudonymous actor id and a time). They are kept at most 24 hours after that person's next search. A person who never searches again keeps their last rows until a staff pruning step exists (Phase 2). Erasure of a person does not remove them automatically in Phase 1.

What yields the identical empty answer:

| Cause                                       | Same bytes? | Note                                                  |
| ------------------------------------------- | ----------- | ----------------------------------------------------- |
| No match                                    | yes         |                                                       |
| Rate limit reached (10 minutes or 24 hours) | yes         | The function returns, it does not raise               |
| Organisation is in another country          | yes         |                                                       |
| Organisation is in the other provenance     | yes         |                                                       |
| Public identifier expired                   | yes         |                                                       |
| Organisation suppressed                     | yes         |                                                       |
| Organisation has no rights record           | no          | It is returned like any other. The record never hides |

"Same bytes" means the body has the same keys and values in the same order, with `expiresAt` computed by the same function in every branch. `expiresAt` slides with the clock (since ladder `0011` the expiry is the private-view window, up to 30 minutes ahead, `0011_private_view_window.sql:32-47`), so tests compare the body with that value removed and check separately that it is a timestamp not more than 30 minutes ahead.

Scope of this claim. A limited answer is indistinguishable from a miss only for a workspace whose own saved company matches no catalogue entry. For a workspace whose own company is listed, the exact lane always returns it, so an empty list can only mean "limited". That tells the person only about their own quota, nothing about the catalogue. The tests therefore use a workspace whose profile matches nothing for the miss, quota, country, provenance, expiry and hidden rows, and note the per-person quota in the fixtures.

Neutral message. The customer never sees a reason. The existing screen already shows "No listed company matches. Try another word, or choose the other option." (`apps/web/app/account/profile/company-link.tsx:586`). Phase 1 keeps that sentence and builds no screen. A limited customer sees it too, and can retry after the window.

Honest limits, stated and not hidden:

- No timing guarantee. A limited answer skips the lookup and is faster than a miss. That reveals only that this person is limited. All catalogue causes (miss, country, provenance, expiry, suppression) run one statement, but equal time is not promised.
- Sybil accounts are mitigated, not removed. A real session needs a verified email, and the per-IP budget still applies. Someone with many verified emails can still read about 600 rows per account per day (60 searches, 10 rows).
- The profile is self-reported. A workspace owner or admin can edit its country and its website, and each edit is a new revision. So the "same country" filter and the website-host match can be steered by a determined person. The residual: one person can probe up to 60 domains and up to 60 name terms per day. The caps limit how fast. They do not stop it. The names returned can include sole traders or licensed-dataset names, so they are not all harmless public names.
- The route's per-IP budget error is a different answer from the neutral empty list. It tells nothing about the catalogue.
- No search or error path names another workspace, a claim or a count.

## 4. Erasure by a redaction record

### Decision

Customer text on a claim can be hidden by a new append-only record. No row of the immutable tables is changed or deleted.

Scope. One redaction record hides, for one claim, all of: the claim note; every evidence statement and url; every event `reason` and `internal_note`; the stored request and result JSON of the claim's customer commands; the stored request JSON of staff decisions on the claim (it holds reason and internal note); and the legal name, website and summary of the profile snapshot as staff see it in the queue and the review. Redaction is all or nothing for a claim. It is per claim, not per workspace or per person.

Readers mask. Every reader that returns this text is replaced once to return a fixed marker instead: customer link state (`organisation_link_state`), staff review, staff queue, and the customer command replay branch. No reader returns the staff decide request JSON, and the decide replay returns only ids and states, so nothing else needs a mask. The redacted claim's own review returns empty candidates, and a redacted claim drops out of the workspace half of other claims' candidates. Ids, states, times, versions, the ledger and the domain events are kept.

Replay of customer commands. An exact retry would otherwise return a stored result that contains the text. The stored result of a command also holds the whole link state of its workspace at that time, so a later command on claim B can carry claim A's approval reason in `link.reason`. The `organisation_link_request` table has no claim column, and a `file` request has no claim id. So the rule is workspace-wide: for ANY receipt of a workspace that has ANY redacted claim, the replaced command function recomputes the current masked state and never returns a stored result. The comparison of the request for conflict is unchanged. Tests cover a replayed `file` command after redaction, and a replayed `add_evidence` for claim B after claim A of the same workspace was redacted.

Honest wording. The words used to staff and customers are: "this claim's text is hidden in the claim, the staff queue, the staff review and the customer link screens." They are never "deleted" and never "hidden from every screen and export". What is not covered, stated plainly:

- The profile screen and the profile revision (ADR-044 module; Phase 2).
- Programme projections and participant labels that copy the legal name (`customer-programme-projection-migrations/0001:56,250`, `0002:30,137`; `customer-participant-label-migrations/0001:367`).
- Other claims of the same workspace that share the same profile revision.
- The workspace name (`app.tenant.name`), commercial roles, sectors and size band. They are business facts and are kept.
- The derived matching keys `name_key` and `host_key`.
- The bytes in the immutable tables, in the stored customer and staff receipts, and in backups.
- The names in an existing link, a suppressed organisation's name, and the staff counterparties catalogue.
- No export of link data exists in source today, so none is claimed or masked.

Who may redact. Staff with the link staff authority (`customer_private.organisation_link_staff()`) who are owner or admin, with fresh MFA, in a session that obeys KI-41 (`CORRIDRA_REAL_USE_ENABLED=true`, lifecycle and real-use configuration on), and the claim must pass the rule. A reason and a ticket-style request reference (the erasure request or ticket number, 3 to 120 characters, no personal data in it, because it is stored in an immutable table) are mandatory. The command carries the claim id it expects to redact, typed a second time, and the two must be equal. A redaction cannot be undone, so a wrong claim id must fail. Nothing in Phase 1 links a G5 erasure-queue request to a redaction automatically. It is a documented staff step, and the reference field is the link between them. Idempotency: the redaction table holds the staff actor, command id and request JSON with a unique key on staff actor and command id. The same command from the same staff returns the original answer; the same id with other content conflicts. The redaction is irreversible by design. There is no "show again" record, because that would let erased text come back.

Finding the claim id while the customer flag is OFF. The existing staff queue and review answer 503 when the flag is off (`apps/web/app/api/workspace/customer-organisation-links/route.ts:17-18`). So slice B also adds one lookup for erasure authority only (the same authority as redaction), not behind the customer flag, that lists the CLOSED claims of one workspace: ids, states and times, no text. The workspace id comes from the erasure request or ticket (how staff map a person to workspaces is the existing erasure process and is unchanged). A closed claim here means not pending, not needing evidence and not approved for creation; an approved claim is closed and can be redacted. A workspace unknown to the caller or on the other side answers with an empty list, identical to a workspace with no closed claims. Claims that are already redacted are listed with a `redacted` flag. For the real intake tenant, redaction and the lookup also need real use enabled, because `organisation_link_staff()` requires `real_use_configuration.enabled` there (KI-41). The same function also accepts the synthetic intake tenant through `app.intake_destination` without that configuration. Redaction takes the workspace lock `customer.organisation_link:<tenant>` that every other write on that workspace takes.

The residual, said plainly. A claim that is still open cannot be redacted. It must first be rejected through the existing decision, which lives behind the customer flag. So a flag-off period with an open claim blocks erasure of that claim until the flag is turned on again. This does not arise in Phase 1, because the flag has never been on and no claim exists. Before any pause of the flag after claims exist, the owner must decide how to handle it (open choice 12).

Effect on an active link. The link stays. The customer sees status "approved", the organisation name and country, the existing label, and the reviewed profile version. The staff reason for the approval and all the claim text show as hidden. A staff revoke (OD5) still ends the link and is a separate decision.

The event for a redaction carries ids, version and state only, never the reason or the request reference.

### Rejected options

| Option                                          | Reason                                                                                                                                                                  |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Update the text columns to null                 | Every link table except the attempts table has `app.reject_rewrite()`. It would break the append-only rule the whole module rests on.                                   |
| Physical delete                                 | Breaks foreign keys, the event chain and the ledger. "Deletion without manifest and guardian PASS" is a closed gate.                                                    |
| Crypto-shredding (encrypt text, drop the key)   | No key management exists in this module. A new security system is a larger decision than Phase 1.                                                                       |
| Redact a copy of the tables                     | Two sources of truth. The original stays readable.                                                                                                                      |
| Redact per field                                | More states to test and explain. All-or-nothing is the honest scope of a removal request.                                                                               |
| Map a replayed receipt to its claim             | The request table has no claim column and the stored result mixes claims. A workspace-wide recompute is simpler and cannot leak.                                        |
| Allow reveal of a redaction                     | Defeats the purpose.                                                                                                                                                    |
| Depend on the account-lifecycle staff authority | That module is optional and may be absent. Calling a missing function would fail at run time. The link staff authority plus owner or admin is the same strictness here. |
| Do nothing                                      | G5: erasure is a request staff must complete within the legal deadline, keeping the records the law requires.                                                           |

### Blast radius

- Auth: no new role. Owner or admin of the intake tenant with fresh MFA, inside the existing staff gates. The new functions are granted to the runtime login like the other staff functions. The table has no grant.
- RLS: one new table, row security on, no policy, no grant, `app.reject_rewrite()`. No existing policy changes.
- Migration history: readers are replaced in slice A and the writer and lookup are added in slice B, so each function is replaced once. All under hash guards.
- Events: one event, audit and outbox chain per redaction, `customer.organisation_link.redacted`, ids, version and state only, written in the claim's workspace through the existing `0003` form of the event helper.
- Money: none. Invoices and signed decisions are outside this module and unaffected.
- Rollback: a redaction cannot be undone. A bad deployment of the writer is backed out by a forward file. Rows already written stay.

## 6. Test plan

### Decision

Tests follow the module pattern (`tests/integration/customer-organisation-links.test.ts`, `real-customer-modules.test.ts`) and prove the following. No existing test is weakened. Every new test must fail on the base commit for the behaviour it adds (a "bite" check).

Full matrices live in the spec. Headers:

- Provenance matrix. Rows: path (customer search, exact lane, candidates organisation half, candidates workspace half, linked-workspace count, queue `candidateCount`, review payload and its `decisions`, `decide` approve and its shared count, ledger guard, EXISTING filing, customer view and overview for a person with a real and a synthetic workspace, and the new staff writers: redact, closed-claims lookup, suppress, rights read and adjust). Columns: real customer, synthetic customer, real staff, synthetic staff. Each cell has an expected result.
- Orphan matrix. Rows: real claim to a synthetic organisation and the reverse; a cross-provenance ledger row (count, approve, revoke); a ledger row whose organisation is later suppressed; an organisation whose identifier expired; a claim with a redacted note still in candidates; an organisation with no rights record (and adjusting it); the workspace half after another claim is redacted; a replayed receipt after redaction; a re-ingested hidden company.
- Empty-answer table (decision 3), with byte comparison.

Other required items:

- Populated-database preservation: install on a database with data; every pre-existing row and function (outside the replaced list) has an unchanged hash; `app.organisation`, profile revisions and the 8-argument ingest function are unchanged. The cross-provenance fixture rows are unchanged by hash.
- Repeat install changes nothing. A changed or missing applied file is refused with the history-mismatch error. A drifted live function aborts at its guard and nothing is applied. The three refusing installers run after the ladder is current.
- Direct SQL denial: the runtime and auth logins cannot read or write any new table (including DELETE on the attempts table), and cannot call any new private helper.
- Roles: owner and admin search; member, outsider, revoked and disabled customers are denied; signed-out and expired proof are denied; wrong tenant staff, operator, viewer and stale MFA are denied for staff functions. Redaction and `shown` deny a reviewer who is not owner or admin.
- Rate limit: 10 in 10 minutes and 60 in 24 hours; rows older than a window stop counting (fixture rows with older times); rows older than 24 hours are deleted by the next search of that actor and no one else's; counts span two of the person's workspaces; two parallel searches at the cap produce exactly one counted lookup; no term is stored (scan the table); UPDATE on the table is rejected.
- Byte identity of a miss and a rate-limited answer (and every other cause in the table), `expiresAt` removed and checked separately.
- Command order: a provenance-dependent input check (short note, `Synthetic ` prefix, URL pattern) uses the workspace's provenance after the role call, for a person who owns a real and a synthetic workspace.
- Redaction: open claim refused; typed claim id mismatch refused; every reader masks; replayed `file` and replayed `add_evidence` of another claim of the same workspace show the masked state; immutability (updates and deletes rejected); the active link survives; the redacted claim's own review has no candidates.
- Event content privacy for redaction and suppression events: ids, versions and state only.
- Ledger guard message: a `linked` insert for a hidden organisation, or a cross-provenance one, fails with "That organisation is not available for linking".
- A real (non-`.test`) evidence URL passes the table check for a real tenant and a non-reserved URL still fails for a synthetic tenant.
- Wrapper: all source types; unknown type; `previously_hidden`; same-transaction atomicity (a failure after ingestion leaves no organisation and no rights row); the 8-argument function hash unchanged; a direct call yields an `unrecorded` organisation; adjusting that organisation writes version 1 with the reason and the tenant from `app.organisation_source`.
- Carry-over: re-ingesting a company whose organisation is hidden (same name key plus country, or same identifier, same side) succeeds, returns `previously_hidden`, and appends a `hidden` suppression row for the new id that points at the old row; only owner or admin can show it. A hidden organisation of the other side is not matched. A direct call to the 8-argument function gets neither.
- Rights authority: an operator of the ingesting tenant can adjust and read through `research.manage`; a reviewer-only actor of the same tenant is denied adjust; another tenant is denied; suppress and redact still need `trust.verify` and their database checks.
- Search route: a POST with `scope: "search"` in the body and a wrong or missing `Origin`, a non-JSON content type or an oversized body is refused before any lookup and writes no attempt row; a valid same-origin POST passes; the per-IP budget still applies; the response keys are unchanged; the GET `scope=search` branch no longer answers. The operator test file `tests/operator/v3-organisation-links-ui.spec.ts` needs handler edits, not only a method swap. `openCustomer` (lines 132-146) answers search only for GET, so it gains a POST branch that answers a body with `scope` "search" with the same fixture. Test 1 (lines about 155-180) registers a later route on `**/api/customer-organisation-links` that takes every POST, pushes to `posts` and returns a view with no `organisations`; its POST handler must call `route.fallback()` for body scope "search" before `posts.push`, or the search POST would be swallowed and `expect(posts).toHaveLength(0)` would fail. These are handler edits with no assertion changed. The no-weakening rule holds: every existing expectation stays as written. Result order: with more exact-lane rows than fit, the final 10 are ordered by name then id, and a fixture where the order differs from lane order proves the displayed order carries no lane information.
- Attempts table: a BEFORE DELETE trigger rejects deleting a row younger than 24 hours, even as the table owner; UPDATE is rejected; only the search function removes older rows of that actor.
- Denial and recovery states: stale profile version refused; exact retry returns the original answer; conflicting command id conflicts; redacted-then-retried claim shows the masked view; a limited customer sees the neutral list and can retry after the window.
- Measurable: zero cross-provenance rows in any search or candidate output across the matrix; at most 10 rows in any answer; workflow input count still 25.

## Consequences

- Real and synthetic data stop meeting in the link module's staff views, count and search. This also closes the legal-name leak (fact 3) that exists in installed code today, behind the flag. Other readers of `app.organisation` are not covered (fact 11).
- Staff get a light, honest record of where an organisation came from and a way to hide one without losing history.
- A takedown or erasure request can be met by hiding, not by deleting. The text stays in immutable storage and backups. This must be said plainly to anyone who asks.
- The two-file install replaces 9 existing functions, all in slice A (8 read-side functions and the search), and none in slice B. Each is hash-guarded, so a drifted environment aborts instead of being overwritten. The builder must compute the hashes from a clean install at the build base, and re-read them if main moves.
- Search gains a write and a delete (the attempt rows). They are serialised per person and bounded.
- Real search stays empty until the owner names sources and staff ingest real organisations. That is data work, not code.

## What this record does not claim

Designed only. Not implemented, tested, deployed, installed, enabled, approved or live. The register states for V3-06-002, V3-06-011, V3-01-018 and V3-05-043 are not changed by this record. The rights record does not close V3-05-043. A link still means "reviewed by Corridra staff from the evidence supplied", never verified.
