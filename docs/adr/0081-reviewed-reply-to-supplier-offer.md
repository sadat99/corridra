# ADR-081: A published supplier reply carried into the supplier offer form

Status: Accepted for build by the owner, 12 November 2026 (answers recorded under Owner decisions). The schema review of migration 0003 and its install remain the owner's. Nothing is installed or enabled. It extends [ADR-069](0069-reply-page.md) (Publish "prepares the mission quotation ... the Corridra team confirms it through the existing quotation form") and [ADR-026](0026-commercial-mission-execution.md) (original offers and revisions) and keeps [ADR-016](0016-mission-intake-and-operator-commands.md) command rules, [ADR-039](0039-explicit-commercial-decision-disclosures.md) and [ADR-040](0040-reviewed-delivery-to-requesting-customer.md) publication and delivery authority unchanged.

## Context

The owner approved the operator slice on 12 November 2026: a Corridra team member carries a reviewed supplier reply into the existing "Record a supplier offer" form, reads the terms and confirms through the existing command. Customer publication stays a separate decision. Read from the code at main bd3b4257:

1. **A reply is tied to one RFQ and one supplier already.** `app.recipient_detail_response` holds tenant, link and body (migration 0025). Its link has exactly one `app.recipient_disclosure` (unique per link), and a reply can carry a quotation only when that disclosure is `SUPPLIER`, `allow_quotation` and names an `rfq_id`; the disclosure guard refused it unless the RFQ lists the link's `app.communication.target_id` and that target belongs to the RFQ's mission. So reply, RFQ, mission and supplier target are derivable in SQL; the operator does not need to choose them, and one target sitting in several RFQs does not make the reply ambiguous.
2. **The review does not store the version it decided on.** `app.recipient_reply_review` (reply review module, installed in production at 2 migrations) stores response id and decision. Where answer correction is installed, `app.review_recipient_reply_seen` refuses a decision on a version the reviewer did not read, and `app.recipient_detail_revise` refuses any correction after Publish or Reject, both under the lock `app.reply_review:<tenant>:<reply>`. So after Publish the reply is frozen: the latest version is the published one. The correction module is not installed in production (ledger, 12 November); without it every reply is version 0, its original body.
3. **The quotation command has no reply field.** `commercialMissionCommand` action `quotation` (packages/domain/src/commercial-missions.ts) is `.strict()`: rfq, target, revision, previous, currency, terms, uncertainties, observed time, and an operator-chosen `sourceId` and `claimId`. `CommercialMissionService.command` (packages/missions/src/commercial.ts) runs under `missions.manage` (owner, admin, operator), takes the tenant lock `<tenant>:commercial-missions`, replays by `commercial_mission_command` id and input hash, and inserts `app.mission_quotation`, whose guard checks the current mission, current requirement version, RFQ membership of the target, route currency, revision chain, term names and exact minor units. **No fresh authenticator check is required for this command today.**
4. **Nothing at the write boundary links an offer to a reply.** The prepared quotation is plain text (`preparedQuotation`, apps/web/lib/reply-review-view.ts) copied by clipboard (apps/web/app/operator/reply-review.tsx), re-typed into the form and re-parsed through decimal money input. ADR-069 lists "an operator publishing without review (the review record is required before the prefilled quotation can be confirmed)" as a handled abuse case; the code does not enforce it.
5. Supplier offer terms hold no staff cost or markup. Private acquisition cost and markup exist only on service quotes ([ADR-073](0073-commercial-arrangements-on-service-quotes.md)), which this decision neither reads nor writes.

Requirements: V3-02-027 (preserve original supplier responses and quotation revisions), V3-02-041 (original quotations, currencies and evidence stay accessible), V3-05-019, V3-04-077 (no hidden material terms), V3-04-076 and V3-05-033 (scoped publication stays its own authority).

## Decision

The smallest safe change: one append-only binding row written in the same transaction as the existing quotation insert, one optional field on the existing command, one write function and one read function, shipped as migration `0003` of the existing reply review module.

1. **Binding table** `app.reply_quotation_binding`: id, tenant, `quotation_id`, `response_id`, `review_id` (the Publish row), `reply_version` (0 to 20), `body_sha256` (64 hex), `mission_id`, `rfq_id`, `target_id`, `created_by`, `created_at`. Tenant-scoped foreign keys to each parent. Unique per quotation and unique per reply: one reply becomes at most one recorded offer. A later supplier change arrives as a new reply and is recorded as the next revision of the same RFQ and supplier through the existing revision chain. No supplier words, terms, amounts or notes are copied into it. Row level security is on; immutable (`app.reject_rewrite`); the existing `app.record_change` event, audit and outbox trigger (payload is id and version 1 only; the column is named `reply_version` so it is never read as the event version).
2. **Read policy**, in the usual sample and real-use pair: a runtime reader sees a binding only if they can read both its offer (`app.research_target_access` on the target) and its reply (the reply table's own policy). Grants: SELECT to `corridra_runtime`; nothing to `corridra_auth`, `PUBLIC` or any customer schema role; no direct INSERT for anyone at runtime.
3. **Write function** `app.bind_reply_quotation(quotation uuid, reply uuid, seen integer, digest text) RETURNS jsonb`, SECURITY DEFINER, `search_path=pg_catalog`, EXECUTE to `corridra_runtime` only. It refuses unless all of these hold, re-checked after its locks:
   - a signed-in actor in the transaction's tenant whose role is owner, admin or operator (the quotation command's authority), and the tenant's sample or real-use access passes (`app.can_access` with the tenant's processing purpose, as the review policies do);
   - the reply review control is open (`app.reply_review_open()`);
   - the quotation row was inserted by this actor **in this transaction**: `created_by` is the actor, `created_at = now()` (the transaction start, the test `app.guard_delivery_experience` already uses) and its `commercial_mission_command` row is not written yet; and no binding exists for it or for the reply;
   - the reply belongs to the tenant, is still retained and is readable by the actor (`app.buyer_link_access`); otherwise one message, "Reply not found", whatever the cause, so other tenants' ids are not probed;
   - a `PUBLISH` review exists for the reply in the same tenant;
   - the reply's disclosure names the quotation's RFQ, the RFQ's mission is the quotation's mission and lists the target, and the link's communication target is the quotation's target;
   - after the lock `app.reply_review:<tenant>:<reply>` (the review and correction lock), `seen` equals the latest version (0 when the correction module is not installed, found by name as `app.recipient_response_decided` does) and `digest` equals `sha256` of that version's stored body text, and no correction is newer than the Publish row;
   - the quotation's currency, terms object and uncertainties equal the reply quotation's exactly (exact minor-unit strings, original currency, every supplied term and no added one), and its observed time equals the time the supplier gave that version;
   - the quotation's source record is of kind `self_declaration`, so a supplier statement is never recorded under a document, observation or public-record source.
   Lock order is the tenant commercial-missions lock (taken by the existing service and guard) and then the reply lock; the correction and review paths never take the tenant lock, so the order cannot invert.
4. **Read function** `app.reply_quotation_prefill(reply uuid) RETURNS jsonb`, SECURITY INVOKER and STABLE, so it reads only what the caller's existing policies allow. It returns the typed terms for the form: response id, `seen` version, `digest`, mission, RFQ, requirement, target, original currency, the terms filtered to the nineteen offer term names with minor units as exact integer strings, uncertainties, the supplier's statement time, source kind `SELF_DECLARATION`, the next revision and previous offer id for that RFQ and supplier, and an eligibility verdict naming the first blocking reason (no Publish, already recorded, no quotation, review closed, currency not on the route, requirement superseded, reply no longer retained). It never returns the link token, contact data, the review note or anything outside the nineteen term names.
5. **Command field.** The `quotation` action gains one optional strict field `replyBinding: { responseId, seen, digest }`. Without it, behaviour is byte for byte unchanged. With it, `CommercialMissionService.command` inserts the quotation exactly as today and then calls `app.bind_reply_quotation` before the command row, in the same transaction; any refusal rolls back the offer, the binding, the command record and their events together. The field is part of the existing input hash, so a retry with the same command id replays and a different reply under the same id conflicts. The function's own refusals are passed through as plain words (narrow allow-list in the service); every other database message keeps the route's existing generic text.
6. **Form.** The existing form takes the prefill and sends the exact strings it received; supplier amounts never pass through decimal parsing. The team member reads every supplied term and every missing one (shown as "Not stated", never zero), picks the self-declared source and claim, writes the reason and confirms. A change to a term is not made on this path: they either ask the supplier through the existing Ask (before Publish) or record their own offer through the unchanged path without the reply link. Screens and words belong to the design lane. The clipboard copy stays as the fallback wherever migration 0003 is not installed.
7. **Authority unchanged.** The review stays owner or admin with a fresh authenticator check. Recording stays owner, admin or operator. Publication to a customer stays `delivery_experience_publication` under owner or admin with a fresh authenticator check; nothing here writes, reads or triggers a publication, a customer read, a notification, an outreach message, an acceptance, a payment or a finance record.
8. **Installation.** A new file `packages/db/recipient-reply-review-migrations/0003_reply_quotation_binding.sql`, additive only, with a prerequisite guard. It is applied only by the existing protected installer action `reply_review_action=install` (the owner approves the environment); the module installer already applies every file in its directory in order, so no installer, workflow or switch change is needed. Builds never migrate. The application paths are behind the existing `CORRIDRA_REPLY_PAGE` switch and report the binding as unavailable when the function is absent.

## Blast radius

- **Tables.** New: `app.reply_quotation_binding`. Read, never written: `app.recipient_detail_response`, `app.recipient_detail_response_revision` (when present), `app.recipient_reply_review`, `app.recipient_disclosure`, `app.buyer_link`, `app.communication`, `app.mission_rfq`, `app.mission_quotation`, `app.source_record`. No existing table, column, constraint, policy, trigger, grant or function changes.
- **Functions.** New: `app.bind_reply_quotation`, `app.reply_quotation_prefill`. Unchanged: `app.guard_commercial_mission`, `app.review_recipient_reply`, `app.review_recipient_reply_seen`, `app.recipient_detail_revise`, `app.recipient_detail_respond`.
- **Roles.** `corridra_runtime` gains SELECT on the new table and EXECUTE on the two functions. `corridra_auth`, `PUBLIC` and customer roles gain nothing. No role, permission or membership rule changes.
- **Routes and code.** The existing `/api/workspace/commercial-mission` POST accepts the optional field; one new read action on the same route; the reply review card and the existing offer form change. No new route family, switch or provider.
- **Money and history.** Offers stay append-only with the original currency and exact minor units; the binding can only make a recorded offer match the supplier's words more strictly. Nothing is converted, totalled, invoiced or paid.
- **What can break.** A wrong check refuses a confirmation that should pass (the plain path still works); a wrong lock order could deadlock a confirmation against a correction (the lock order above prevents it, and a test covers it). Nothing else reads the new table.
- **Rollback.** Pause reply review (`reply_review_action=pause`): the binding function refuses and the form falls back to copy. Or deploy compatible source without the field. Bindings, offers, replies and events are kept; no row is deleted. A defect in the SQL is fixed by a forward migration.
- **Unchanged.** The plain offer path, its authority and its messages; reply review, Ask, correction and their controls; customer publication, reports, books and decision cards; real-outreach, provider, payment and synthetic-only gates; the sample-only reply page.

## Abuse cases

- **Publishing without review**: refused unless a Publish row exists for the same tenant and reply.
- **A newer correction than the one read**: refused on version or digest mismatch; after Publish a correction is already refused by ADR-069.
- **Carrying a reply to the wrong mission, RFQ or supplier**: refused unless the reply's own disclosure, RFQ and communication target match the offer.
- **Inflating or editing the supplier's price or terms while claiming the reply as source**: refused unless currency, every term, uncertainties and statement time are exactly the reply's.
- **Upgrading evidence**: a self-declared reply cannot be recorded under a document, observation or public-record source.
- **Lost role, lost target or reply access, removed member**: refused by the existing permission check before any read and again inside the function after its locks.
- **Expired eligibility** (reply retention ended, review paused, mission closed or cancelled, requirement superseded, route currency removed): refused by the function or the existing guard, and shown by the prefill before typing.
- **Double click, two team members, replay**: the existing command id replays; a second command for the same reply is refused ("This reply is already recorded as an offer"), backed by the unique key; the tenant lock serialises both.
- **Another workspace's ids**: one "Reply not found" for every cause; policies scope every read.
- **Staff cost or markup leaking**: offer terms have no such field, the command and SQL refuse unknown term names, and the binding and its events carry ids only.
- **Customer exposure by side effect**: none; publication is untouched and still needs its own approval.

## Rejected options

- **Assisted copy without binding (today).** Keeps the clipboard and re-typing. Fails V3-02-027 and V3-02-041: nothing proves the recorded offer is the supplier's statement, a re-typed or re-parsed amount can drift, a correction can be missed, and ADR-069's review-required abuse case stays unenforced.
- **Store the binding in the command's JSON result or in the quotation terms.** Rewrites the meaning of existing records and puts provenance where no constraint checks it.
- **Let the operator choose the RFQ and target and only check membership.** The reply already fixes both; a choice adds a way to be wrong.
- **Create a new source and claim from the reply in the same transaction.** Writes trust records from a new path with its own rights, retention and locator questions; larger review for no gain in this slice. Kept as an owner option below.
- **Add a fresh authenticator check to the bound path only.** The plain path records any offer without one, so the check would add friction without removing a risk; publication, where exposure happens, already requires it. Kept as an owner option below.
- **A separate module and installer action, or a new switch.** More owner steps; the binding has no meaning without reply review, and pausing review must stop it.
- **A trigger on `app.mission_quotation`.** Changes a core guard path for every offer.

## Owner decisions

1. Who may confirm a bound offer: A, owner, admin or operator, the same as recording any offer today (recommended); B, owner or admin only.
2. Fresh authenticator check on the bound path: A, none, the same as the existing command (recommended, see Rejected options); B, required.
3. Source for the bound offer: A, the team picks an existing self-declared source and claim, checked in SQL (recommended); B, the transaction creates a self-declared source and claim from the reply (larger change, new trust writes).
4. Schema review of migration 0003 and the install through `reply_review_action=install` stay with the owner.

Owner answers, 12 November 2026, verbatim choices: build "Approve and build (Recommended)"; decision 1 "Owner, admin or operator (Recommended)"; decision 2 "No, same as today (Recommended)"; decision 3 "Team picks an existing self-declared source (Recommended)". Decision 4 stays open until the owner reviews migration 0003 and approves its install.

## Required acceptance

Database (integration): installs additively and repeatably, a changed file stops it, with and without the correction module; runtime and auth cannot write the table or call anything not granted; positive bind for version 0 and for a corrected then published reply; refusals for no Publish, Ask only, Reject, newer or stale version and wrong digest, wrong mission, wrong RFQ, wrong supplier, other tenant, changed term, amount, currency, uncertainties or statement time, non-self-declared source, lost role, lost target access, removed member, review paused, reply retention ended, mission closed, requirement superseded; same command replays, a changed command conflicts, a second command for the same reply is refused, two concurrent confirmations end with one offer; a refused bind leaves no offer, command row or event; events carry no words, terms or digest; no publication or customer-visible change follows. Unit: the command field is strict and only on `quotation`; the prefill schema keeps exact minor-unit strings and original currency and rejects unknown term names. Operator browser: publish, carry, read, confirm at the smallest supported width; refusal, conflict and unavailable states; copy fallback when 0003 is absent.
