## 1. Objective

Make Corridra look, read and behave like a calm, precise, globally credible product that serves the business: more qualified mission requests, more introductions accepted, faster operator delivery, and trust that holds up. Presentation and navigation only. The backbone (domain, API, authentication, RLS, money, evidence, permissions, readiness gates) does not change in this programme. UI first, then backend work, as the owner decided.

Governing product direction is [Corridra Product Vision v2.1](../product/corridra-product-vision-v2.1.md); [product-vision.md](product-vision.md) is the working summary. Design rules live in [ui-direction.md](ui-direction.md).

1. Header stays at five items; "For Institutions" stays in the footer and on the home lead section.
2. Home headline: the lead section used "Going to China? Know who is worth meeting." Superseded by the two-routes heading (PR 54). The Fusion-approved hero headline is unchanged for now.
3. Sourcing is the primary action on the lead section; delegations are secondary.
4. "Request" replaces "brief".

Still needs the owner:

1. Review the privacy page wording. It is legal text and still says "briefs" while the screens say "requests". It was left unchanged on purpose.
2. Confirm or change the hero headline (the Fusion headline "The right market. The right people. The next move." versus a situation headline).
3. Decide whether to soften the notice on the request page and the "coming soon" wording on the sign-in page. Both were kept on purpose because people enter details there or the state is functional.
4. Choose the next piece of work: the data-driven corridors list with a configuration-only test corridor (UI and tests only), or institution accounts from the audit (changes authentication and migrations, so it needs an explicit go-ahead and an ADR).
5. Authorise or decline the audit's roadmap pull requests ([saas-readiness-audit.md](saas-readiness-audit.md)): real-data admission and tenant provisioning come first.
6. Configuration, not code: re-create `NEON_AUTH_COOKIE_SECRET`, `NEON_AUTH_BASE_URL` and `OPERATOR_RECOVERY_EMAIL_KEY` as Sensitive variables in the Vercel project, because Vercel flags them as readable secrets. Only the owner can change them.
7. External items from the audit that only the owner can start: legal entity and documents, payment-provider eligibility, a private EU scanner and storage, branch protection. They are tracked in the [deferred controls](../implementation/deferred-controls.md).

Nothing is in progress at the time of writing. The last application release is PR 55; PR 56 changed documents only.

## 5. How to keep this file current

1. Change this file in the same pull request as any change to scope, order, decisions or status.
2. Add a row to the revision log for every owner decision, withdrawal or reversal. Never delete a row. Mark a superseded decision in the "Effect" column.
3. Move an item from "Open" to the log when it is decided.
4. Keep the current plan table short: one row per step, one next action.
5. The work log says what was done. This file says what the plan is.
