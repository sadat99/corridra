# V2 Part 3 product and delegation operations

Use the existing operator workspace and tenant permissions. All mission operations remain synthetic. Customer identity signup is independently live; it does not activate customer mission processing.

1. Review a short brief from `/plan`. Company country and target market are explicit; unsupported directions remain unconfigured. Assign a reviewed route through existing configuration, then collect requirements and evidence through Part 2 services.
2. Prepare a delivery programme and import participant briefs through the existing bounded CSV/XLSX workflow. New optional columns `companyCountry`, `marketCode`, `missionJob` must be supplied together. Each accepted participant remains an independent mission. Confirm the visible import counts.
3. Record organiser, market, dates, commercial purpose, time zone, human owner and reason in the programme experience panel. Add a proposed agenda with participant mission IDs and owned next action/deadline. Confirm only against actual accessible scheduled/held meetings. Shared meetings must have the same actual time/venue; a cancelled/rescheduled version requires review.
4. Publish reviewed mission copy and select meetings/outcomes through existing delivery. An owner/admin with fresh MFA may then approve exact requirements, targets, original quotation revisions and participant agenda rows. Later assessments never silently replace the pinned snapshot. Explain uncertainty and stale comparisons.
5. Create an expiring CLIENT capability for that publication. A guest may redeem it at `/client`; a verified Neon customer may paste the same invitation in `/account` My missions. Account email alone never confers access. Tokens remain in memory and must not be pasted into logs, tickets or evidence screenshots.
6. For an institution, select only authorised participant publications and reporting/export permissions. Tick the explicit delegation-context option when required. Old links default to false. Context and agenda are bounded by creation time and approved participant meeting versions. No confidential quotation extension is included. Explain the declared versus explicitly attributed distinct-company denominator.
7. Prepare an existing policy-gated recipient introduction and capability. An owner/admin with fresh MFA may approve a purpose-limited supplier/distributor/partner disclosure and exact RFQ for enabled quotations. Never include private contact/relationship notes. Record outbound action manually only under existing policy; this feature sends nothing automatically.
8. Review recipient declarations and optional visit interest in the workspace. Follow the normal source/claim, quotation and meeting services for subsequent decisions. A declaration is not verification, acceptance, attendance, an order or payment.
9. Revoke capabilities when no longer needed. Expiry, opt-out, publisher access loss and source retention deny subsequent access, including retained reply reads. Do not extend retention by duplicating a source.

English is the interface language. Bangla guidance and English/Bangla date/number choices do not claim full translated UI. Enter original Chinese names and terms unchanged. Preserve translations separately as derived information. Original monetary amounts use the selected registered currency precision; no FX is applied. Dates display with explicit zones, and units remain original text.

## Release and recovery

Keep Git and Neon branch totals at or below ten. Preserve unfinished PRs, required live branches and sterile parents. Validate locally with the normal full gates, actual scanner/PostgreSQL and Chromium. Never overlap integration runs that reset the same isolated fixture database. Validate migration 24→25 and replay on a verified sterile-template child, then delete only that exact completed child after evidence capture. Inspect the exact live synthetic branch and original migration hashes before a separate live migration job; digest all original application/identity columns and row counts before and after. Never target the independently managed customer-auth project.

Publish one product PR, obtain passing checks on its exact final head, apply the separately inspected safe live migration, then merge normally. Verify the production alias, READY deployment ID and exact merged SHA, public routes and anonymous access boundaries. Check recent error/fatal logs. Delete only the completed product branch after ancestry verification; preserve every unfinished dependency PR. Roll back application entry points using a compatible Part 2 deployment, retain migration/history and issue forward fixes. Builds never run migrations.
